## 1. 配置和运行范围

日常运行 main.py：先按 configs/post_extraction_config.yaml 运行round1事件提取，正常结束后自动导入本次范围内已成功保存的帖子。主入口启动前也读取 configs/event_processing_config.yaml，取得事件去重分析表路径和账号代币映射；导入来源、日期范围固定沿用本次round1事件提取实际参数，不要求手工同步两份配置的日期。initialize_mode 只控制独立导入入口，main.py 不依赖此模式。

round2事件去重归组与round3事件影响分析仍分别启动，读取 configs/event_processing_config.yaml。独立导入入口保留，供单独核查或处理历史数据；日常不必再手动执行。

round1帖子事件提取表路径和事件去重分析表路径必须不同，路径原样交给客户端。两份 AI 配置的相对路径按 event_processing_config 所在目录解析。认证仍由已有 AI 配置模块读取环境变量或配置目录的 `.env`。

任务、事件、AI 和 Embedding 的 YAML 配置统一拒绝同一字典内的重复键，键须为字符串；重复键即使值相同也报错，不保留其中某一次，也不合并两次的值。例如 user_name_to_tickers 中同一账号先写 [BTC]、再写 [ETH]，加载配置时停止，尚不创建数据客户端或导入事件。一个账号需要映射多个代币时，只写一次账号键，对应 [BTC, ETH]。不同字典内使用相同键名合法。

`start_time/end_time` 须同时为带引号的 `YYYY-MM-DD`，两端包含全天；第二、三轮必须填写，未设置时在读表前停止。独立导入仍允许两端同时为空并沿用原有全范围规则。范围使用帖子原发布时间，不转换时区，不是程序从启动到结束的时间；再次运行不自动扩大任务范围。history_lookback_months 默认 3，须为正整数日历月数，供第二轮前史、候选和向量准备共用；第三轮 repeat 继承响应使用独立的严格此前规则，不使用该配置。

事件去重分析表仅由一个运行程序协调写入。round2事件去重归组与round3事件影响分析分别启动；同一张事件去重分析表不支持多个独立程序同时抢占，状态认领不是数据库锁。AI 请求在程序内部并发，所有数据读写都在调用线程。

## 2. 检查round1事件提取并展开记录

自动导入直接接收round1事件提取每段保存结束后交出的内存数据：一份是本次调用 AI 后成功保存的帖子；另一份是本段读取round1帖子事件提取表时已经 status="1"、本次未再调用 AI 的帖子。两份都使用 date/id 索引及 text、user_name、status、ai_response_content，事件内容来自 ai_response_content 中的 events，导入时不再 read round1帖子事件提取表。失败帖本次不导入，以后补跑成功后再导入。独立 import_event_records_from_table 入口仍读取源表，默认 successful_only=False 要求范围内全部成功；传 True 时只选择成功帖。

独立导入继续比较本批成功帖对应的已有记录，同日其他帖子及其任务不属于本批核对范围；固定输入冲突时停止。main.py 本次读取 round1帖子事件提取表时没有帖子已经 status="1"，就不读取事件去重分析表的数据；只要有帖子读取时已是 status="1"，导入时就读取事件去重分析表，仅核对索引，不比较已有行的业务字段。原帖 ID 必须稳定唯一，成功状态不人为回退；历史输入、映射或状态被修改时，使用独立导入核查并决定重算范围。

实际 JSON 须恰好为 `{"events":[{"event":"事实", "tickers":["ETH"]}]}`：外层仅 events，事件对象仅 event/tickers，事件正文非空，tickers 为数组。拒绝重复 JSON 字段、非标准数值及非法文本。

`events=[]` 正常通过且不展开；即使账号没有代币映射也不报错。`tickers=[]` 则从 `user_name_to_tickers` 查原帖用户名，使用配置的非空代币列表；没有映射报错。非空代币数组中出现空字符串、null 或非字符串同样报错，不当作空数组处理。

`configs/event_processing_config.yaml` 已按用户提供的 TradeCoins 50 名单（生成于 2026-09-18）填入 50 组映射：原 `screen_name` 对应 `user_name`，原 `ticker` 转为单元素列表。沿用用户名完全一致的匹配规则，区分大小写，不去掉 `@` 或空白，也不根据迁移备注匹配旧账号。例如 `BitcoinMagazine` 的空 tickers 补为 `["BTC"]`；`bitcoinmagazine` 或 `@BitcoinMagazine` 均不命中这条映射。迁移备注只记录原名单说明，实际源帖的用户名仍待核对。

这里“空代币数组”和“缺少字段”分两步处理：

1. 第一轮允许 `tickers: []`，因此该帖可以正常保存为 `status="1"`。如果 tickers 字段缺少、为 null 或不是合法数组，则第一轮业务校验失败，按该帖的请求预算重试；最终仍无效时保存第一轮失败状态。已经成功的旧帖不会自动重跑，但导入时仍检查其 JSON。
2. 导入接收本次全部待导入成功帖，先完整展开到内存，再访问和写入事件去重分析表。任一事件 tickers 为空且原帖用户名没有映射，就抛出包含帖子 ID 和用户名的错误，停止本次整批导入；不会只跳过该事件，也不会先保存其他合法事件。
3. 第一轮已保存结果和成功状态保留，已有事件表数据不修改；本次不新增任何事件行，也不为无代币事件写 round2_status="-1"。补齐账号映射后重跑同范围 main.py，使用已保存的第一轮回答补导，不重新请求这些成功帖的 AI。未解决代币问题时直接重跑仍会停止。

例如同次导入有帖子 A：`{"events":[{"event":"事实A","tickers":["BTC"]}]}`，以及帖子 B：`{"events":[{"event":"事实B","tickers":[]}]}`。B 的原 user_name 为 `account_b` 且没有映射时，A、B 本次都不会新增到事件表。补入 `account_b: ["ETH"]` 后重跑，追加 A→BTC、B→ETH，并按已有索引去重。若 B 为 `{"events":[]}`，则 B 不生成行，也不会阻止 A 导入。

代币去掉首尾空白、转为大写，并在同一事件内去重；暂不合并 LEND/AAVE 等别名。已有 tickers 时不额外追加账号映射。原事件顺序不变，记录 ID 使用零起始事件序号。date 原值和精度保持不变，原帖整数 ID 仅在新表中转成字符串。

字符串 date 必须含完整时分秒，也接受时间戳对象；只有 `2018-01-01` 的文本不能用于新流程。原帖 ID 须为全表唯一的非空字符串或整数，不能含冒号。

例如一个事件的代币为 `[" eth ", "ETH", "LEND"]`，只产生 ETH、LEND 两条记录。另一个事件 tickers 为空且账号配置为 `["BTC"]`，只产生 BTC；原round1事件提取 JSON 不修改。

### 历史回答中未转义引号的批量处理

2026-10-16 用户确认并实施：已有回答在导入时可按以下规则修复正文引号。无需逐条改库或重新请求 AI，执行原有 `python -X utf8 -m entrypoints.import_events` 即可。

1. 自动导入与独立导入共用处理：先按现有规则解析第一轮回答，合法回答直接使用。只有 JSON 语法解析失败时，才尝试处理 `event` 正文中未转义的英文双引号。
2. 修复仅允许在这些正文引号前增加反斜杠；不删除或替换已有字符，不补逗号、括号、字段、代币或缺失的正文。支持多个事件、两种字段顺序，保留已有合法转义。引号后出现逗号、冒号、容器符号或疑似下一字段时，按正文边界检查后续结构；结构不合法则停止，不回退并把字段当正文重新解释。处理后再次执行原有 JSON 和 events/event/tickers 结构校验。
3. 修复只在本次导入内存中进行，不写回第一轮表，不更改其状态和原始回答，不调用 AI。两种导入入口使用相同规则，保证再次导入时获得相同的固定输入。
4. 批量检查本次范围内的回答，日志记录修复的帖子 ID，并集中记录无法修复的帖子 ID 与原因；不输出完整回答。存在无法修复的回答时，本批在建表或写入前停止，不跳过坏记录，也不先导入其他记录。全部通过后沿用现有建表、去重与续建流程。
5. 第一轮新请求的输出继续严格校验和重试，不启用这项历史兼容处理。

例如 `{"events":[{"event":"机构表态：加密货币"正常化"","tickers":[]}]}` 可在内存中修复为 `{"events":[{"event":"机构表态：加密货币\"正常化\"","tickers":[]}]}`，得到的事件正文保留 `机构表态：加密货币"正常化"`。正文截断、缺少 tickers、重复字段或事件边界不明确的回答不自动补全。

保守停止的例子：`{"events":[{"event":"引述"a", "b"后文","tickers":[]}]}` 中，引号后的逗号也可能是字段分隔符，程序不会猜测它属于正文。这类记录与其他无法修复记录一起报错，本批不写入。日志逐条提供帖子 ID 和原因，最终异常保留首条原因和本批错误总数；校验完成时汇总帖子数、引号修复数和不合法数。

## 3. 初始化与续建

三种数据写入接口正常返回即本次整批全部写入，抛异常即本次完全未写入。失败不读回、不做部分确认；所有更新只由一个程序协调。

独立入口的 auto 先读取目标：仅异常类名为 DataNotFound 或文本含独立标识 DataNotFound 时 register/write，其他读取错误直接传播；已有表走严格 resume 检查。独立入口可配置 auto/create/resume。主入口的内存导入分流见下文，不再调用独立入口读取源表。

create 用于尚未注册的新目标：生成完整初始批次后 register 一次，再 write。注册失败停止；写入异常时调用共用 write_with_retry 重试同一批，不再次注册。空事件仍写合法空表结构。

resume 只追加新记录，不补列、不补单元格、不修改旧行：

1. 启动读取旧表，检查结构、索引唯一性和本范围固定输入。缺列、输入冲突、本范围多出来源以外记录时，在写入前报错。空字符串按原表结构处理，不能与缺失值混同。
2. 找出本范围展开记录中目标不存在的复合索引。新旧记录之间的 record_id 必须全表唯一，日期索引类型、时区和精度必须一致；范围外旧记录也参与唯一性检查。已有状态、关联、分析结果、错误及范围外数据均保持原值。
3. 完整旧表没有新记录就返回新增数 0，不调用任何写入。否则通过 update_by_index 提交完整初始列和新索引；不能夹带已有索引。auto 遇到已注册但无行无列的目标、且本批也没有事件行时，只用 write 补齐合法空表结构，不再次注册。正常返回后才返回新增数。

仅已注册、完全没有任何行和列的空目标按初始空表看待，支持 create 写入失败后改为 resume；非空缺列旧表及仅有部分列的空表仍报错。这是首次写入尚未成功的目标，不会补写任何旧行。

create、resume 以及 auto 选择的相应写入流程均沿用默认最多 3 次保存尝试，包含首次；异常后有剩余预算则等待 1 秒，重试同一完整批次。预算耗尽抛 BatchPersistenceError，保留阶段及原异常并停止，不做异常读回。再次运行 auto 或 resume 会重新读取实际状态，已追加成功的索引不会再次提交。

例如旧表已有 A、B，本次展开 B、C、D，只追加 C、D。首次异常表示 C、D 都没写入，下一次仍提交 C、D；再次运行时新增数为 0。若 B 缺少必需列或固定输入比较失败，直接报错，不修复 B，也不先追加 C、D。统计总数为旧行数加本次新增数，无需拼接完整目标表。

展开和初始化不加载 AI 配置、不调用 AI。round1事件提取 initialize_tasks 仍为原单次初始化入口，不新增自动重试。

2026-10-15 用户最新要求已实施：main.py round1事件提取正常结束后，使用内存中的成功帖子自动导入，不再手动执行导入或重读round1事件提取。事件展开、映射与写入由事件模块负责；是否读取事件去重分析表核对索引，取决于本次读取 round1帖子事件提取表时是否有帖子已经 status="1"，具体步骤见下文。独立入口继续保留严格核查能力。round2事件去重归组与round3事件影响分析按已有任务处理，不重新展开round1事件提取；不新增表、状态字段或恢复文件，不自动启动后续两轮。

main.py 正常返回round1事件提取统计后才开始自动导入，普通帖子失败不阻止其他成功帖导入。若本范围没有任何成功帖，则跳过导入，不读取、注册或写入事件去重分析表。round1事件提取异常或用户中断时直接退出，不开始导入；此前已保存成功的帖子，下次重新运行同一范围时会跳过 AI，再参加自动补导。导入失败也保留round1事件提取结果，main.py 抛出原异常并退出；再次运行同一范围会自动补导。main.py 的返回值仍为round1事件提取 ExtractionSummary，新增事件数记日志。

round1事件提取读取每个分段时，先记住哪些帖子已经 status="1"。本段结果全部保存并通过月末检查后，可选 on_successful_posts 回调交出两份副本：new_posts 是本次调用 AI 后成功保存的帖子；previous_posts 是本段读取时已经 status="1"、本次跳过 AI 的帖子。两份都只含原 date/id 索引及 text、user_name、status、ai_response_content。main.py 收集这些副本，round1事件提取正常结束后才调用 import_event_records_from_posts，不再次读取round1事件提取。默认不传回调的旧 run_extraction 调用方式仍可使用。主入口只保留这些必要数据，内存随本次成功数量增长，不持有失败帖或无关 AI 字段。

### 主入口的正常追加与补导

如果本次读取round1帖子事件提取表时，没有任何帖子已经 status="1"，round1事件提取正常结束后按以下步骤直接追加：

1. 从本次成功保存的内存数据中解析 ai_response_content.events，校验并生成任务的完整初始字段。
2. 调用 read_meta(result_path) 确认事件去重分析表是否存在，不 read 已有任务，也不扫描旧索引。
3. 明确 DataNotFound 时 register 一次、write 完整初始表；已有目标直接 update_by_index 追加本批。已有目标且本批全部空事件时不写入；首次目标则仍创建完整空结构。

如果本次读取round1帖子事件提取表时，有帖子已经 status="1"，整个处理顺序如下：

1. 读取时已是 status="1" 的帖子不再调用 AI，保留该行已保存的 ai_response_content；其他帖子按原规则处理，成功后保存。
2. round1事件提取正常结束后，解析这些内存回答中的 events，包括读取时已成功和本次新成功的帖子，生成带原 date 和稳定 record_id 的任务，不重新读取round1帖子事件提取表。
3. 读取一次整张事件去重分析表，检查索引结构和唯一性，按 (date, record_id) 核对。已存在的任务跳过，保留其round2事件去重归组与round3事件影响分析状态和结果；不存在的任务才追加完整初始字段，不比较已有行的业务字段。
4. record_id 已在其他日期出现或新增日期索引类型不一致时，在写入前停止。目标明确缺表则 register/write 本次全部候选；已注册但无行无列的目标可继续追加，全部空事件则只 write 补齐结构，不重复注册。

例如，本次配置处理 2026 年 1 月 1 日至 1 月 31 日发布的帖子：

| 帖子 | 本次读取前的情况 | round1事件提取如何处理 | 自动导入如何处理 |
| --- | --- | --- | --- |
| A | round1事件提取 status="1"，上次事件任务写入失败 | 不再调用 AI，使用已保存的 ai_response_content | 核对后追加缺少的任务 |
| B | round1事件提取 status="1"，任务已导入，round2事件去重归组也已完成 | 不再调用 AI，使用已保存的 ai_response_content | 索引已存在，跳过，保留round2事件去重归组结果 |
| C | round1事件提取 status="-1"，上次调用失败 | 重新调用 AI，成功后保存结果 | 使用本次成功保存的 ai_response_content，核对后追加缺少的任务；本次仍失败则不导入 |

A、B 读取时已经成功，因此本次只读取一次事件去重分析表，A、B、C 生成的任务一起核对索引。读取整张目标表不会扩大准备导入的帖子范围，2 月发布的帖子不参与本次处理。这里的“再次运行”指重新执行 main.py；“1 月 1 日至 1 月 31 日”指帖子发布时间范围，不是程序运行时段。不设置日期限制时，round1事件提取按全表处理。

如果任务其实已导入、进程随后退出，再次运行也会跳过已有索引。round1事件提取与事件去重分析表是两次独立写入，不共同回滚。已有任务若重新提交完整初始值，可能将结果置空、状态改回 0，所以核对后只能提交缺少的索引。

无论是否核对旧任务，都按相同整批数据重试保存，失败后不读回、不追加未确认结果。其他元数据或数据读取错误直接传播。主入口只记录本次新增事件数，不为统计全表总数再读旧表；独立初始化的 InitializationSummary 仍沿用原统计口径。正常直接追加依赖 ID 稳定唯一、成功状态不人为回退及单程序写入；人工修改历史输入、映射或状态后的核查与重算仍使用独立入口。

## 4. round2事件去重归组前置检查与恢复

第二轮使用公共时间规则计算历史补读范围和窗口资格，并通过公共历史读取函数检查索引、列和返回日期。第三轮按配置范围读取本次任务，仅在处理 repeat 时补读必要历史响应。月份与月末窗口边界的处理见 [实现问题](../IMPLEMENTATION_ISSUES.md)。

先按配置日期读取本次事件任务，只检查表结构、索引和日期范围，按状态选择已有任务。普通列原值使用，不校验 NaN、类型、空字符串、状态枚举、历史结果或摘要格式。不读取、解析或重新展开round1事件提取事件结果。范围内没有待处理任务时不读前史或表尾元数据。

有待处理任务时，按配置月数（默认 3）计算所有待处理时刻的窗口下界，取其中最早日期，按日期读取该下界至处理起点前一天的历史，与当前任务组成内存工作表；不重复读取当前任务已有的日期。日期接口按整日读取，精确时刻边界在内存判断。元数据提供表尾日期，处理范围之后若仍有记录，只按日期读取 asset、round2_status 两列检查补录冲突，不读取这些记录的事件、向量或回答，也不加入候选。

范围内全部完成或没有可认领任务时直接返回，不读取全表摘要。第二轮始终不读取原帖正文或第一轮表；当前 event 是完整且固定的事实输入，AI 只接收 current.published_at、current.event 及各候选组的 candidate_id、history 事件列表，每条历史包含 published_at、event。每条 published_at 是对应 df 的 date 索引值的字符串，保留完整精度和时区。candidate_id 为本次请求内的 E1、E2 等短编号；真实 event_id、记录定位和代币留在程序内部用于检索和保存。

round2事件去重归组按 batch_size 分批将当前范围 9/-1 恢复为 0，保留错误、旧结果和其他阶段字段。恢复不检查历史 repeat 的空字段或摘要，不补成功状态。窗口内已有起点仍要求阶段已完成、同币且严格早于当前披露；缺失或窗口外起点不再回查或核实，组输入须标记截断。

按币找出本范围最早未完成时刻 T，并取该币全部待处理任务的最早窗口下界 B，要求 `[B, T)` 内已导入的同币前史完成关联。月末截断可能使后续任务的下界时分秒更早，因此 B 不只取最早任务的下界。窗口内未完成则停止并提示手动补跑，窗口外旧任务不阻塞。历史检查不展开第一轮帖子或检查导入覆盖。候选检索按每条当前披露 t 使用 `[t-配置月数, t)` 的已完成同币记录，不自动补跑范围外任务。

若已有较晚的同币关联，而较早记录又变成待处理，停止提示核查补录或回退范围；本版不自动重算已经完成的下游结果。相同发布时间的部分续跑可以继续，因为同一时刻的记录互不进入候选历史。

例如 ETH 的 1 月 10 日、1 月 20 日记录已完成round2事件去重归组，又补入一条 1 月 15 日记录：这条披露可能改变 1 月 20 日当时应看到的历史，进而影响其关联结果。因此启动检查停止，让用户核查后决定重算范围；程序不会自动删除或重做 1 月 20 日之后的结果及 round3事件影响分析结果。

具体识别使用已有 date、asset、record_id 和 round2_status，不增加插入时间字段。处理范围内的更晚记录直接检查；范围之后的记录只读两列状态数据。若同币存在更晚且 round2_status=1 的记录，则报“疑似历史补录或历史状态缺口”，列出待处理与更晚已完成的时间、ID；相同发布时间不算更晚。3 个月限制向过去回看的前史，不取消这项更晚完成检查。

前史校验在已读取的 DataFrame 上建立 `record_id → 原行位置` 字典，按币分组，只保存位置及所属数据段的引用，不按币复制完整表。每个币只检查自己的窗口内前史及更晚完成记录，窗口内已知起点按 ID 定位。窗口外或无法读取的起点不能验证其是否存在、同币或已完成；这是严格截断后的能力边界。索引仅在内存使用，不创建数据库索引。

这不能区分新补录与人为把旧记录改回未完成；两者都会形成历史缺口。round1事件提取新增记录尚未导入时，round2事件去重归组只处理当前已有任务，不报告覆盖缺失；导入新记录后再做时间检查。范围内全部已经完成时直接返回；源数据被修改、删除或已有结果被人为改写，不由这一时间检查证明或追踪。

正常失败续跑不受影响：1 月 10 日完成，1 月 15 日失败，1 月 20 日尚未开始，重启会先补跑 1 月 15 日，再处理 1 月 20 日。相同时间部分完成的续跑也要求没有更晚的同币关联已经完成；若后来补录的同刻记录位于已完成历史中间，仍会触发上述检查。

全部关联已经完成时，核对后直接返回，无需接入检索函数或 AI。还有未完成任务时，检索入口、AI 配置和非空提示词全部就绪才开始认领。

## 5. 历史检索接口和时间边界

2026-10-16 用户确认并实施 bge-m3 纯向量检索：只编码各条 event，不使用关键词或排名融合。历史 update 的完整 event 都参与评分，new_information 保留在内部组历史中，第三轮只使用本条记录的 new_information，不重复拼入向量文本，也不再发送给第二轮 AI。向量保存在事件去重分析表 embedding 列；实现和阈值例子见 [表内向量方案](../plans/EMBEDDING_TABLE_STORAGE_PLAN.md)。

读取已完成round2事件去重归组的事件去重分析表行，在内存建立按币和事件组组织的索引。round3事件影响分析尚未完成或失败不影响这些行的历史资格。程序没有把全部历史直接交给 AI。

批量载入历史时，各币的候选记录一次按完整发布时间、record_id 排序；单条关联保存成功后加入有序列表。查询通过二分定位 `[当前披露时间-3个月, 当前披露时间)`，只复制该区间内的记录，不逐条遍历窗口外历史或重新排序。相同时间按 record_id 排序，返回副本；同刻及未来记录均排除。第二轮组输入同样只提供该窗口内历史。

例如 T 为 2025-10-01 12:00:00，按默认 3 个月计算，下界为 2025-07-01 12:00:00；下界同刻的已完成同币披露参与评分，早 1 纳秒不参与，T 同刻及未来披露也不参与。2024-05-31 回推 3 个月取 2024-02-29，2025-05-31 回推 3 个月取 2025-02-28，保留时区、时分秒和纳秒。组起点若在 2010 年，不回查它；窗口内的近期 update/repeat 仍可召回该组。内部组历史保留截断标记，第二轮 AI 只接收事件文本和候选短编号。向量评分继续使用现有临时矩阵、float64、组内最高分、阈值和最多 10 组。

本次处理跨多年时，每条披露分别按自己的发布时间回看 3 个月，不能统一使用最后一条披露或程序运行日的下界。窗口内披露越多，向量准备、相似度计算及 AI 历史输入的开销也越大；时间截断不代表有固定字节数或输入长度上限。

默认通过 `embedding_config_path: "embedding_config.yaml"` 使用内置向量检索。也可设置 `retriever: "模块:函数"`，或在应用调用 run_relation 时传入 retriever 函数；选择优先级为应用注入、自定义函数、内置向量。业务接口仍为 `retrieve(current, searchable) -> RetrievalSelection`。

独立 Embedding 配置的 base_url 后追加 `/embeddings`，模型默认 bge-m3，每批默认 8 条。密钥从进程环境或该配置同目录 `.env` 中的 EMBEDDING_API_KEY 读取，进程环境优先。缺少地址、密钥或合法参数时不认领新任务。similarity_threshold 默认 0.50，允许 [-1, 1] 内有限数值；不再有本地缓存路径。

第二轮按配置日期读取任务及所需历史，按币和时间队列在内存中推进，不逐条查数据库。开始认领前，准备本范围全部待处理披露，以及同币且至少能进入一个待处理时点前 3 个日历月窗口的已完成历史披露的 embedding；窗口为 t-3个月 ≤ 历史时间 < t。该列用 JSON 字符串保存 model、model_version、config_hash 和模型已归一化的 vector；标识匹配才复用，空字符串或标识变化时重新生成，格式损坏时停止。同文本在内存去重，每条对应披露仍保存自己的向量。响应须数量一致、index 完整唯一、维度一致、数值有限且非零，范数与 1 的绝对误差不超过 1e-5。程序保留模型返回数值，不重新归一化或转成 float32，内存用 float64 数组直接计算内积；编码规则标识为 event-only-service-unit-f64-v3。整批通过后通过共用存储重试仅更新 embedding 列，保存成功才进入内存评分；写入重试不重新调用 Embedding。准备结束或异常均关闭 HTTP 客户端，不使用 SQLite。提前编码未来披露不改变其历史资格；无历史的待处理行也保存向量供后续时点使用。窗口外起点不读取、不生成向量，缺起点的候选按前述截断规则提供。

对当前时点合格历史逐条计算余弦相似度，按 event_id 取组内最高分，只保留分数大于等于 similarity_threshold 的组，再按组分数降序取最多 10 组，同分按 event_id 升序。不能先取 10 条披露再去重，也不把重复披露分数相加。默认阈值下，0.49 不提交、0.50 提交；无历史或所有组都低于阈值时直接 new，进入round3事件影响分析。阈值是试运行参数，不表示同一事件的概率。

每批 Embedding 默认最多尝试 3 次，包含首次；网络传输故障、5xx 和无效响应共用预算。复用 common.network 的异常分类、指数随机退避和 Retry-After 解析，本地退避上界从 1 秒翻倍，最高 30 秒，可配置；5xx 的合法 Retry-After 与退避取较长等待。429、其他非成功 HTTP 或预算耗尽停止本轮，不伪造空候选；该预算不占关联 AI 请求次数。表内损坏、程序异常及存储失败不作为接口输出重试。config_hash 只包含服务、模型、人工版本及编码规则，不含实际 event；同一配置各行一致。event 沿用固定输入约定，人工改动时清空对应 embedding 并确定下游重算范围；更换同名模型权重时要更改 model_version。表内已成功保存的批次在重启后复用，Embedding 或存储错误不按低分处理。

- 检索接口的 current 包含 record_id、原发布时间 date、asset、event 和 source_post_id，不含 source_text；第二轮 AI 仅接收 published_at 和 event，published_at 取内部 date 值，其余定位字段供程序使用。
- searchable 是同代币、当前披露时间回推配置月数至当前时刻之前的已完成披露副本，默认 3 个月，包含 event_id、event_relation 和 update 的 new_information。下界包含，上界排除；返回顺序为时间、record_id。
- 返回的 event_ids 必须是最多 10 个不同事件组 ID 的元组，顺序表示评分函数选出的相关性顺序，且都来自本次 searchable。
- 通用接口的 auto_new 默认为 False。内置评分器在前史检查通过且 searchable 为空，或所有组分数都严格低于阈值时，返回空 event_ids、auto_new=True 和带规则标识的非空 reason；阈值放行同时在原因中记录最高分和阈值。空窗口或低分不证明全网没有相关事件。

没有内置配置、自定义配置或应用注入时明确停止，不生成虚假的空候选。评分函数返回错误或自身发生异常同样停止，不能转为自动判新，也不消耗 AI 输出重试预算。

选出组 ID 后，内部仍只组织本次 3 个月窗口内的组事实。窗口内有唯一合法 new 起点时，first_disclosure 提供该起点、history_trimmed=false；没有窗口内起点时，保留组 ID、first_disclosure=null、history_trimmed=true，并额外提供 first_available_disclosure，表示窗口内最早的原始披露，不把它改成 new。timeline 提供窗口内全部 update，repeat_count/disclosure_count 只统计窗口内记录，不加入同刻及未来披露。这些内部字段仅供第二轮程序组织候选，不原样发送给第二轮 AI；第三轮不使用组历史。

例如 2010 年的组在 2024-12-01 只有一条 repeat，2025-01-01 召回时不读取 2010 年起点；内部 first_available_disclosure 提供 2024 年 repeat 的 event 事实。发送第二轮 AI 时，该候选只包含 candidate_id 和 history，history 包含这条 repeat 的 date 索引值和完整 event 文本，不发送真实 event_id、截断标记或披露次数。

每次关联输入、候选和评分不写业务表；生成的向量和模型/配置标识保存在 embedding 列。续跑复用有效向量，重新计算未完成记录的候选，已完成关联不重做。阈值变化不影响向量标识，但只作用于后续待处理记录；不会自动重算历史。原轮次 config_hash 仍不覆盖 Embedding 参数、阈值或 history_lookback_months；需要在一次研究处理中保持检索规则一致，若更改已处理历史的口径，重算范围另行确定。

## 6. round2事件去重归组调度和输出

按代币建立时间队列，不同代币可并发。同币前一时刻的关联全部保存确认后，才启动下一时刻；完全相同的发布时间使用同一份此前历史，可以共同并发。不能靠 ID 排序把同刻披露当作彼此历史。

先共同保存 `round2_status="9"` 和 `round2_config_hash`，再执行该条检索或提交 AI。build_relation_input 按已选候选顺序分配 E1、E2、……、E10，返回精简后的 JSON 文本及“candidate_id → 真实 event_id”映射。文本只包含当前 published_at、event、候选短编号和历史 published_at、event 对象列表，通过已有 task.text 模板构造请求，不为业务字段增加模板变量。固定输入结构如下：

```json
{
  "current": {
    "published_at": "2025-01-03 12:00:00",
    "event": "ABC Protocol 已开始执行1000万美元代币回购计划。"
  },
  "candidates": [
    {
      "candidate_id": "E1",
      "history": [
        {
          "published_at": "2025-01-01 12:00:00",
          "event": "ABC Protocol 提议投入1000万美元回购代币，尚待治理投票。"
        },
        {
          "published_at": "2025-01-02 12:00:00",
          "event": "ABC Protocol 的1000万美元代币回购提案已通过治理投票。"
        }
      ]
    }
  ]
}
```

每组 history 保留窗口内起点及全部 update 的 published_at 和完整 event，由程序按发布时间和 record_id 排序。缺少起点时，先提供 first_available_disclosure 的 published_at 和 event（published_at 取内部 date 值），再接全部 update；同一条披露同时出现在 first_available_disclosure 和 timeline 时只发送一次，不按文本相同去重。普通 repeat 沿用既有规则，不重复加入历史正文。当前事件及每条历史的 published_at 都直接取对应 df 的 date 索引值并转为字符串，不转换时区或截断精度；这是披露时间，不必等同事件实际发生时间。事件文本中原有的日期、数字、版本和限制条件原样保留，不补写或删改。

第二轮 AI 不接收真实 event_id、资产、record_id、source_post_id、历史 event_relation、new_information、披露次数或 history_trimmed；时间窗口、同币筛选和同刻排除由程序负责。提示词只按两个步骤判断：先比较所有候选，确认均不是同一具体事项才选 new；唯一匹配后比较全部历史，没有新增事实选 repeat，有新增事实选 update 并填写新增信息。任一步无法可靠判断或无法唯一匹配时选 uncertain。正式 system 提示词保存在 configs/round2_ai_config.yaml，关系选择和新增信息填写融入这两个步骤，保留 `# ***标题***`、固定输出结构和四种 JSON 示例，user 继续为 `{{task.text}}`。

update 的 new_information 是供第三轮独立理解本次变化的说明，不能只写“获批”“金额提高”等短摘要。应交代事项主体及对象、此前已知状态或数值、本次新增或修正的内容、变化后的状态和直接相关条件；多项新增事实分别写清，不为缩短文字而遗漏。仅带入理解本次变化必需的旧事实，不复制完整历史，也不把旧事实重新当作本次新增。

此前状态只能来自唯一匹配组的 history，应结合全部历史找到当前披露以前最近已知且未被后续事实更正的状态，不能只与最初提案比较；本次新事实只能来自 current.event。不能借用其他候选组或外部知识，不把批准等同于执行，不把计划额度等同于实际资金流，也不在第二轮判断经济影响。

金额、数量、比例、期间和限定条件须保留可比口径。同口径且能直接比较时写清旧值、新值及变化量；不能将累计总值当成本次新增量，也不能混用预算与实际执行、不同期间或不同币种的数据。历史已知的重要条件在本次没有交代是否满足时，明确写本次未披露，不能默认条件解除或已满足。

历史缺少旧状态时，仅在影响理解变化的地方注明“所给历史未披露此前状态/数值”，不补造旧值；当前未披露执行情况，应写“本次未披露是否执行”，不能写“尚未执行”。已经能够确认同一事项且有新增事实时，不因无法补齐旧状态就改为 uncertain；关系或是否新增本身无法确定时才沿用 uncertain。

例如历史为“ABC 提议1000万美元回购，尚待治理投票”，当前为“该提案投票通过”，新增信息应写“ABC 的1000万美元回购计划此前处于提案、尚待治理投票阶段；本次披露投票已通过，状态由已提议转为已获批准；本次未披露是否开始回购”。不能只写“投票通过”，也不能写成已经产生1000万美元回购资金流。若同一计划、同一统计口径的累计回购由400万美元增至600万美元，应区分累计600万美元与新增200万美元，不能将本次新增写成600万美元。

输出仍为三个字段，new_information 仍是字符串，不新增旧状态、现状态等数据库列。程序继续只校验字段、空值和 update 的非空文本，不能据此保证事实准确或前后对照完整；真实输出质量需用人工标注样本检验。新提示词只用于后续任务，已完成的短摘要不自动补写或重算，配置摘要冲突仍按原规则停止。

round2事件去重归组 AI 正文须恰好包含 event_relation、matched_candidate_id、new_information：

| 关系 | matched_candidate_id | new_information | 保存行为 |
| --- | --- | --- | --- |
| new | null | null | 建新组，event_id=自己的 record_id。 |
| uncertain | null | null | 合法输出转为 new，原始关系记日志。 |
| update | 本次候选短编号 | 非空字符串 | 映射回真实组 ID 后继承，保存新增事实。 |
| repeat | 本次候选短编号 | null | 映射回真实组 ID 后继承，第二轮不写第三轮状态，等待第三轮复制历史响应。 |

候选已经限定为同资产、有效时间范围的组。validate_relation_output 校验短编号属于当前请求后，转换为内部 matched_event_id 真实 ID，交给原保存流程；返回真实长 ID、未知短编号、旧字段 matched_event_id 或多个匹配都属于无效 AI 输出，使用原请求预算重试，不猜测或自动纠错。

编号和映射在首次提交本任务前各生成一次，同一个 RequestJob 的网络、5xx 和无效输出重试复用同一输入及映射，不重新检索或编号。不同任务的 E1 可以指向不同组，映射由各自的校验回调独立持有，并发不共享。重启未完成任务时仍重新检索并建立本次运行的映射；不新增映射表或持久状态。

例如本次映射为 E1 → 10001:0:ABC，历史披露该回购计划已获批准，当前首次披露开始执行，AI 可输出 `{"event_relation":"update","matched_candidate_id":"E1","new_information":"ABC 回购计划此前已获批准；本次披露开始执行，状态由已获批准推进至开始回购。本次未披露已执行金额。"}`，程序保存 event_id="10001:0:ABC"。round2_ai_response 中的 AI 原始正文仍保留 matched_candidate_id="E1"，不改写成真实 ID；事件表列及真实 event_id 的含义不变。

关联字段、round2_ai_response、round2事件去重归组完成状态和空错误共同保存；new/update 的round3事件影响分析状态为 `0`；repeat 不写第三轮字段，初始状态仍为 `0`，等待第三轮复制有效响应。每条关联立即保存确认，随后才更新同币历史，不等待攒批。AI 正文保留原始 uncertain，业务关系仍按 new 保存；自动判新不生成回答，round2_ai_response 为空。

普通单条最终失败时清空本条关联字段，保存round2事件去重归组 `-1`、错误和最后一次可安全提取的回答及调用信息，暂停该币后续关联。其他代币继续，尚未开始的行保持 `0`。停止型接口错误仍停止整轮。

## 7. round3事件影响分析检查、调度和保存

第三轮对 new/update 分析本次完整事件的代币影响，对 repeat 复制同币同组严格此前最近一条有效第三轮响应。按配置日期读取事件任务，仅有待处理 repeat 时补读必要历史响应列与表元数据；不读取原帖、不解析或发送向量、不重做第二轮关联或第一轮导入。

repeat 继承的有效来源必须是同 asset、同 event_id、round2_status 和 round3_status 均为 `1` 的记录，披露时间严格早于当前记录；外层回答 JSON 及 ai_response_content 的五字段正文须通过校验。按完整披露时间取最近有效记录，较近但无效的响应会跳过；同刻多条有效来源按 record_id 文本排序取最后一条，已成功复制的 repeat 也可作为来源。同刻及未来记录始终排除。

仅有待处理 repeat 时，先从处理起点之前按月从近到远读取 asset、event_id、round2_status、round3_status、round3_ai_response、round3_config_hash 六列；所有目标组找到有效来源后停止，最多回看到表起点，不受第二轮 3 个月检索窗口限制。内存每组只保留最近有效响应。本范围每个月先保存 new/update 的全部已完成 AI 结果，再按披露时间处理 repeat，同刻全部处理后才推进来源，随后进入下月。仅 repeat 的运行无需加载 AI 配置或启动网络线程。

repeat 成功时原样复制来源 round3_ai_response 与 round3_config_hash，连同 round3_status=`1`、空错误一起保存；不改第二轮字段，不刷新来源 JSON 中的 usage、response_created、attempts 或 created，也不增加本轮 HTTP 请求数。找不到有效来源时保存状态 `-1`、空响应和明确错误，可在来源补齐后重跑；历史读取或存储失败按原规则停止。旧版已标第三轮完成但回答为空的 repeat 不自动回填，需将待回填记录的第三轮状态重置为 `0` 后再运行。

start_time/end_time 必须同时配置，起止日全天均包含，按自然月分段。启动时先检查整个处理范围：每条记录的 round2_status 必须为 `1`，event_relation 只能是 new/update/repeat；new 的 event_id 必须等于自身 record_id，update/repeat 必须引用非空且不同于自身的组 ID。只检查这些本条记录能确定的关系，不回查组起点的存在、资产或时间；这些关联已由第二轮完成。record_id 唯一性只检查本次处理范围，包括跨月重复，不扫描全表事件内容。

无任务或第三轮全部完成时直接返回，不加载 AI 配置或读取配置摘要。存在未完成任务时，整个范围检查通过后才逐月按 batch_size 将第三轮遗留的 `9/-1` 恢复为 `0`；保留旧回答 JSON 和错误，不根据残留回答补成功，不自动修复 repeat 的异常旧状态。恢复与失败不改第二轮状态。后月第二轮未完成或本条关联不合法时，前月也不会先恢复或认领。

模型请求仅选择待处理 new/update，先共同保存第三轮状态 `9` 和 round3_config_hash，再逐条构造 JSON 文本。输入必含 asset、event；new_information 仅在有内容时附带，均为顶层字段。以下为带新增信息的例子：

```json
{
  "asset": "BTC",
  "event": "某公司将比特币购买计划由1亿美元提高至1.5亿美元。",
  "new_information": "购买额度由1亿美元上调至1.5亿美元，增加5000万美元。"
}
```

asset 指定本次分析的代币；event 使用本条固定事件事实。新增信息为空时只发送 asset 和 event；有新增信息时附带第二轮保存的 new_information，辅助理解事件进展和新旧变化。始终分析当前完整 event，不将范围限制为新增部分。空字符串、null 或仅含空白的新增信息均省略该字段，不发送 null、空字符串或其他占位；非空文本原样保留。repeat 继续跳过 AI。请求不包含 current 包装、关联类型、日期、任何 ID、原帖或历史字段。

没有新增信息时，例如发送 `{"asset":"BTC","event":"某公司公布比特币购买计划。"}`。一条帖子同时影响 BTC 和 ETH 时，展开后的两条任务分别发送自己的 asset，不能合并成一次分析。event 和 new_information 中已有的主体、日期、状态、金额和限制条件原样保留；第三轮正式 system 提示词已配置于 configs/round3_ai_config.yaml，按角色、输入、经济影响、四维判断口径和输出要求组织。始终分析当前完整 event，new_information 仅辅助理解进展和新旧变化；允许通用经济原理，不补充未提供的事件或代币事实，不重新去重。方向、重要性、执行阶段、经济影响持续时间分别判断，信息不足不默认中性或中等重要性。具体取值及边界以该 YAML 为准，代码按以下规则严格校验新回答。

第三轮没有历史窗口、组起点或原帖可用性的前提；第二轮已完成且本条基本关系合法的 update，即使没有组历史或原帖，也可以分析。history_lookback_months 仅作用于第二轮。第三轮不建立 EventHistory；repeat 可以读取范围外已完成的历史响应，不扩展任务范围或补跑范围外 AI。保留首次认领前的全表 round3_config_hash 单列核对，跨月复用，读取失败、缺列或摘要冲突时停止；已完成结果不自动重算。

当前月任务全部保存确认后释放本月数据，再进入下一月；网络线程和客户端跨月复用。共用执行模块继续控制并发数、答复缓冲、定时保存和停止收尾。收取完成消息后释放网络名额，保存和内存同步正常返回后才清空缓冲。最终成功、失败按结束状态汇总，不重复累加。

月末在候选队列和网络占用清空、剩余答复保存后，调用 execution.check_month_complete(processing)，仅检查本范围内的状态 `9`，不额外读表。仍有 `9` 则停止，普通失败 `-1` 允许进入下月；范围外的 `9` 不影响本次任务。保存失败只重试同一批写入，不重新请求 AI，不读取或执行下一月；预算耗尽停止，已完成的检查、恢复和保存不回滚。CLI 已写入但内存同步失败时停止，不重复写库。

round3事件影响分析每份新答复只在网络业务入口校验一次。默认 validate_impact_output 要求合法 UTF-8 JSON 对象，恰好包含五个非空字符串字段；拒绝重复键、Markdown 代码块、额外解释、缺少或多出的字段、null、非字符串及纯空白值。前四个字段严格匹配以下枚举，不自动去除字段值首尾空白或转换同义词：

| 字段 | 允许值 |
| --- | --- |
| direction | 利好、利空、中性、不确定 |
| materiality | 高、中、低、不确定 |
| execution_stage | 未开始、执行中、已完成、不确定 |
| persistence | 短期、中期、长期、不确定 |
| materiality_reason | 非空说明文本，原样保留；理由质量由样本评估 |

枚举错误包含具体字段和允许值，作为 OutputValidationError 使用原请求预算重试，不擅自修正或写为成功。信息不足时相关字段可独立填写“不确定”，不增加跨字段组合限制。注入 validator 继续负责完整新输出校验。结果转换不重复校验，提交保留列权限和字符串检查；普通读取不重新校验历史成功结果；用于 repeat 继承时须校验源正文，校验代码调整本身不改变配置摘要，也不自动重算已完成结果。

校验对象是接口 choices 中的 message.content 原始正文，校验后才封装为 round3_ai_response 保存。保存对象的 ai_response_content、usage、response_created、attempts、created 是外层调用信息；其中 ai_response_content 字符串内才是五个经济影响字段。字段不匹配错误列出缺少和多出的字段，JSON 根值不是对象时指出实际类型，便于识别额外包装或重复 JSON 编码。

答复按原记录键收取。达到 batch_size、result_buffer_size 或 flush_interval_seconds 即批量提交 round3_ai_response、round3事件影响分析状态及错误；结束时保存剩余答复。第三轮正文仍保留五字段结构及既有校验，数据库不再拆列；失败也保存最后一次可安全提取的原始正文和调用信息，必须结合状态使用。round3事件影响分析普通失败仅影响本条，继续处理其他记录。

两轮回答列均保存 ai_response_content、usage、response_created、attempts、created 五个 JSON 键，不保存推理文本。usage 只取最后一次响应，缺失为 null；attempts 包含实际发起的 AI 请求及重试，不含存储重试。response_created 为接口生成时间，created 为每次提交数据库前的当前北京时间，统一使用 YYYY-MM-DD HH:mm:ss。同批共用 created，存储重试只重新取 created，成功后同步实际提交值；不重新调用 AI，不累计 usage。恢复、认领、跳过完成记录不改回答时间。自动判新的第二轮回答列为空。repeat 的第三轮响应与配置摘要原样复制来源记录，usage、response_created、attempts、created 均保留源值，存储重试也不刷新；本条不产生 AI 请求，不能把复制的 usage/attempts 当作新增调用。取消且无最终结果不伪造回答。字段、失败和示例见 [表结构与回答保存口径](../data/EVENT_RESULT_TABLE.md#两轮-ai-回答的保存口径)。

## 8. 请求重试、错误和停止

共用round1事件提取网络请求、限速、响应外层解析和停止规则。round1事件提取也检查正文的 events/event/tickers，具体规则见 [round1事件提取关键规则第 6 节](KEY_RULES.md#6-什么结果算成功)，导入复用同一校验。三轮各任务的网络传输故障、可重试 5xx 和无效 AI 输出共用该任务的 run.max_attempts，包括第一次请求，默认 3 次；round2事件去重归组还检查非法匹配 ID。不同任务、不同轮次独立计数。正常 uncertain 无需重试。

只有明确的 OutputValidationError 视为可重试 AI 输出错误；程序异常或评分插件异常停止，以免重复调用掩盖问题。HTTP 429、401 和其他停止型状态、5xx 预算耗尽仍按round1事件提取停止整轮。具体网络异常分类见 [round1事件提取关键规则](KEY_RULES.md)。

共享 error_message 保存最近一次最终失败，最多 512 字符。当前阶段成功时清空；恢复到 `0`、认领为 `9`、跳过已完成任务时保留。round2事件去重归组续跑不会清除round3事件影响分析已失败记录的错误。

第二、三轮每个分段恢复成功后输出 INFO 日志，包含阶段名称、日期范围、遗留处理中 `9` 数量、历史失败 `-1` 数量、实际恢复数及恢复后的待处理数；恢复数为 0 也会显示。日志在本段状态写入全部确认后打印，恢复失败时不误报完成。第三轮无任务或全部完成时提前返回，不执行恢复；恢复只重置本阶段状态，不删除旧回答或错误。

第三轮入口在首次读库前打印“启动准备”，说明日期范围、分段数量及先检查第二轮再恢复第三轮的顺序；准备完成后汇总任务数、已有完成数、恢复后的待处理数、失败数和处理中数，之后才建立 AI 请求线程。范围为空或全部完成时也输出零待处理统计及无需调用 AI 的说明。该日志使用 event_processing_config.yaml 的 INFO 级别；已启动的进程需更新代码并重新启动后才能使用新日志。

“业务输出无效，准备重试”表示 HTTP 2xx 响应未通过接口响应解析或本轮正文校验，不仅指枚举不合法。重试及 2xx 最终失败日志附带具体原因，例如回答被截断、缺少字段或字段枚举不合法；不打印完整输入、提示词或回答。最终失败的 error_message 和 round3_ai_response 中最后一次正文可用于核对实际回答。HTTP 非 2xx 和传输异常继续沿用原日志及错误落库规则。

存储重试与请求预算分开。CLI 异常表示本次整批未写入，有预算则重试同一批；预算耗尽抛 BatchPersistenceError。若 CLI 已正常返回，随后内存同步发生普通异常，也抛 BatchPersistenceError，消息明确说明“CLI 已写入，但内存同步失败”，结果已经在数据库中，不再重试。两类错误都先关闭网络、保留答复并停止，收尾不继续保存。round1事件提取与round3事件影响分析通过 unsaved_results 保留原缓冲，round2事件去重归组保留最多一条已出队消息；其他消息留在 completed_results、unpublished_results 中。异常附带答复不代表它必定尚未落库，重启以数据库状态为准。

独立入口在加载本轮 AI 配置前进行状态恢复，使用默认存储重试；之后按该轮 AI 配置中的 run 存储参数保存。应用注入 ai_config 时从启动恢复起使用这份配置。

网络线程发现停止型错误时自行通知关闭，取消剩余请求并退出，不等待调用线程检查。调用线程统一在 finally 中调用 shutdown 一次并等待网络退出，再按错误类别保存已生成答复或直接保留答复停止。round2事件去重归组不维护额外 started 标记；round1事件提取与round3事件影响分析保留认领保存后、提交请求前的停止检查。

用户中断时也通知网络线程收尾，尽量保存已生成的最终答复；没有最终答复的认领行留 `9`，下次恢复。强制结束进程时，尚未保存的内存答复会丢失，需要重调 AI，也不能保证服务端撤销已收到的请求。无需增加持久化输入或候选表。

三个入口正常返回为退出码 0，异常为 1，用户中断为 130。单条普通失败在返回统计的 failed/blocked_assets 中体现，程序处理完可继续任务后仍正常返回；正常退出不代表所有行成功。

用户已确认现有 xdata 用法、只提交原索引和目标列的按列更新、字符串空值处理准确，并确认追加须使用 `update_by_index` 且只提交新索引。续建已按第 3 节实施。事件去重分析表布局及真实客户端联调事项见 [实现问题记录](../IMPLEMENTATION_ISSUES.md)。

## 9. 两轮 AI 配置摘要

事件去重分析表保存 round2_config_hash、round3_config_hash，初始均为空字符串。直接调用 common.config.ai_config_hash，与round1事件提取使用同一计算规则：原始提示词模板和 api.payload 按固定 JSON 编码计算 SHA-256；模型、temperature 等 payload 参数会改变摘要，并发、重试、URL 和认证不参与。摘要不是 AI 输入或检索候选快照。

读回摘要不校验类型、格式或历史成功行的非空要求，不填空、不补写。9/-1 只恢复为 0。范围内没有待认领任务时不调用摘要接口，也不要求加载当前 AI 配置。

确实需要认领时，统一调用 common.store.read_stage_hashes，通过 `cli.read(result_path, start_time='', end_time='', columns=[hash_column])` 读取本阶段全表摘要，含范围外记录；空日期表示全表，返回 DataFrame，直接取摘要列原值。第二轮的 hash_column 为 round2_config_hash，第三轮为 round3_config_hash；本次运行一次核对，摘要跨月复用。读取失败或返回缺列时停止，不回退整表读取。初始空字符串不参与，其他原值与当前摘要不等则配置冲突。round1事件提取也采用相同的全表策略。

认领只提交原索引及当前阶段的两列：状态=9、该轮 config_hash。round2事件去重归组自动判新同样绑定本阶段配置，因此所有完成关联都必须有 round2_config_hash；这不表示必然调用过 AI。round3事件影响分析 new/update 认领时保存摘要，repeat 不请求模型，保存时复制来源记录的 round3_config_hash。两轮可以分别使用不同提示词和模型。

成功、失败、恢复和结果保存不重写摘要。认领异常时，状态和摘要都完全未写入，按原两列整批重试，正常返回后才发送 AI 请求；不再读回或处理只写状态未写摘要的情况。

初始化 resume 不补摘要列或缺失单元格，缺必需列仍报错，旧单元格不做通用质检。新初始摘要为空，认领保存当前摘要；历史摘要缺失不自动补。恢复可能先于配置核对完成，冲突时保留已经恢复的状态，不回滚。
## 10. 共用 Store、认领与最终统计

PostTaskStore 和 EventRecordStore 继承 common.store.TableStore，分别保留业务输入与结果转换。选择端检查待处理状态，claim 不重复检查状态，只共同保存状态 9 和已核对摘要。三轮恢复均按 batch_size，round2事件去重归组结果仍即时写入，round1事件提取与round3事件影响分析按数量、时间和结束保存。

载入执行分段时记录已有完成基准，结束时从已同步的内存状态统一统计：新增完成为当前 1 减基准，失败为当前 -1，待处理为 0，处理中为 9。重复保存不重复计数，不额外读库；未知状态原样保留，可能不计入任何分类。公开返回字段名称不变，AI 请求次数由网络层单独提供。

共同存储重试只负责实际 CLI 写入、等待和预算耗尽；注册在循环外执行一次。数据库成功后由 Store 更新正在使用的快照，随后释放临时批次；完整建表和追加没有工作快照需要更新。round1事件提取手动一次性初始化脚本不改。完整边界与示例见 [共用实现方案](../history/STORE_REUSE_PLAN.md)。
