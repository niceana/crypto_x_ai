# round1事件提取关键处理规则

这里说明会影响处理范围、结果、调用费用和恢复方式的行为。运行方法见 [使用说明](../../README.md)，字段见 [round1帖子事件提取表](../data/TABLE_DESIGN.md)，具体代码通过下方链接定位。

2026-10-15 用户确认的 [存储精简方案](../history/STORAGE_SIMPLIFICATION_PLAN.md) 已实施：正常返回即整批写入，异常即未写入，保存失败整批重试、预算耗尽停止。本文正文描述当前行为；后面的接口修正、损坏数据恢复和旧测试场景作为历史记录保留。

2026-10-15 主入口新增自动衔接：main.py 启动前同时校验 configs/event_processing_config.yaml，复用一个 cli 运行round1事件提取，正常结束后自动导入实际处理范围内 status="1" 的帖子；普通失败帖子补跑成功后再导入。没有成功帖跳过导入，round1事件提取异常或中断不开始导入。导入失败不回滚已保存的round1事件提取结果；再次执行同一范围的 main.py，成功帖子跳过 AI，导入模块去重补齐任务。目标读取明确为 DataNotFound 时才 register/write，已有目标仅追加新索引。round2事件去重归组与round3事件影响分析仍分别启动，不增加round1事件提取字段。完整规则见 [事件导入](EVENT_RULES.md#3-初始化与续建)。

以下round1事件提取日期、分段、网络和保存规则继续适用于 run_extraction。可选 on_successful_posts(new_posts, previous_posts) 回调在本月结果全部保存、结束检查通过后交出副本：new_posts 是本次调用 AI 后成功保存的帖子；previous_posts 是本月读取round1帖子事件提取表时已经 status="1"、本次跳过 AI 的帖子。两份数据只含原 date/id 及 text、user_name、status、ai_response_content，原调用方式和返回统计兼容。

main.py 正常结束round1事件提取后，从这些内存数据的 ai_response_content.events 生成任务，不额外读取round1事件提取。如果本次读取时没有帖子已经 status="1"，只查目标元数据后直接追加；如果有，就读取一次整张事件去重分析表，将这些帖子和本次新成功帖子生成的任务一起按 (date, record_id) 核对，只追加缺少的任务，保留已有round2事件去重归组与round3事件影响分析状态和结果。准备导入的帖子仅限本次配置的帖子发布时间范围，不是程序启动到结束的时间；不设日期限制时按全表处理。整个主入口内存随成功数据量增长，不承诺只持有单月数据。

## 1. 建立初始任务

初始化完整读取现有源帖子，保留原 `date/id` 两层索引及字符串 `text`、`user_name`，建立 [round1帖子事件提取表](../data/TABLE_DESIGN.md) 规定的完整数据。初始状态为 `"0"`，配置标识和结果为空。空源也会建立结构合法的空表。

流程是读取源 → 校验并建立round1帖子事件提取表 → `cli.register(task_path, "timeseries", "")` 注册目标 → `cli.write(task_path, df)` 一次写入。源校验或建表失败不注册、不写入；注册失败不写入；整个初始化不自动重试。

初始化使用已知尚未创建的新目标，不读取或检查目标是否存在，不承诺避免覆盖。注册和写入是两次调用：注册正常返回、随后写入报错时，会留下已注册的目标，但这次失败写入没有保存数据。用户须核查目标状态，再选择新目标或按真实客户端规则处理原目标后重跑。仅清空数据不保证重复注册安全。

初始化不按处理日期过滤，不读取 AI 配置，也不调用 AI。以后新增帖子的完整任务由现有数据流程创建，程序不会从源表补建遗漏任务。

代码：[初始化接入](../../entrypoints/initialize_tasks.py)、[任务初始化](../../initialization/post_tasks.py)。

## 2. 处理哪些日期

`start_time/end_time` 同时设置时，使用 `YYYY-MM-DD` 字符串，包含起止日期全天；起点不得晚于终点，起止同日有效。两端均不设置时，只读取全表一次；只设置一端会报错。

例如 `2021-01-01` 至 `2021-12-31` 按 12 个自然月处理；一月读取 `2021-01-01` 至 `2021-01-31`，二月从 `2021-02-01` 开始。截止日期若写成 `2022-01-01`，还会处理这一天。

每月使用配置日期字符串读取；保存异常不额外读取round1帖子事件提取表。当前月请求结束且结果保存确认后，才读取下个月；空月或全是已成功任务的月份也会继续后续月份。起止不足整月时，使用实际指定日期。

日期依据原任务索引，原值、时区和精度保持不变。客户端必须返回范围内的记录，程序发现范围外数据会报错，不会自行扩大范围或删掉多读的记录。截止日下一天的零点只用于本地校验末日全天，不传给客户端。

日期字符串对应哪个日历时区、是否覆盖末日全天，仍需用真实客户端验证。只改变日期范围不改变处理配置的标识。

代码：[日期分段与共用执行](../../common/execution.py)、[读取范围校验](../../common/validation.py)。

## 3. 开始处理与重启

三轮运行端共用 `common/store.py::TableStore`。round1事件提取手动初始化脚本及其输入检查、注册写入行为不改。

每月首次读取后，只把本月遗留的 `"9"` 和 `"-1"` 改回 `"0"`；已有成功 `"1"` 和范围外记录保持不变，旧结果及配置标识保留。

读取只检查索引、九列结构和日期范围。数据库普通列的类型、NaN、空字符串、状态枚举、旧结果 JSON 和摘要格式均不做通用校验，也不转换或填空。新 AI 回答业务校验和新提交字符串检查保留。见 [round1帖子事件提取表](../data/TABLE_DESIGN.md#读取普通列原值与全表摘要)。

任务沿原读取顺序选取。发送请求前，先共同保存状态 `"9"` 和本轮配置标识，确认保存后再请求 AI。请求及运行内重试期间保持 `"9"`，不保存中间失败或尝试次数。

最终成功共同保存 `"1"` 和结果，最终失败共同保存 `"-1"`、可用结果及原因。本轮新失败不再次进入处理列表；下次运行读取到它时才重新处理。

round1事件提取不另设 active_keys 集合，也不维护成功、失败累加器。载入时记录已有完成数量，保存后只更新工作快照；月末与round2事件去重归组与round3事件影响分析共用结束状态统计，新增完成为结束时 1 的数量减载入基准，失败为当前 -1 的数量。重复保存同一终态不重复计数，未知状态原样保留，分类和可以小于总数。

例如 A、B 都已认领，答复包含 A 成功、B 普通失败。首次写入异常时两行仍为 9、缓冲不释放；下一次提交同一批。保存和内存同步成功后，A 为 1、B 为 -1，保存进度加 2，月末按状态计入成功 1、失败 1。预算耗尽则停止，不在收尾继续写。已有范围内状态 9 非零时不能进入下月，普通失败 -1 允许继续。

例如网络重试后仍失败，本轮只保存一次最终失败；重新启动后，该任务重新开始尝试。成功任务直接跳过。

代码：[任务选择与保存](../../common/store.py)。

## 4. AI 输入与配置变化

任务配置与各轮 AI、事件及 Embedding 配置共用安全 YAML 加载器。所有字典键须为字符串，同一个字典内不允许重复键，即使值相同也报错；例如 post_extraction_config.yaml 两次设置 task_path，或 logging 下两次设置 level，都会在配置加载时停止。不同字典可使用相同键名。任务和事件配置在创建数据客户端前读取，重复键不会触发任务读写。

AI 消息只包含配置中的提示词和单帖 `text`，不发送任务键、用户名、状态或旧结果。提示词支持 `{{task.text}}`；请求体还支持 `{{prompts.system}}`、`{{prompts.user}}`。插入的正文不再次当作模板执行，未知变量会报错。

请求为非流式 POST JSON。公司接口消息字段使用 `messages`，模型及其他参数来自 `api.payload`；common.ai_protocol 按配置字段构造请求，不猜测字段名称。环境变量只在接口 URL 和请求头中展开，同目录 `.env` 的优先级低于进程环境。

默认请求参数包括 `temperature: 0` 和 `provider_options: max`；后者作为字符串 `"max"` 原样发送。

每次启动读取一次 AI 配置，整轮使用同一份内容。修改文件不会改变已经运行中的请求。

`config_hash` 是用原始提示词模板和 `api.payload` 计算的 SHA-256 标识。计算前按固定 JSON 格式排列字段和编码，避免仅因字段顺序不同而得到不同标识。它不包含帖子正文、URL、认证、日期范围、并发、重试或响应解析逻辑；不同帖子使用同一配置时标识相同。

首次实际认领前，用 common.store.read_stage_hashes 调用 `cli.read(task_path, start_time='', end_time='', columns=['config_hash'])`，按列读取目标全表 config_hash，与当前配置比较；空日期表示全表，范围外摘要也参与。本次运行只计算、读取一次，跨月复用。返回 DataFrame，直接取 config_hash 列原值；读取失败或返回缺列时停止，不回退整表读取。空字符串不参与，其他原值不一致则停止，不补旧摘要。全部完成时不调用摘要接口。改提示词、模型或其他 payload 参数须使用符合该配置的新表，不能混写。

代码：[配置加载](../../common/config.py)、[请求构造](../../common/ai_protocol.py)。

## 5. 请求失败时怎么办

以下次数均包含首次请求，网络重试、服务错误和 AI 输出校验失败共用同一帖子的尝试预算；默认最多三次，实际以 `run.max_attempts` 为准。每帖独立计数，三轮之间不共用次数。

| 情况 | 本轮处理方式 |
| --- | --- |
| 建立连接、读取响应或发送数据时出现指定的网络错误或超时 | 有预算则重试；耗尽后仅该帖失败，继续其他任务。 |
| 服务返回 500～599 | 有预算则重试；最后仍是服务错误时停止整个程序。 |
| 返回其他非成功状态，包括重定向、400、401、403、408、429 | 保存该帖失败并停止整个程序，等待人工排查。 |
| 请求地址、协议、代理或等待连接池异常 | 停止整个程序，不自动重试。 |
| 成功状态码但响应解析失败、生成时间无法转换、回答截断、拒答或正文为空 | 有预算则重试；耗尽后仅该帖失败，继续其他任务。 |
| 正文不是约定 JSON，或事件字段、类型、代币列表不合法 | 有预算则重试；耗尽后仅该帖失败，继续其他任务。 |
| 单帖请求构造失败或其他非停止型请求异常 | 仅该帖失败，不自动重试。 |

本地读取超时可重试，服务返回 HTTP 408 则停止；等待连接池超时也停止。具体异常类型由 [网络模块](../../common/network.py) 的 `_RETRY_NETWORK` 和 `_STOP_REQUEST` 列表限定，不根据错误文案猜测类别。

重试之间采用随机等待，等待上限随次数增加并受配置限制。可重试的 5xx 若带有效 `Retry-After`，后续新请求共同遵守服务要求的等待时间；429 始终停止，不自动等待恢复。可选每秒起发上限同时约束首次请求和重试，为 0 时不额外限速。

网络错误或 5xx 不能证明服务端没有执行请求，重试仍可能重复执行并产生费用。

例如首次网络超时，第二次返回 `{"events":[{"event":"事实","tickers":[null]}]}`，只剩一次请求机会。重试继续使用相同帖子、配置和提示词，不追加纠错消息；中间失败不落库，最终保存仍使用独立的存储预算。

## 6. 什么结果算成功

成功要求 HTTP 状态为 200～299，响应为标准 JSON 对象，没有明确 error。候选回答列表 `choices` 中必须只有一项整数编号 `index=0`，程序取这一项；它必须是 assistant 消息、`finish_reason="stop"`、正文为非空白字符串，并且没有拒答或内容过滤。需要保存的字段须能正常编码。

2026-10-15 用户要求round1事件提取也增加业务输出校验。通过接口外层检查后，正文必须是标准 JSON 对象，恰好包含 `events` 数组；每个事件恰好包含 `event` 和 `tickers`，`event` 为非空白字符串，`tickers` 为数组，其中每项均为非空白字符串。拒绝重复 JSON 字段、非标准数值、无法编码的文本、代码围栏和 JSON 之外的说明。

`{"events":[]}` 是合法的无事件结果，`{"events":[{"event":"事实","tickers":[]}]}` 也合法。round1事件提取不检查账号代币映射、不改写或去重代币、不判断事件事实及币种归属是否正确；映射与规范化继续在后续导入时进行。请求时和导入时共用 common.validation.validate_extraction_output，避免口径不一致。

仅导入已有回答时，允许在内存中修复 event 正文未转义的英文双引号，修复后仍执行上述严格校验；不写回第一轮表，也不调用 AI。第一轮新请求不使用该兼容处理。支持范围、批量报错和停止规则见 [历史回答引号修复](EVENT_RULES.md#历史回答中未转义引号的批量处理)。

空 tickers 的第一轮成功不代表可以导入：账号无映射时，导入程序在写入事件表前停止本次全部导入，第一轮结果及成功状态保留；补齐映射后重跑同范围补导。缺少 tickers 字段、tickers 为 null 或包含非法项则第一轮校验失败并按请求预算重试。完整处理顺序和混合合法事件的例子见 [事件展开规则](EVENT_RULES.md#2-检查round1事件提取并展开记录)。

正文和推理保留原文，不用解析后的对象覆盖原始回答。一般失败保留最后一次可安全提取的结果及具体原因；生成时间无法转换时，按下文规则清空全部 AI 结果。原因最多 512 个字符，不保存完整原始响应。已成功历史任务继续按原规则跳过，不追溯新增的正文业务校验；导入前仍会完整检查固定的round1事件提取结果。

`usage_json` 只记录最终一次响应的 usage，不累计中间重试。缺失或 null 时为空，不能据它计算全部尝试的总费用。

### `response_created` 保存北京时间文本

最终响应的数值 `created` 按 Unix 秒转换为北京时间（固定 UTC+8），保存为 `YYYY-MM-DD HH:mm:ss` 字符串，小数秒不保留。例如用户提供的真实接口值 `1791947560` 保存为 `"2026-10-14 11:12:40"`。转换在响应解析阶段完成，保存模块直接写入该文本。不使用本机时区，不根据数值大小猜测秒或毫秒，也不替换帖子的索引时间。

`created` 缺失或为 null 时，生成时间写空字符串，不因此判失败；`0` 是有效时间戳，保存为 `"1970-01-01 08:00:00"`。非数值（包括布尔值和数字字符串）或超出可转换日期范围时，本次响应失败；若预算耗尽时仍有此问题，最终共同保存 `status="-1"`、空的 `ai_response_content/reasoning_content/usage_json/response_created` 和失败原因，覆盖这条任务上次留下的 AI 结果。其他失败仍保留最后一次可安全提取的结果。

若本次响应还有更优先的 HTTP、接口、回答或编码错误，保留原有优先错误原因；仅时间转换失败时，原因明确说明 `response_created` 无法转换。成功 HTTP 响应中的时间转换失败按第 5 节在剩余预算内重试；HTTP 失败仍按第 5 节决定重试或停止。改动只作用于之后的新响应，不自动转换或清空其他已完成的历史记录。

代码：[响应解析](../../common/ai_protocol.py)、[结果写入](../../common/store.py)。

## 7. 保存时只改哪些内容

### 已确认并实施的整批保存约定

2026-10-15 用户确认 write、update_by_column、update_by_index 正常返回即本次整批及全部提交列写入，抛异常即完全未写入。已按确认方案删除 pending_patch、异常读回、逐行确认和剩余行重试。各轮保留原索引、指定列、排序、副本、类型检查和存储预算。

这只覆盖单次调用，多次调用不共同回滚。例如认领状态保存成功、最终结果保存失败时，已经保存的认领状态保留，重启按恢复规则处理。AI 分析结果中同时包含成功和普通失败，仍作为一批共同保存。初始化续建只追加新记录，不修复旧行；细节见 [事件规则第 3 节](EVENT_RULES.md#3-初始化与续建)，完整实现和验证见 [存储精简方案](../history/STORAGE_SIMPLIFICATION_PLAN.md)。

所有更新按原 `(date, id)` 定位，通过同一客户端的 `update_by_column(task_path, df)` 提交本次指定列。提交的 DataFrame 可以只包含本批要更新的部分行，索引键直接取自原读取表，普通列只包含下表列出的字段；未提交列保持原值。客户端必须提供按列更新的接口，不能用 `update_by_index` 代替。

并发请求的答复随完成消息携带原任务键，先按键生成每行结果，再检查本批复合键唯一，并将整个更新表按 `(date, id)` 升序排列，确认索引严格递增后提交。先比较 `date`，日期相同再比较字符串 `id`；不转换索引值、日期时区或精度，不单独重排索引。恢复状态、认领任务、最终保存和异常收尾均遵守此规则；保存异常时整批重试仍使用相同排序。重复键在调用客户端前报错，不静默去重。

例如原帖键为 `(2021-01-01, "10")`、`(2021-01-01, "2")`、`(2021-01-02, "3")`，答复按第三帖、第二帖、第一帖的顺序完成，提交时仍按上述原帖键的顺序排列，答复和同一行其他结果字段一起移动。这里 `"10"` 排在 `"2"` 前，因为 ID 保持字符串类型。每个更新批次内部严格递增；任务选择仍沿原读取顺序，不等待较早请求完成才保存较晚请求。

| 操作 | 提交的列 |
| --- | --- |
| 重启恢复 | 只改 `status`。 |
| 标记开始处理 | `status`、`config_hash`。 |
| 保存最终结果 | `status`、`ai_response_content`、`reasoning_content`、`usage_json`、`response_created`、`error_message`。 |

成功清空旧错误，缺失的结果字段明确写空字符串，不能保留上次结果冒充本次结果。状态和相关字段在一次更新中共同提交，按用户确认的接口约定全部成功或全部未写入。

最终保存前，先校验本批所有更新字段都是字符串。发现非字符串时，报错说明具体字段名和实际类型，例如 `最终更新字段必须为字符串：字段=response_created，实际类型=int`；错误说明只包括字段名和类型，本批在写入前停止。该校验针对本轮待保存结果，不读取历史结果字段，也不将非字符串自动转成文本。

默认每 200 条最终结果保存一次，不足时按首条结果等待时间达到 1 秒保存，月末和收尾时也提交余量。实际值以 `batch_size`、`result_buffer_size`、`flush_interval_seconds` 为准，结果缓存容量不得小于批次大小。

保存异常时，本次整批完全未写入，不读回，不更新内存、状态计数或保存进度。有预算则按 storage_retry_seconds 等待后，用相同索引、列和值重试整批；每次传给客户端独立副本。storage_max_attempts 默认 3 次且包含首次，默认等待 1 秒，最后一次失败后不再等待。正常返回才同步本批内存；提交前校验和提交后内存同步异常不进入 CLI 存储重试。

保存失败只重试写入，不再次请求 AI。预算耗尽抛 BatchPersistenceError，保留 stage 和原始异常链，停止网络、保留结果及队列，收尾不额外保存。异常不再包含 pending_patch。round1事件提取与round3事件影响分析的 unsaved_results 保留原结果元组缓冲；round2事件去重归组保留最多一条已经出队的原完成消息，其余消息通过 completed_results、unpublished_results 保留。数据只在当前进程内，退出后丢失；下次按数据库状态恢复，可能需要重新请求未保存的 AI 结果。

CLI 已正常返回、随后内存同步发生普通异常时，同样抛 BatchPersistenceError，但消息明确为“CLI 已写入，但内存同步失败”。此时数据已经落库，收尾不能重写；原答复仍附在异常中供核查，重启读取数据库后按已保存状态处理。

缓冲保存条件只保留批次数量、等待时间和任务结束；容量保护统一在收取入口。中断留下完整批次时，收尾先保存该批再取下一条完成消息。网络统一在 finally 中关闭一次。

代码：[任务保存](../../common/store.py)、[批量保存](../../common/execution.py)。

## 8. 停止、并发与实际保证

一个round1帖子事件提取表只支持一个处理程序写入，其他新任务创建流程也须协调写入。同步客户端始终在调用入口线程使用，AI 请求在独立网络线程执行。

默认同时处理 100 个网络作业，完成消息及结果缓存有容量限制；实际参数来自 AI 配置。每月数据表仍可能很大，按月读取和有界结果缓存不代表整个程序有固定内存上限。两端日期未设置时会全表读取。

答复通过原 `(date, id)` 与帖子关联，不能按答复到达的行号配对。2026-10-14 用户反馈 xdata 在第 86 行附近拒绝无序或重复索引；本地复现确认旧实现能保持键与答复的对应，但会直接提交完成顺序形成的无序批次，即使键全部唯一也能触发同类拒绝。此次修复在统一更新入口排序并检查重复键，实际运行的第 86 行及真实客户端行为仍需接入核实。

整体停止时不再开始新任务或重试。网络线程发现停止型错误后，`request_stop()` 同时设置停止标志并通知 `_serve()` 开始收尾，不再等调用线程执行 `check()` 或 `shutdown()` 才取消剩余请求。触发停止的最终失败结果及此前已生成的最终结果仍交给调用线程；网络线程取消并等待其余任务结束、发布对应消息，然后关闭 HTTP 客户端和事件循环。

调用线程通过 `check()` 获知停止，停止自己的调度，并通过 `shutdown()` 等待网络线程退出，再按已有保存规则处理完成消息。`shutdown()` 在正常结束和用户中断时也负责发出停止通知。重复通知保留第一次停止原因；初始化期间收到的停止要求也必须执行，不能一直等待关闭。

提交和停止通知按同一把短锁确定先后。停止前已安排的作业正常进入收尾；停止后到达的提交直接生成停止消息，不再安排到事件循环。每条提交的作业只发布一次完成或停止消息，停止消息不伪造 AI 最终结果。已标记开始处理、但没有最终结果的任务保留 `"9"`，未开始的任务保持 `"0"`，停止后不读取后续月份。强制结束进程可能来不及保存。

例如调用线程正在保存数据库，另一个请求返回 401：网络线程立即通知收尾，取消其余仍在等待的请求；已生成的成功结果和这条 401 失败结果等待调用线程保存。即使某条被取消的请求原本再等一秒就可能完成，也不再等待；没有最终结果的认领行留 `"9"` 供下次恢复。

本地停止不保证远端请求撤销。请求已执行但结果丢失或未保存时，下次运行可能重复调用；程序不保证服务端恰好执行一次。

正常结束表示指定范围的本轮处理及保存完成，允许存在本轮失败任务；统计区分已有成功、本轮成功和本轮失败。异常收尾日志不表示处理完成或结果全部保存。
