## 1. 目标与判断

用户希望按公共部分和各轮独立代码整理目录，并检查还能共用什么。采用根目录直接划分基础公共能力、事件业务公共能力、初始化和三个轮次，启动入口另行集中。

现有主要问题是归属不清，公共能力已经抽出较多，继续建设统一运行框架的收益有限。

已核实的情况：

- `ai_batch` 同时包含公共网络、配置、保存、执行和 Store，也包含第一轮的任务表、初始化、结果转换和启动。
- `event_pipeline` 同时包含事件导入、第二轮、第三轮以及两轮共用的结果表和事件历史。
- 三轮已经共用 `NetworkWorker`、`TableStore`、存储重试、索引结构校验；第一轮与第三轮已经共用 `run_segments` 和 `SegmentCoordinator`。
- `impact.py` 从 `relation.py` 导入 `current_input`、`require_prompts`。第三轮因此需要导入第二轮实现才能取得共用函数。
- `records.py` 在函数内导入 `store.validate_table`，`store.py` 又导入 `records.py` 的字段和时间函数。当前通过局部导入可以运行，但模块依赖可以进一步理顺。
- 第二轮、第三轮使用同一张统一结果表。不能为目录对称而拆成两张表或复制两个事件 Store。
- 初始化实际有两种业务：源帖子建立第一轮任务；第一轮成功回答展开为后续事件任务。后者既有主入口自动调用，也有独立导入入口。
- 当前生产代码单文件最大约 370 行，没有必要把每轮都固定拆成输入、校验、转换、调度等多个小文件。

## 2. 可行方案比较

| 方案 | 好处 | 代价与判断 |
| --- | --- | --- |
| 保留三个现有包，只调整文件名称和少量位置 | 修改范围最小，旧命令和导入容易保留 | 公共和第一轮、导入和后续两轮依然混放，改善有限 |
| 根目录按公共能力、事件共用、初始化和轮次组织 | 找代码时能先按业务定位，公共依赖清楚；能继续使用现有核心实现 | 需要修改导入、配置定位、测试替换路径及文档链接；推荐 |
| 每轮完全独立，或引入统一的阶段基类和插件框架 | 表面结构对称 | 前者重复事件表和历史逻辑，后者增加调度分支及接口；当前没有对应需求 |

推荐方案带来的主要收益是可读性和维护边界，不预期因为移动目录而提高运行速度。相同处理规则、同样的数据读取和请求预算下，时间和内存占用应基本不变。

## 5. 还值得共用和不宜合并的部分

本次新增价值主要来自以下归位，并非再写一套执行框架：

1. **事件数据约定独立。** 将字段、表结构和事件输出格式从运行及初始化代码中取出，消除 `records` 与 `store` 的双向依赖。
2. **共用输入直接引用。** 第二、三轮直接使用 `events.inputs.current_input`；第三轮不再通过第二轮获取公共函数。
3. **JSON 解析和业务规则分开。** 严格 JSON 解析是基础能力；`events/event/tickers` 是事件数据约定。三轮仍各自校验新回答的业务含义。
4. **日志和退出处理适度复用。** 当前存在重复设置，但第一轮初始化、第一轮处理与后两轮的默认格式和报错方式并不完全相同。只提取相同操作，保留各入口既有参数、检查顺序和初始化错误提示，不顺手统一行为。
5. **测试夹具归位。** `test_entrypoint.py`、`test_store.py` 从 `test_event_pipeline.py` 导入 `Tables` 等辅助对象。将这些模拟客户端和样例生成函数放入测试支持模块，再按初始化、历史、第二轮、第三轮划分大测试文件。已有断言保留。

不合并三轮调度。第二轮同币的下一时点必须等待当前时点全部结果保存；同一时点使用相同前史，最终普通失败会暂停该币。第一轮和第三轮处理相互独立的任务，适合现有分段并发及缓冲。保留这个区别比统一调度类更清楚。

不合并两种初始化。第一轮完整读取源帖、一次建表；事件导入按事件和代币展开，还包括自动追加、恢复补导、独立固定输入核对。这些是业务差异，只继续共用已经存在的索引校验和存储重试能力，不改变第一轮初始化的既定行为。

不引入 AI 配置继承。三份 AI 配置有相同字段，但模型、提示词及运行参数可以分别调整。相同 YAML 片段不是必须新增配置合并机制的理由。

不新增通用仓储、阶段插件、统一结果类型或每轮专属存储副本。现有 `TableStore`、两个业务 Store 和两种执行方式已经覆盖需求。
