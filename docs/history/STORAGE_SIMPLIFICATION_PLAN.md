## 2. 采用的选择和取舍

采用同步提交、整批重试、异常停止。保存函数正常返回后，调用方按整批已保存处理；失败则用原数据重试，不再读取数据库判断有没有保存。

删除对部分写入、写入成功但客户端报错的处理，不增加兼容开关、存储状态表、恢复文件或依赖。收益是减少失败时的数据读取、逐行比对、数据副本和分散的状态检查；正常保存次数与批次大小保持现状。

代价是后续更换客户端仍须满足已确认的调用约定。失败时不再通过额外读回发现运行期间其他程序修改数据，这与现有单个程序协调写入的要求一致。启动读取、历史数据校验和输入冲突检查继续保留。

## 3. 一次按列保存的处理顺序

1. 按现有业务规则生成本批更新表，检查允许修改的列、字符串值、编码和重复键。整行按原复合索引排序，不重建日期索引，不改变时区或精度。
2. 本批更新表只保存在保存函数的局部变量中。每次向 CLI 传入副本，避免客户端改动重试使用的数据；store 不保存另一份待确认更新。
3. 调用 update_by_column。只对这次 CLI 调用抛出的普通异常进行存储重试；提交前校验和提交后的内存同步错误不进入重试循环。
4. CLI 抛异常时，本批视为完全未写入。不读回、不确认其中任何行，也不增加成功数、失败数或保存进度。有剩余预算时，等待后提交同一整批数据。
5. CLI 正常返回后，调用 _confirm 同步本批内存及计数；普通同步异常转换为消息明确的 BatchPersistenceError，外层直接停止，不能在 finish 中再次写入。原答复仍保留供核查，重启读取已落库状态。
6. 预算耗尽时抛出 BatchPersistenceError，保留阶段和原始异常链；调用方停止，不再提交本批或后续批次。KeyboardInterrupt、SystemExit 等退出信号不作为普通存储异常自动重试，继续进入停止收尾流程。

保留 run.storage_max_attempts、run.storage_retry_seconds，默认分别为 3 次和 1 秒。次数包含首次提交；只有还有下一次尝试时才等待。存储尝试不消耗 AI 请求预算，也不重新请求 AI。

write_columns 删除 validate_observed、immutable_columns 参数；各 store 删除只为异常读回提供的校验闭包及 pending_patch 初始化。_read_segment 仍用于正常读取任务；业务字段校验和不可修改列的写入限制继续保留。

## 4. 各轮结果、计数和缓冲

认领仍先共同保存状态 9 和配置摘要，正常返回后才发送对应 AI 请求。认领保存最终失败时，该批不发请求；此前其他批次已经保存的状态不回滚。

第一轮、第三轮继续使用 SegmentCoordinator.buffer，以及现有网络完成队列和 unpublished 列表。只有结果保存正常返回后，才清空对应缓冲并增加整批保存进度；失败时整批结果仍保留，不产生部分成功计数。

第一轮继续在 _confirm 中按内存原状态 9 到 1/-1 的转换计数，保留重复保存不重复计数的能力；不再有一次 CLI 调用内的部分确认。第三轮继续沿用恢复后的完成基准与现有范围汇总。批次大小、缓冲容量、定时保存和公开统计字段保持现状。

第二轮继续单条即时保存。当前代码从完成队列取出消息后才保存，因此在局部保留当前这条原始完成消息，保存成功才释放。最终保存失败时，将这条消息附在异常的 unsaved_results；队列中尚未处理的消息继续通过 completed_results、unpublished_results 保留。此缓冲最多一条，不在 store 上增加待保存状态，也不另存候选列表。

第二轮自动判新没有 AI 答复，不额外制造响应缓冲；保存失败后停止，重启依据已保存状态执行现有规则。关联正常保存后，才允许加入历史并推进同币后续时点。

上述异常数据仅供当前进程调用方核查，进程退出后仍会丢失。重启从数据库读取：已完成行跳过，未保存结果的遗留 9 按原规则恢复后重新处理，不新增跨进程结果恢复能力。

## 5. 失败停止、异常收尾和月份切换

BatchPersistenceError 保留公开导出和 stage，删除 pending_patch 参数和属性，不以 failed_patch 等名字复制同一套状态。仓库内相关引用集中在保存模块、初始化和测试；外部调用方若读取该属性，需要随本次接口变化调整。

第一轮、第三轮按已有异常类型处理：捕获 BatchPersistenceError 后先停止网络并等待退出，附上原结果缓冲和完成队列，再传播异常；不调用 finish 额外保存，避免预算耗尽后再次尝试。_retain_unsaved 删除 store 参数，只收集已有缓冲和队列。

第二轮同步调整收尾：保存失败后停止网络并保留当前消息及队列，不继续消费并保存后面的结果。通过异常处理顺序控制，不增加常驻的保存失败标志。收尾时的网络错误不能覆盖已经发生的保存错误。

AI 停止型错误、用户中断等其他停止原因，仍先关闭网络，再尽量保存已生成的最终答复。收尾保存同样使用原存储预算；如果此时耗尽预算，立即停止并保留剩余缓冲及原始停止原因的异常链。保存失败不转换成一条 AI 业务失败结果。

check_month_complete 简化为只接收已有 processing 数量，删除 pending_patch 参数。run_segments 删除汇总前只检查 pending_patch 的调用；正常执行只有在剩余缓冲保存返回后才会汇总，保存失败直接经异常路径停止。两轮仍在各自汇总入口检查范围内状态 9：存在 9 就不能加载下一月，已保存的普通失败 -1 仍允许继续。月末不增加数据读取或未确认集合。

## 6. 初始化与续建的配套调整

本节已按用户最新删除请求更新：create 完整建表，resume 仅追加新记录。所有旧行保持原值，删除自动补列、补单元格及修复进度。

create 全部校验通过后 register 一次，再 write 完整初始批次，失败整批重试；空表同样保存结构。注册失败停止；write 预算耗尽后可用 resume 接续已注册的空目标。

resume 启动读取并严格检查旧表结构、索引、字符串字段和本范围固定输入，任何缺列、缺失值或冲突都在追加前停止。仅无任何行和列的已注册目标按初始空表处理；非空缺列数据和带部分列的空表不自动补齐。

按原复合索引筛出不存在的新记录，检查新旧 record_id 全表唯一及日期索引类型、时区和精度一致，然后只对完整新增批次调用 update_by_index。没有新行直接返回。保持输入、已有结果及范围外记录，不调用 update_by_column，不拼接完整目标表；总数直接为旧行数加新增行数。

默认保存预算仍为 3 次、间隔 1 秒，包含首次；失败不读回，重试同一新增批次，耗尽则抛保存异常停止。重启 resume 从实际数据筛选新行，已保存索引不会重复追加。第一轮 initialize_tasks 不改。
