# 第一轮成功数据从内存导入后续任务

2026-10-15 Store 共用调整已完成：第一轮读取普通列不做内容质检，事件导入仍在实际解析回答时检查业务结构；旧事件表通用单元格质检取消，固定输入比较、索引去重和新行追加保留。事件写入调用共用 write_with_retry，注册在循环外；内存交接和主入口导入触发方式保持本方案原有规则。第一轮手动初始化不改，真实摘要按列接口另保留占位。

日期：2026-10-15。状态：按用户确认方案实现。本次读取第一轮结果表时，如果没有帖子已经是 status="1"，就直接用本次成功保存的内存数据导入，只查目标元数据；如果有帖子已经是 status="1"，就使用这些行已保存的 ai_response_content，并读取统一结果表核对索引，只追加缺少的任务。导入时均不重新读取第一轮结果表。保留首次自动建表、失败补跑及第二、三轮独立启动。

## 按真实顺序处理

1. main.py 加载 job_config.yaml 与 event_config.yaml，后续任务来源和日期沿用本次第一轮实际参数，复用同一个 cli。日期范围按帖子原发布时间筛选，不是程序从启动到结束的时间；未设置日期限制时读取全表。
2. run_worker 按该范围读取第一轮结果表；设置日期范围时按自然月分段。每段读取后，先记住哪些帖子已经是 status="1"：这些帖子跳过 AI，保留其已保存的 ai_response_content；其他帖子继续按原规则认领、请求、重试和保存。
3. 当前分段全部结果保存并通过月末检查后，可选 on_successful_posts(new_posts, previous_posts) 回调交出两份成功帖副本。new_posts 是本次调用 AI 后成功保存的帖子；previous_posts 是本段读取时就已经 status="1"、本次未再调用 AI 的帖子。失败及未确认保存的结果不交出。
4. 回调在调用线程执行，只交出原 date/id 索引和 text、user_name、status、ai_response_content。main.py 收集这些必要数据，不复制推理、用量等无关字段，也不读取源表补齐。
5. 整次第一轮正常结束后，调用 import_saved_event_records 导入这些内存数据。第一轮异常或用户中断时，不开始导入；已经保存成功的帖子，下次在配置范围内读到时会是 status="1"，跳过 AI，并通过 previous_posts 交给导入模块。
6. 没有成功帖时直接返回第一轮统计，不查询或创建目标表。普通帖子失败不阻止其他成功帖导入；失败帖子补跑成功后再导入。

## 本次读取时没有已成功的帖子：直接追加

如果本次读取第一轮结果表时，没有任何帖子已经是 status="1"，则 previous_posts 为空。第一轮正常结束后，执行以下步骤：

1. 直接使用本次成功保存的内存数据，解析 ai_response_content 中的 events，按原规则生成 record_id、原 date 和全部初始字段，不重新读取第一轮结果表。
2. 只调用 read_meta(result_path) 确认统一结果表是否存在，不读取已有任务或扫描旧索引。
3. 明确 DataNotFound 时 register 一次，再 write 完整初始表；已有表直接 update_by_index 追加本批。已有表且本批全部为空事件时不写入；首次缺表仍写入合法空结构。

例如第一轮本次只完成新帖子 B，已有事件表包含 A：导入只使用内存中的 B，查询目标元数据后追加 B，不读取 A，也不重新读取第一轮。

## 再次运行：补上之前未导入成功的任务

再次运行 main.py 时，如果本次读取的第一轮结果表中，有帖子已经是 status="1"，则 previous_posts 非空，按以下步骤处理。这也适用于本次配置的日期范围与以前处理过的范围重叠的情况。

1. 第一轮只读取本次配置的帖子日期范围。读取时已经 status="1" 的帖子不再调用 AI，直接保留该行 ai_response_content，以及原 date/id、text、user_name、status；其他帖子按原规则处理。
2. 第一轮正常结束后，导入模块解析内存中的 ai_response_content.events，包括读取时已成功的帖子和本次刚成功保存的帖子，不再读取第一轮结果表。
3. 通过 read(result_path) 读取一次整张统一结果表，检查索引结构和唯一性。虽然这里读取整张目标表，但准备导入的帖子仍仅限本次第一轮配置的日期范围，不会额外导入范围外帖子。
4. 按 (date, record_id) 逐条核对：统一结果表里没有的，追加完整初始字段；已经有的，跳过，保留原行的第二、三轮状态、关联和分析结果。不比较已有行的事件正文、状态、评分等业务字段。
5. 同一 record_id 已在其他日期出现，或新增日期索引类型不一致时，在写入前停止。

例如，本次配置处理 2026 年 1 月 1 日至 1 月 31 日发布的帖子，并且每帖只生成一条 ETH 任务：

| 帖子 | 本次读取前的情况 | 第一轮如何处理 | 自动导入如何处理 |
| --- | --- | --- | --- |
| A | 第一轮 status="1"，上次事件任务写入失败 | 不再调用 AI，使用已保存的 ai_response_content | 目标中没有 (A 原发布时间, A:0:ETH)，追加这条任务 |
| B | 第一轮 status="1"，任务已导入，第二轮也已完成 | 不再调用 AI，使用已保存的 ai_response_content | 索引已经存在，跳过，保留第二轮结果 |
| C | 第一轮 status="-1"，上次调用失败 | 重新调用 AI，成功后保存结果 | 用本次成功保存的 ai_response_content 生成任务，核对索引后追加缺少的任务 |

A、B 读取时已经成功，因此本次只读取一次统一结果表，A、B、C 生成的任务一起核对索引；C 本次仍失败则不导入。2 月发布的帖子不参与本次处理。这里的“再次运行”指重新执行 main.py；“1 月 1 日至 1 月 31 日”指帖子发布时间范围。

目标明确缺表时，register/write 本次全部候选；已注册但没有任何行和列的空目标可继续追加。全部空事件时，只 write 补齐合法结构，不重复注册。

## 首次建表、保存与停止

用户已确认首次建表须 register/write，读取缺表报 DataNotFound。元数据或数据读取的异常类名为 DataNotFound，或错误文本含该独立标识时才建表；其他读取异常原样传播，不注册或写入。

register 只执行一次；write 或 update_by_index 默认最多尝试 3 次，失败重试同一完整批次，不读回、不再次注册。CLI 正常返回即整批成功，异常即本批未写入。

导入失败保留第一轮已保存结果，main.py 抛出原异常。再次执行相同范围时，程序读到这些帖子已是 status="1"，直接使用已保存的 ai_response_content，核对统一结果表后追加缺少的任务。两张表分两次写入，不共同回滚。不新增导入状态、恢复文件或其他表。

## 输入约定与核查边界

正常直接追加依赖原有约定：原帖 ID 稳定唯一，已成功第一轮任务不人为回退、改 ID 或修改输入，同一结果表由一个程序协调写入。

人工修改历史输入、映射或成功状态时，须通过独立 initialize_event_records 入口核查并决定重算范围。独立入口继续保留 auto/create/resume、严格旧表校验和固定输入比较；它仍可读取源表，不属于日常内存导入路径。

## 接口、统计和内存

run_worker 增加可选关键字参数 on_successful_posts，原五个参数、默认行为和 RunSummary 返回值保持兼容。不传回调时，核心不为导入保留数据，也不导入事件模块。

import_saved_event_records(cli, settings, new_posts=None, previous_posts=None) 返回本次写入事件行数，不为计算全表总数读取旧表。独立 initialize_event_records 继续返回原 InitializationSummary。两条入口复用缺表识别及整批写入重试，避免维护两套保存逻辑。

main.py 为第一轮正常结束后的导入保留必要成功数据，内存随本次成功数量增长。若本次读取第一轮结果表时没有已成功的帖子，不读取或暂存旧事件表；只要读取时有帖子已经是 status="1"，导入时就读取并暂存一次旧事件表以核对索引。这里没有固定字节数的内存上限。
