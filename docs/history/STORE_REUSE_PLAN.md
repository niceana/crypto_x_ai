# 三轮 Store 共用实现与运行规则调整方案

日期：2026-10-15。

状态：用户确认后已实施。本文保留确认时的方案结构和实施边界，第 16 节记录实际结果。真实摘要按列读取接口按要求保留占位；第一轮一次性初始化脚本及函数保持原样。

## 1. 目标、范围和依据

将第一轮 `TaskStore` 与第二、三轮 `ResultStore` 中重复的读取、索引定位、状态恢复、认领、更新批次构造、保存后同步和状态汇总实现集中维护。两类保留各轮业务入口、输入组织及结果转换，共用一个较小的核心类。

本次不改变第一轮、第三轮独立任务并发，以及第二轮按同币时间推进的调度依赖。不新增数据表、状态列、恢复文件、插件框架、用户配置项或第三方依赖。

本方案的依据分为三类：

| 类别 | 内容 |
| --- | --- |
| 方案确认时的实现 | 两类 Store 分别持有读取快照和索引位置映射；三轮按列保存已共用 `persistence.write_columns`；第一、三轮已共用 `execution`；第一轮在保存后累加成功、失败数，第二、三轮主要按结束状态汇总。 |
| 本次用户确认的调整 | 取消数据库普通列内容校验；三轮按全表、本阶段核对配置摘要；摘要按列读取且接口先占位；恢复统一按 `batch_size`；认领按第一轮的职责划分；统计统一结束时按状态汇总；共用存储重试；第一轮一次性初始化不动。 |
| 尚待接入的信息 | 真实的按列读取 CLI 函数名称、参数和返回格式。本文只规定内部用途，不猜测真实接口。 |

现有单写入程序约定继续适用：同一目标由一个程序协调写入，数据读写留在调用线程；状态认领不提供多个程序之间的抢占锁。

## 2. 模块职责与依赖

### 2.1 采用一个核心类、两个业务类

新增 `ai_batch/store.py`，提供共用的 `TableStore` 核心。现有 `TaskStore`、`ResultStore` 使用这个核心，不再分别维护相同的基本流程。

| 模块 | 调整后的职责 |
| --- | --- |
| `ai_batch/store.py`，新增 | 读取当前范围的快照、建立原键位置映射、按原索引构造更新批次、阶段字段约束、分批恢复、认领写入、成功后更新内存、按状态汇总；集中放置摘要按列读取占位入口和摘要一致性比较。 |
| `ai_batch/tasks.py` | 保留第一轮 `TaskStore` 业务封装、任务选择、响应转保存字段及第一轮已有公开导出。一次性初始化函数和它仍使用的辅助校验不改。 |
| `event_pipeline/store.py` | 保留 `ResultStore` 业务封装、处理范围选择、事件关联及经济影响结果转保存字段、原帖正文定位、必要的事件运行前提。 |
| `ai_batch/persistence.py` | 共用一次存储调用的整批重试；按列保存入口保留索引检查及整行排序。重试函数不承担注册、业务转换、统计或内存同步。 |
| `ai_batch/runner.py` | 第一轮启动、分段加载、调用共用汇总，以及交出新成功和载入时已成功的帖子。 |
| `event_pipeline/relation.py` | 第二轮候选、输入、回答校验、按币时间队列、即时保存和历史推进。 |
| `event_pipeline/impact.py` | 第三轮已有任务的阶段前提、跨月历史准备、请求输入、回答校验和结果转换；继续委托共用执行器。 |
| `ai_batch/execution.py` | 继续共用第一、三轮的分月推进、网络名额、结果缓冲和停止收尾，改用统一后的汇总结果。 |
| `event_pipeline/records.py` | 保留事件生成、导入和去重业务；将本模块现有存储重试循环改为调用共用重试函数。 |

依赖方向：`TaskStore`、`ResultStore` 使用 `TableStore`；`TableStore` 使用共用保存、配置摘要和索引能力。共用模块不导入事件业务模块。共用核心不判断 `new/update/repeat` 的业务含义。

### 2.2 核心合并到什么程度

| 当前相似代码 | 共用后的处理 |
| --- | --- |
| 两个构造函数中的读取、原键位置映射 | 由核心加载快照并建立映射；各轮补充自己的运行上下文。 |
| `_read_segment()` | 核心根据有无日期范围调用现有 `cli.read`。 |
| 第一轮 `_index()` 与后续 `write()` 内的索引定位 | 共用从原索引按位置取批次的实现，不重新构造日期键。 |
| 更新表构造、提交字符串检查 | 核心只检查本程序本次准备提交的数据，不检查整张读回表的单元格。 |
| `recover()` 的重置动作 | 核心将调用方给出的本阶段遗留 `9/-1` 按批改为 `0`。 |
| `claim()` 的两列写入 | 核心共同保存状态 `9` 和已核对的配置摘要；不再次检查所选任务是否为 `0`。 |
| `_confirm()` | 核心更新当前快照中对应行列，不再累加第一轮专用成功、失败计数。 |
| 两种成功、失败汇总方法 | 共用结束状态统计；两种原返回对象仅负责字段名称映射和跨段累加。 |

阶段差异使用代码中的固定字段描述：状态列、摘要列、允许修改的列。使用简单常量映射，不增加注册器、配置文件或通用策略框架。

阶段字段对应如下：

| 阶段 | 状态列 | 摘要列 |
| --- | --- | --- |
| 第一轮 | `status` | `config_hash` |
| 第二轮 | `round2_status` | `round2_config_hash` |
| 第三轮 | `round3_status` | `round3_config_hash` |

第一轮既有九个普通列、事件表既有十六个普通列及两张表的原索引继续保留，不合并物理数据表。

## 3. 分别保留的业务逻辑

### 3.1 第一轮

- 单帖独立任务、原读取顺序、分月与并发方式保持现状。
- 新回答继续校验 `events/event/tickers`；无效回答按既有请求预算重试。
- 保存原始回答、推理、最后一次响应的用量、响应时间及错误，不新增原始响应或中间尝试的保存。
- `on_successful_posts` 继续在分段保存完成后交出两类成功帖；第一轮正常结束后，主入口再从内存生成后续任务。

### 3.2 第二轮

- 同币按时间推进；同一发布时间共享此前历史，该时点全部处理并保存后才加入历史。
- 候选检索、组历史构造、三个关联字段的回答校验分别保留。
- 正常 `uncertain` 转为 `new`；请求失败、截断、无效 JSON、非法匹配 ID 继续按失败处理。
- 关联结果即时保存。`new/update` 同时将第三轮设为 `0`；`repeat` 同时将第三轮设为 `1`，正常初始经济影响字段保持空。
- 自动判新同样保存本阶段摘要，不能因为未调用 AI 而绕过配置核对。
- 普通任务最终失败后暂停同币后续时点，其他币继续；保存未成功前不推进历史。

### 3.3 第三轮

- 本范围第二轮全部完成并具备可用事件组关系后，再处理第三轮。
- 仅 `new/update` 进入分析；`repeat` 跳过 AI。
- 新回答保留五字段校验和现有可替换 validator 接口，每次新答复仍只在网络业务入口校验一次。
- 经济影响结果批量保存；普通失败只影响本条，不改第二轮状态和关联。
- 跨月事件起点和此前进展继续保留；第二轮的 180 天候选窗口不裁剪第三轮组历史。

以上转换分别生成待写字段，随后调用共同保存流程。共用核心不把三轮结果拼成一种通用 AI 响应结构。

## 4. 读取规则：原值使用，不做普通列内容质检

### 4.1 取消的检查

对数据库返回表的普通列，不再逐格或整列检查字符串类型、NaN、None、pd.NA、空字符串、空白字符串、UTF-8 编码、状态枚举或摘要的十六进制格式。不自动补值、不将 NaN 转为 `""`，不改写读回字段。

第一轮不再区分“成功行必须严格检查结果、未成功行允许旧结果缺失”来执行读取质检；第二、三轮也不保留读表时全部单元格必须为字符串的检查。恢复阶段不再扫描已保存五字段结果或为了历史成功记录执行通用完整性检查，不根据残留结果自动补成功。

这项改变适用于运行端 Store、既有结果恢复，以及为待处理任务读取原帖正文的普通列内容检查。不能通过将同一检查搬到另一个加载函数，继续执行已取消的通用质检。

### 4.2 仍需区分的操作

| 操作 | 处理方式 |
| --- | --- |
| 索引、列名结构、必要字段是否存在、日期范围及原键唯一性 | 保留原有定位所需检查；它们不检查普通列单元格的内容，也不转换索引。 |
| 读取普通列 | 原样使用；不预先检查是否为 NaN 或空字符串。 |
| 状态选择 | 根据约定状态的原值选择任务，不为其他值自动推断状态。 |
| 摘要一致性 | 继续按第 5 节执行实际配置比较，不另做单元格类型或格式质检。 |
| 事件运行前提 | 第三轮要求第二轮完成；实际使用的历史组引用、资产与发布时间关系须能够构造正确业务输入。保留这些运行依赖，不扩大为历史字段质量扫描。 |
| AI 新回答 | 保留各轮业务输出校验和重试。 |
| 本程序准备提交的新值 | 保留允许列、字符串与编码检查，逻辑空值写 `""`。 |
| 导入时实际解析第一轮回答、展开及核对固定输入 | 保留既有业务处理；本次不删除生成任务所必需的解析或固定输入比较。读取旧表的通用单元格质检按本节取消。 |

对已保存关系，只保留运行所需的阶段、组引用、同币及严格早于当前披露等前提；不因本次共用恢复重新检查历史 `new_information` 是否空白、已有影响字段是否为非空字符串，或历史成功行是否缺少摘要。历史数据不自动修复。

### 4.3 取消校验后的实际影响

- 已成功帖的旧回答为空，不会在第一轮加载时被通用质检拒绝；若后续导入确实解析该回答，仍可能在实际解析时失败。
- 普通字段为 NaN 时原样保留；构造请求或执行实际业务操作若无法使用它，异常在实际使用位置传播，不先清洗或另加一轮质检。
- 第一轮某行 `status` 为未知值时，既不等于 `0`，也不是需恢复的 `9/-1`，因此不会自动加入待处理队列。
- 不因数据库字段有异常值而自动重做已完成任务或扩大处理日期。

## 5. 配置摘要：同表同阶段一致，按列读取占位

### 5.1 一致性口径

三轮统一要求：准备继续写入时，核对目标表本阶段的全表已有摘要，包含本次处理日期之外的记录。第一轮从当前的分段核对改为全表核对；第二、三轮保留各自阶段独立核对的方向。

继续调用现有 `config_hash`。原始提示词和 `api.payload` 参与摘要，模型和 temperature 等位于 payload 中的参数随之参与；并发、重试、URL 和认证不参与。摘要也不代表检索候选、账号映射或评分函数的完整版本。

当前运行配置只计算一次摘要，全表一致性只在本阶段本次运行确实需要认领时核对一次，跨月份复用核对后的摘要。不在逐条认领或每月加载时反复读取整列、计算摘要。

### 5.2 内部占位接口

在 `ai_batch/store.py` 集中保留一个内部入口，方案名称为 `read_stage_hashes(cli, task_path, hash_column)`。

- 输入是已有客户端、目标表路径、当前阶段摘要列名；不传日期限制，因为核对范围是全表。
- 真实接入只能使用用户之后确认的按列取数 CLI 函数，只读取所需摘要列。
- 内部调用方只需要遍历该列的原始值。真实函数是否返回 DataFrame、Series 或其他结构，等用户确认后在该入口适配；不在此猜测。
- 不把值转换为字符串，不填空，不校验十六进制格式。
- 占位未替换时，提示按列读取摘要接口尚未接入并停止相关运行，不能假装得到空集合，也不能用整表 `read` 或逐月整表扫描替代。
- 方案确认后已创建占位函数，并用模拟接口验证调用流程；真实接入仍等待用户确认，不猜测 CLI 方法。

第一轮初始化脚本、事件生成与导入不因这个占位入口增加摘要核对。仅运行端需要继续认领时才调用。

### 5.3 比较、缺省值和失败行为

1. 原有初始空字符串 `""` 不参与配置比较。
2. 其余原值直接与当前摘要比较；不同则停止，保留旧结果和旧摘要，不自动覆盖。
3. 若读到 NaN 或 None，不执行“缺失值校验”或补值；它们与当前摘要不一致时仍会触发配置冲突。这属于配置比较的结果。
4. 不再另外根据历史成功状态检查“摘要必须非空”，也不凭本次配置补写旧摘要。没有摘要的历史结果无法由此证明其生成配置；本方案不推测旧配置。
5. 配置冲突在首次 AI 请求或自动判新写入之前停止。现有恢复在配置核对前发生的顺序保留，所以遗留状态可能已经恢复为 `0`，不回滚已完成的恢复写入。
6. 本范围全部完成或没有实际需要认领的任务时，不调用摘要占位接口。第一轮原有配置加载入口保留；第二、三轮全部完成时继续允许不加载本轮 AI 配置。
7. 第三轮仍会读取完整事件历史；该读取不再顺便收集摘要来替代按列入口。去掉 `hashes` 的分段累加、每月重复配置比较及仅用于历史成功摘要缺失质检的状态。

例如，处理三月任务，但一月已有摘要 A、本次配置为 B，认领前停止；即使只处理三月，也不能混入第二套配置。不同阶段分别使用 A、B、C 不冲突。

## 6. 读取和前置处理的真实顺序

### 6.1 第一轮

1. 按现有入口加载配置、校验配置日期参数。
2. 按自然月读取处理范围；不设日期时保留全表读取。
3. 进行结构和原索引检查，普通列原值保留；记录本段已完成数量。需要交出成功帖时，继续记住载入时已成功的索引。
4. 批量恢复本段遗留状态，建立候选队列。
5. 首次实际认领前，通过按列占位接口完成全表摘要比较并缓存本次摘要；后续月份直接复用。
6. 认领、请求、转换并保存结果；结束时统一汇总，交出已确认成功帖，释放本段数据。

### 6.2 第二轮

1. 保留现有结果表和历史的读取范围，选择本次日期范围中的已有任务，不重新展开第一轮。
2. 检查定位结构，记录已有完成基准；批量恢复本阶段遗留状态。
3. 全部完成则返回；否则保留已有同币前史与补录冲突的运行判断，不扩大任务范围。
4. 读取本轮配置，按列核对全表本阶段摘要，读取待处理任务实际使用的原帖正文。
5. 从已完成关联形成历史，建立同币时间队列，再进入原有调度。

### 6.3 第三轮

1. 保留现有元数据日期边界与跨月历史准备；逐月读取必要结果，保留跨月原键唯一性和构造历史所需的索引。
2. 在任何恢复写入和 AI 请求前，完成整个处理范围已有任务的第二轮运行前提检查。后月第二轮未完成时，前月也不先恢复。
3. 全范围前提通过后，按月批量恢复第三轮，判断是否有待分析的 `new/update`。
4. 确实需要分析时加载配置，通过按列占位接口核对本阶段全表摘要一次。
5. 按月加载执行数据，只在有待分析任务的月份读取所需原文。缺少任务所对应的原帖索引仍在本月认领前失败；普通列值不另做内容检查。已保存的较早月份结果保留。
6. 继续使用现有独立任务执行器，结束时汇总并释放当前月快照。

## 7. 恢复、选择与认领

### 7.1 状态定义与恢复

状态继续使用字符串 `"0"` 待处理、`"9"` 已认领处理中、`"1"` 完成、`"-1"` 普通最终失败。读取时不验证枚举；运行逻辑按这些原值工作。

仅将本次处理范围、当前阶段原值为 `9/-1` 的记录改为 `0`。已完成记录和范围外记录不改。只提交状态列，不改旧结果、错误或任一阶段摘要。

三轮均按当前恢复操作使用的 `run.batch_size` 分批提交。未加载本轮 AI 配置时，第二、三轮继续使用现有默认运行参数；注入配置时从恢复起使用注入配置，之后沿用实际本轮配置。配置文件中的既有默认值和加载顺序不因此调整。

例如三条待恢复行、`batch_size=2`，分两次写入 2 条和 1 条。第一批成功、第二批失败耗尽预算，则前两条已为 `0`，第三条仍为原状态；立即停止。下次只需恢复仍为 `9/-1` 的记录。

不根据旧结果完整与否自动补 `1`，不修复历史 `repeat` 状态，不清理异常旧值。

### 7.2 任务选择与认领职责

- 候选集合根据待处理状态和本轮业务前提形成；出队选择沿用第一轮的职责划分，由选择端确认状态为 `0`。
- 第二轮的选择发生在同币时间队列中，第三轮的选择增加 `new/update` 条件；不强行共用一种调度队列。
- `claim()` 接收已选原键和已核对摘要，只共同保存当前阶段状态 `9` 与摘要，不再次检查状态，不重新扫描配置。
- 认领正常返回并更新内存后，才提交相应 AI 请求。已有“阻塞保存后、实际请求前”的停止检查保留。
- 空选择不写数据库、不发送请求。每个候选键按现有队列规则只出队一次，不新增认领集合或抢占机制。

## 8. 保存与存储重试

### 8.1 写入接口和注册边界

| 操作 | 接口 | 重试范围 |
| --- | --- | --- |
| 修改已有任务的指定字段 | `update_by_column` | 同一批原索引和本次提交列。 |
| 后续事件表首次完整写入 | `write` | 同一份完整初始数据；注册不在循环中。 |
| 向后续事件表追加新行 | `update_by_index` | 只包含新索引及完整新行的同一批数据，不夹带旧行。 |

第一轮一次性初始化脚本不适用本节的新接入调整，保持原调用和失败行为。

共用函数置于现有 `persistence.py`。它接收实际写入操作、原批次和运行重试参数，负责尝试、等待、重试同一批、耗尽后抛保存异常。每次调用给客户端独立副本，避免客户端修改入参影响后续重试。

一次存储调用继续采用用户已经确认的约定：正常返回即整批及全部提交列写入，普通异常即本次整批未写入。不读回确认、不处理部分写入，不重建 pending_patch 等持久或常驻未确认状态。

首次建后续事件表时先注册一次；注册失败直接停止。注册成功后，写入失败只重试写入，不再次注册。写入预算耗尽后，重新运行仍按既有导入规则处理实际目标。

### 8.2 按列保存的处理顺序

1. 业务类将已通过新输出校验的结果转换为待写字段。
2. 核心按原键取原索引、构造更新表，检查本阶段允许列、本次提交字符串及编码、重复键。
3. 更新表整行按原复合索引排序，保证答复与原键对应，不转换日期时区或精度。
4. 共用重试函数调用 `update_by_column`。普通写入异常且还有预算时，等待后重试同一批。
5. 写入正常返回后，退出重试函数，再更新正在使用的内存表对应行列。
6. 内存更新正常完成后，调用方才释放该批答复缓冲、增加保存进度或推进第二轮历史。

只捕获实际存储调用的普通异常来重试。提交前检查、结果转换和提交后内存同步都不放进重试循环。`KeyboardInterrupt`、`SystemExit` 等继续按停止规则传播，不作为普通写入错误反复尝试。

默认存储预算仍来自现有 `RunConfig`：最多 3 次，包含首次；有下一次尝试时才等待，默认 1 秒。存储预算不消耗 AI 请求预算，不重新请求 AI。

### 8.3 各阶段可修改列

| 阶段 | 允许修改的内容 |
| --- | --- |
| 第一轮 | 本阶段状态、配置摘要、回答、推理、用量、响应时间及错误；原文和用户名不修改。 |
| 第二轮 | 事件 ID、关联关系、新增信息、第二轮状态及摘要、按业务规则联动的第三轮状态、错误；原事件、资产、源帖 ID 及第三轮分析字段不修改。 |
| 第三轮 | 五个经济影响字段、第三轮状态及摘要、错误；第二轮关联、状态和摘要不修改。 |

认领只提交本阶段状态和摘要。恢复只提交本阶段状态。成功、失败和结果保存不重写配置摘要。当前阶段成功清空共享错误；恢复、认领和跳过已完成记录保留原错误。

### 8.4 提交批次与时机

| 操作 | 第一轮 | 第二轮 | 第三轮 |
| --- | --- | --- | --- |
| 恢复遗留状态 | 按 `batch_size`。 | 改为按 `batch_size`。 | 改为按 `batch_size`。 |
| 认领 | 根据当前空闲网络名额选一批。 | 保留现有按币时间调度的即时认领。 | 根据当前空闲网络名额选一批。 |
| 最终结果 | 按批次数量、时间或任务结束提交。 | 一条结果即时保存，确认后推进。 | 按批次数量、时间或任务结束提交。 |

`batch_size` 不要求所有操作必须等满批才执行。第一、三轮时间到达和任务结束仍提交不足一批的数据，现有缓冲容量约束保留。

## 9. 内存更新和释放

当前工作快照与临时提交表分别处理：

- 当前快照只持有现有阶段或分段正在使用的数据。保存成功后更新对应行列，供后续任务选择、第二轮历史和最终状态统计使用，不再维护一套独立成功、失败计数。
- 临时更新表和本批答复在成功路径处理完后释放；不再常驻保存一份待确认副本。
- 第一、三轮当前月份结束并汇总后释放本月完整表；第二轮沿用现有表与必要历史的生命周期，不在本次引入分月重构。
- 事件表完整初始写入和新增行追加没有正在运行的 Store 快照需要同步，写入成功即可返回并释放临时数据。共同重试函数不强制所有调用方同步内存。

例如记录 A 的数据库状态已从 `9` 保存为 `1`：内存也更新为 `1`，月底统计才会将其计入新增完成。第二轮还须使用保存后的事件 ID、关联和新增信息加入历史，才能处理后续同币披露。

若数据库写入成功、内存同步发生普通异常，抛明确的保存阶段异常，说明数据库已写入但本地同步失败；停止网络并保留答复，不再次提交。重启后读取数据库真实状态继续。异常附带答复不表示它一定尚未落库。

## 10. 统一统计规则

### 10.1 基准和结束值

每个执行分段在处理前记录本范围状态为 `1` 的数量，称为“已有完成基准”。恢复只改变 `9/-1`，因此恢复前后这个数量相同。第三轮在执行分段使用已恢复后的读取快照记录基准，继续保留现有准备阶段与执行阶段的分工。

分段正常结束时，使用已经同步的内存状态统一计算：

| 统计 | 计算口径 |
| --- | --- |
| 总数 | 本段本次范围的记录数量。 |
| 已有完成 | 处理前记录的完成基准。 |
| 新增完成 | 结束时状态 `1` 数量减完成基准。 |
| 本次失败 | 结束时状态 `-1` 数量；遗留失败进入运行前已恢复为 `0`。 |
| 待处理 | 结束时状态 `0` 数量。 |
| 处理中 | 结束时状态 `9` 数量。 |

共用汇总只返回这些标量。第一轮 `RunSummary` 和后续 `StageSummary` 保留既有公开字段名称和返回类型，通过字段映射、跨段相加使用同一计算方法。不增加新的公开统计类或未知状态字段。

第一轮删除 `_confirm()` 中的新增成功、失败累加，以及只服务这两个计数的内部状态。重复保存同一终态不会改变结束时状态数量，因此不重复计数。运行期间共用执行器的“已保存答复进度”继续按成功提交的缓冲条数累计，它与最终成功、失败分类分开。

### 10.2 统计限制和阶段含义

- 不为最终统计重新读取数据库；每段对内存状态进行一次分类汇总，跨段只保留标量。
- 未知状态、NaN 或其他无法匹配约定字符串的值，按实际比较结果不进入相应分类。总数仍包含该行，分类和可能小于总数，不通过额外质量校验强制相等。
- 第三轮的 `repeat` 通常在本轮开始前已由第二轮标为完成，计入已有完成；第二轮自动判新计入第二轮新增完成。完成数量不等于 AI 请求次数。
- `http_attempts_started` 继续由网络层提供，第二轮 `blocked_assets`、第一轮耗时保留原含义。
- 正常月份切换前，沿用已有 `processing` 数量检查：有 `9` 则不能进入下一月；普通失败 `-1` 可以继续。异常退出仍传播原异常，不将失败收尾伪装成正常统计返回。

例如 10 条记录，开始时完成 3 条，本次成功 4 条、失败 2 条、还有 1 条待处理，结果为：总数 10，已有完成 3，新增完成 4，失败 2，待处理 1，处理中 0。

## 11. 停止、保存失败与恢复

网络请求预算、限速、停止型错误和关闭方式保持现状。网络统一在既有 `finally` 中关闭一次，不增加关闭状态标志或通用调度包装层。

| 情况 | 行为 |
| --- | --- |
| 认领写入耗尽存储预算 | 该批不发 AI 请求，停止运行；已成功的更早批次不回滚。 |
| 最终结果保存耗尽预算 | 停止网络，保留现有答复缓冲和完成队列；收尾不重开预算、不继续写入，不进入下一月。 |
| 数据库成功、内存同步失败 | 停止并报告明确原因；不重写已提交批次，重启读取真实状态。 |
| 用户中断或其他网络停止 | 先关闭网络，再按现有规则尽量保存已生成最终答复；没有最终答复的认领行保留 `9`，下次恢复。 |
| 第二轮普通 AI 任务失败 | 保存本条失败，暂停同币后续时点，其他币继续。 |
| 第一、三轮普通 AI 任务失败 | 保存本条失败，不阻止其他独立任务。 |

第一、三轮继续使用现有结果缓冲；第二轮最多保留一条已出队、正在保存的答复。异常上保留既有答复和队列引用，不增加跨进程恢复文件。强制退出后，未保存的内存结果可能需要重新请求 AI。
