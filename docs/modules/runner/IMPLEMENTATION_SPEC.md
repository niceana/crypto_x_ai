## 1. 目的与范围

单 worker 按自然月顺序处理任务表中的帖子，每段先读任务、恢复遗留状态，认领时共同确认状态 9 和本轮配置摘要，再执行请求及程序内重试，最后将状态 1/-1 和最终结果共同保存。目标并发 100，默认结果每 200 条保存，不足时定时及当前月份结束提交；当前月全部保存确认后才进入下个月。

同步 cli 保持在调用入口线程，独立网络线程运行 asyncio 与共享 HTTPX 客户端。不创建 5 万个协程，不新增进程池、持久化重试堆、任务超时扫描或恢复进程。

## 2. 入口与前提

run_worker(cli, task_path, config_path, start_time=None, end_time=None) → RunSummary。cli 为调用方已经提供的同步数据客户端，支持任务规格规定的 read 和 update_by_index；task_path 为配置中的任务数据标识，原样传给每个 TaskStore。三个前置参数均为必填，不接收 callbacks 或 TaskCallbacks，不增加通用存储接口。worker 不创建数据客户端或新任务，也不接收源帖子 DataFrame。任务表使用 user_name 记录用户名；结构与输入核对由任务模块执行，旧 username 表不自动兼容或迁移。总起止日期仍从调用方配置传入，不增加命令行参数或 YAML 的月份开关。

调用方在整轮运行期间管理 cli 的生命周期，每个 TaskStore 保持同一客户端和任务路径。工具范围为按日的 [start_time, end_time]，两端日期均包含全天；按帖子 date 索引读取，date 与原帖 created_at 一致且处理时不变。任务配置的有界起止值为带引号的 YYYY-MM-DD 字符串；运行模块仅用不含时分秒的 date 对象做日期校验和自然月计算，并把当前分段的 YYYY-MM-DD 字符串交给 TaskStore。segment_start/segment_end、TaskStore 保存的边界及实际 cli.read 参数是同一组字符串；任务模块读取时不再格式化边界。帖子 date/id 保持原类型、时区、精度和值，详见任务规格。现有全年配置同步为 start_time="2021-01-01"、end_time="2021-12-31"；外部调用方须以实际最后一天表示截止日期。

调用方保证仅一个 worker 写同一任务表，前次网络线程已结束，现有数据流程创建新任务与 worker 写入已协调。允许脚本、Notebook 或已有事件循环中调用同步入口；它阻塞调用线程，网络使用独立循环。

目标 Python 3.8，使用 threading、queue、asyncio、time、datetime、HTTPX，不使用 asyncio.to_thread、TaskGroup、asyncio.timeout 或新版类型语法。

## 3. 总体执行顺序

记录启动时间 → 在 run_worker 启动处处理无界/单端配置 → 将两端日期字符串解析为 date → 检查 start<=end → 一次加载并固定配置快照，不计算摘要 → 按时间升序生成自然月闭区间的日期字符串 → 使用同一组 segment_start/segment_end 记录分段日志并交给 TaskStore(config, cli, task_path, segment_start, segment_end) 读取当前分段并建立快照 → 将本段 9/-1 重置为 0 并保存确认 → 检查本段 0，无则汇总并继续下一段 → 首次有 0 时建立共享网络线程并等待就绪 → 选择 0，认领时计算摘要并共同保存 status=9/config_hash → 提交作业、收取最终响应并批量保存 → 完成本段所有任务，保存余量并确认无待保存结果 → 汇总本段标量统计、释放本段数据 → 进入下一段 → 所有分段完成后关闭网络资源、等待线程结束 → 输出总成功失败数并返回。

每个帖子仅提交一个作业，该作业内部完成请求构造和最多 max_attempts 次请求，最终只发布一条结果。主循环不把新产生的 -1 重置为 0，也不等下一次 worker 启动。

### 启动处的日期转换与检查

直接在 run_worker 既有启动 try 中按顺序处理：

1. start_time/end_time 都是 None 时，将内部 start/end 设置为 None。
2. 只有一端为 None 时，沿用 ValueError("起止日期必须同时设置或同时不设置")，不读取数据。
3. 两端均设置时，直接执行 date.fromisoformat(start_time) 和 date.fromisoformat(end_time)，得到仅有年月日的 date 对象。配置沿用带引号的 YYYY-MM-DD 字符串；使用目标 Python 3.8 的标准库检查日期格式及有效性，非法日期或不符合格式的值原样报错，不增加正则预检、日期类型分派、ISO 时间字符串及 Z/时区处理。
4. start>end 时，抛 ValueError("start_time 不能晚于 end_time")，避免反向范围跳过全部月份却报告处理完成。start==end 有效，表示只处理该日。
5. 日期处理通过后才 load_config，继续原启动校验、标准异常日志和后续月份循环。

例如 "2017-01-01"、"2017-01-31" 在启动处转为 date(2017, 1, 1)、date(2017, 1, 31)，只用于日期检查和自然月计算；启动日志中用它们的标准字符串表示，仍显示 2017-01-01、2017-01-31。没有日期时间对象或附加的 00:00:00。"2017-01-31" 到 "2017-01-31" 处理 1 月 31 日全天；反向 "2017-02-01" 到 "2017-01-01" 在任何 cli 读写前报错。

不添加日期解析辅助函数、类型兼容入口或新的配置项。日期范围处理使用标准库 date；UTC HTTP 日期 Retry-After 是实际网络时间，继续保留其 datetime 和 timezone 依赖，与任务日期范围分开处理。

## 4. 自然月分段与月份切换

两端均未设置时保留一个无界分段，TaskStore 使用 cli.read(task_path) 读取全表一次，不向 cli 传入值为 None 的日期关键字，不享有按月内存限制。只设置一端、日期无法解析或 start_time>end_time，均在读取和状态更新前失败。有界边界由日格式配置解析为 date，只包含年月日；不推断或转换任务索引时区，真实 cli 的日历解释仍须与任务索引日期一致。_month_ranges 只按这些 date 对象推进，不添加时间或时区分支。

有界分段以解析后的起始 date 为第一段起点，依真实执行顺序生成：

1. 当当前起点 cursor<=end 时，使用标准库 calendar.monthrange(cursor.year, cursor.month) 得到当月天数，以该年、月和天数构造当月最后一天。
2. segment_end 取当月最后一天与总截止 date 中的较早者，形成包含两端全天的当前分段。
3. 使用 cursor.isoformat()、segment_end.isoformat() 生成 YYYY-MM-DD 字符串；这就是分段日志和 cli.read 的实际边界，不向客户端传次月月初或时分秒。
4. 当前段已经包含总截止日时结束生成；否则 cursor 推进到 segment_end 的下一个日历日，继续下一月。先判断结束再推进，末段不额外计算超出总范围的下一天。

月末长度来自标准库日历，日历日推进使用 timedelta(days=1) 作用于 date，不作用于带时区的帖子时间戳。两端都在同一自然月内只读一次；跨自然月即分段，首尾不足整月只处理交集。不改变帖子原 date/id，仅对范围边界做解析与日历运算。

例如 [2021-01-01, 2021-12-31] 依次得到 [2021-01-01, 2021-01-31]、[2021-02-01, 2021-02-28]，直到 [2021-12-01, 2021-12-31]，正常流程读取 12 次。2022-01-01 不在本次范围内，不生成第 13 段。若用户明确配置总截止日为 2022-01-01，则该日属于本次范围，另生成 [2022-01-01, 2022-01-01]。每月读取后立即完成该月的处理和写回，不先读取 12 个月再处理；存储异常核对所需的额外读回不计入正常读取次数。

部分月例子为 [2021-01-15, 2021-03-10]：依次处理 [2021-01-15, 2021-01-31]、[2021-02-01, 2021-02-28]、[2021-03-01, 2021-03-10]。1 月 31 日晚间帖子只在第一段处理，2 月 1 日零点只在第二段处理，3 月 10 日晚间包含在最后一段；相邻段不重叠，各段并集恰好为原范围。闰年二月最后一天为 2 月 29 日，12 月末的下一日为次年 1 月 1 日，均使用日历日期计算。

每段只在首次进入时恢复该段 9/-1，不在总范围启动时先读全部月份集中恢复，也不回读已经完成月份。空段、只有 1 的段直接进入下一段，不计算摘要、不发 HTTP；当前段没有 0 不代表整个总范围完成。本轮已经保存的 -1 保留到下一次 worker 启动，不能因月间切换而重置。

月份切换前要求本段候选队列、submitted、完成队列、结果缓冲、active_keys、pending_patch 都已清空，所有可提交终态已确认。本段失败行已保存为 -1 不阻止切换。只累计 RunSummary 的标量计数，释放本段 DataFrame、TaskStore、候选键和作业引用，不 concat 全年 DataFrame 或累计全年响应。一个 worker 内的网络线程、AsyncClient、限速器和统计继续复用，不跨月份重叠执行；正常切换不重新加载配置。

任何停止、下述须停止 worker 的 HTTP 状态或请求异常、读取或不可恢复保存异常均停止整个月份循环，不继续读取后续月。已完成月份保持其已保存结果；当前月没有最终响应的任务按停止规则保留 9；尚未进入月份不读、不重置状态。整个运行不是启动时的全表快照：已完成月份后来新增的任务留到下次运行，尚未读取月份以进入时的读取结果为准。

## 5. 线程与消息边界

调用入口线程保有当前分段的 DataFrame、TaskStore、同一 cli、固定 task_path、候选队列、submitted、active_keys、最终结果缓冲和运行统计，不为更新复制全表，也不保留已完成月份的整表；候选、在途与结果关联统一使用原 (date, id) 的 TaskKey。网络线程拥有事件循环、AsyncClient、真实 asyncio.Task、程序内尝试计数、等待与全局限速。

网络客户端准备好后设置 ready；主线程短时等待并检查线程失败，不能无限等已退出的线程。客户端启动失败直接传播，不标为帖子失败。

RequestJob 只含不可变的原 TaskKey=(date, id) 和当前选中行的 text 快照，只在提交时提取单帖输入，不提前把整个 DataFrame 转为请求列表，也不携带 user_name、历史结果、DataFrame 或 cli。date/id 只用于作业关联，不进入 payload；网络线程不能修改或重生成该键，只将 text 传入 render_payload(config, text)。主线程先共同保存 9 和本轮摘要，再经 loop.call_soon_threadsafe 提交，网络循环 create_task 并保存真实 Task；网络构造与重试使用计算摘要时的同一个固定配置快照。

每个作业只发布一条 CompletionMessage，内容为原 TaskKey、最终 ParsedResponse、本作业实际 HTTP 起发数，或 worker 停止/批次错误信息。不包含要求落库的重试次数或截止时间。

submitted 从提交到收取消息占作业名额，数量不超过 concurrency；完成队列容量为 concurrency，使用 put_nowait，不在事件循环阻塞。队列意外满属于不变量破坏，停止且不能丢结果。active_keys 从登记 9 到最终行确认才释放，保证同帖不重复处理。

## 6. 请求构造与一次请求

全运行共享一个 AsyncClient，连接和保活上限为 concurrency，follow_redirects=false、transport 自动重试关闭、trust_env 来自 YAML，默认 false。客户端阶段 timeout 使用 run.timeout_seconds，属于基础传输设置，不根据任务状态计时判断是否“挂了”。

作业开始后用配置模块根据提示词与 text 渲染一次独立 payload，本次所有请求使用同一快照，不添加用户名、帖子 ID 或日期。捕获 TaskRenderError 后直接取实际异常的简短说明，传给 request_failure(error_message)，不请求 HTTP、不自动重试，作为该帖最终失败返回。

每次请求先检查停止信号、遵守共享限速与暂停，再调用 client.post。收到响应后直接按 HTTP 状态和剩余尝试预算检查停止条件，须停止时立即设置共享停止信号，不等主线程收取结果才阻止其他请求。HTTP 状态与完整响应文本供当次解析；只有准备重试的 5xx 才提取 Retry-After 用于内存等待。只将 success、HTTP 状态、正文、推理、usage、created 和 error_message 带入最终结果，不保留响应原文或其他接口诊断元数据。HTTP 200 本身不代表业务成功。

按实际异常类型处理：ConnectError、ReadError、WriteError，以及 ConnectTimeout、ReadTimeout、WriteTimeout 可按下节预算重试。PoolTimeout 是获取连接池名额超时，不视为网络波动；InvalidURL、UnsupportedProtocol、LocalProtocolError、RemoteProtocolError、ProxyError 也不作为可重试网络故障，均按停止规则结束整个 worker。RemoteProtocolError 表示服务端协议异常，不能仅凭没有有效响应就认定为网络波动。其他 RequestError（包含 DecodingError 和未列入上述范围的异常）只终结该帖，不自动重试。先捕获具体类型，再捕获 RequestError，不用 TimeoutException、NetworkError 或 RequestError 的基类捕获扩大重试范围。失败原因直接使用 str(exc) 的非空白说明，空说明才使用实际异常类名；经 request_failure(error_message) 封装，不生成内部错误码、异常分类字段或文案映射。未预期程序异常是批次错误，不能泛化成 AI 失败。异常继承与含义依据 [HTTPX 异常文档](https://www.python-httpx.org/exceptions/)。

## 7. 程序内重试

每帖开始时内存 request_count=0。每次调用 client.post 前加 1，网络故障和 HTTP 失败共用该计数，不按错误类型分别计算预算。先按实际 HTTP 状态或当前捕获的异常类型检查下述停止条件，命中则设置共享停止信号、发布该帖最终失败且不重试；没有停止条件且 ParsedResponse.success=true 时立即结束。其余失败仅在满足下列重试条件且 request_count<max_attempts 时继续，其他情况返回最后失败。每次重试真正起发前再次检查共享停止信号。

允许自动重试的范围只有两项：上节明确列出的六种网络传输异常，以及 500<=http_status<=599 的全部 5xx。5xx 判断不因响应 body 非 JSON、缺少错误消息或包含正常 choices 而改变；包括 501、505 在内的 5xx 也遵守同一有限预算，不另建厂商状态码映射。其他非 2xx 立即停止整个 worker，包含 HTTP 400、401、403、408、422、429 和重定向响应；429 即使有 Retry-After 也不等待或重试。

若本次返回 5xx 且 request_count 已达到 max_attempts，立即停止整个 worker，并发布该帖最后 5xx 的最终失败，交由用户排查；不能保存 -1 后继续让整批任务逐帖消耗预算。若耗尽预算时最后一次是允许重试的网络异常，则仅返回该帖最终失败，其他作业继续。依据最后一次实际结果判断，不因为中间曾出现 5xx 就增加历史错误状态。

2xx 解析或结构失败、明确 error、拒答、截断、空正文以及 TaskRenderError 不自动重试，只终结该帖；其他非停止型 RequestError 同样只终结该帖。判断直接放在异常处理与 HTTP 响应分支，不向 ParsedResponse 增加 retryable、错误码或失败类型字段，不解析 error_message 或厂商 code/type 来调整重试与停止。下一次启动仍将读取范围内全部 -1 重置为 0，重新获得本次预算。

准备重试的第 n 次失败后，上界 u=min(backoff_max_seconds, backoff_base_seconds × 2^(n-1))，随机等待 [0,u]；达到上限后直接使用上限避免溢出。5xx 的有效 Retry-After 更晚时遵守它。等待使用异步睡眠和单调时钟，不阻塞事件循环；全局停止信号出现后，不再等待重试或发下一次请求。

默认 max_attempts=3，包括首次。第 1 次可重试失败等 0～1 秒，第 2 次等 0～2 秒，5xx 的更晚 Retry-After 除外；第 3 次失败结束，中间始终保持数据库 9。第 2 次成功只保存第 2 次成功结果，全部失败只保存最后失败与 -1。

例如 503→500→200 且正文有效，只保存最后成功结果并继续；503→503→503，保存最后失败并停止整个 worker；503→400，在第 2 次立即停止，不发第 3 次；503→ReadTimeout→503 共用三次预算，最后仍为 5xx 时停止。三次 ConnectError，或 503→ReadTimeout→ReadTimeout，则只保存该帖最后网络失败，不停止其他任务。次数按实际尝试累加，不能为网络错误和 5xx 各发三次。

次数、临时失败、退避和 Retry-After 均只存在于当前进程，不保存数据库、不从旧结果列恢复。崩溃后下一次启动重新计数。每个作业覆盖全部请求及重试等待，等待期间占一个作业名额；这是简化调度的代价，大量退避可能降低吞吐。

## 8. 全局限速与服务端等待

requests_per_second=0 时无固定间隔，大于 0 时全部实际请求及重试共用限速器，起发至少间隔 1/rps 秒；空闲不累计额度，请求执行不持有限速锁。

准备重试的 5xx 中，有效 Retry-After 更新进程内全局暂停，截止取既有暂停与本次服务端要求中更晚者，不能被后来的短等待缩短；已在途请求继续。支持非负秒数和 HTTP 日期，HTTP 日期按当前 UTC 时间换算为非负等待，再用单调时钟等待；不合法值忽略，不以本地退避上限截短。等待结束重新检查暂停和停止信号，状态仍为 9。预算已耗尽的 5xx 直接停止，不建立恢复等待；429 也直接停止，不设置服务端暂停。

例如 rps=5，相邻起发至少间隔 0.2 秒；收到可重试的 HTTP 503、Retry-After=10 后，后续所有起发至少遵守该暂停；10 秒内若其他在途请求返回 429，立即停止而非暂停后继续。不把暂停截止写入任务结果用于下次恢复。

## 9. 协调、缓冲与最终保存

每轮先检查停止/批次错误，命中时禁止提交新作业并进入收尾；已有最终结果仍按容量规则收取并尽力保存。正常运行时先检查当前缓冲的保存条件，需保存则先写回；再逐条收取完成消息，每条加入后重新检查保存条件，需保存则先写回再取下一条。最后在空余作业名额内选取状态 0，由任务模块计算本轮摘要并以两列 status=9/config_hash 共同更新，确认后才提交；输入快照在网络线程构造请求；每条消息保留原 TaskKey，主线程以该键定位当前分段 DataFrame 行。

选取 0 前、写入 9 前及每个作业提交前再次检查共享停止信号。若同步 cli 正在写入 9 时收到停止，不能强制撤销该写入；确认后不再提交对应作业，这些行保留 9，下次启动恢复。不以“停止新起发”承诺撤销已经开始的 cli 或远端操作。

收取消息后释放 submitted；正常最终响应进入结果缓冲，active_keys 保留直到任务模块确认最终保存。临时失败不会产生 CompletionMessage，不回填数据库 -1，也不生成重新入队事件。

result_buffer_size 是主线程未确认最终结果数的硬上限。收取下一条完成消息前必须保证缓冲仍有容量；缓冲满时先保存，保存未确认前既不取下一条消息，也不补充新作业，尚未收取的消息留在有界完成队列。每条消息加入缓冲后立即判断 batch_size、容量和时间阈值，不能先将队列整体取完再判断。更新重试或核对期间暂停收取，不丢弃结果；更新最终失败则走存储故障停止路径。

网络在途及完成队列共同不超过 concurrency，额外驻留最多约 result_buffer_size+concurrency 个结果；本次读取范围的 DataFrame 不计入该上限。按日期减少读取行数用于控制这部分内存，不先全量读取再过滤。例如 batch_size=result_buffer_size=200，缓冲已有 190 条、完成队列还有 20 条，只先取 10 条，保存并确认这 200 条后再取余下 10 条；保存抛错期间余下消息仍在队列，不让缓冲变为 210 条。

达到 batch_size、首条缓冲驻留达到 flush_interval_seconds、既没有其他在途作业也没有立即可提交任务、正常结束或收尾时提交。每批 df1 只包含原读取行的 date/id 索引及 status、ai_response_content、reasoning_content、usage_json、response_created、error_message 六列；逐行填入 1/-1 和最新结果，通过一次 update 共同保存，成功清空旧错误，无响应失败清空旧正文/推理/用量/接口时间；不设置结果阶段、终态阶段两个回调。

当前月份结束条件见月份切换约束，本段已保存的 -1 不阻止进入下一月，也不在循环中重置。等待重试的作业仍在 submitted 中，必须等其本次最终结果，不能让它跨月继续。整个 worker 只有所有分段完成后才正常退出。无立即工作时 Queue.get 超时不超过 0.25 秒，避免忙等。

## 10. worker 停止与异常收尾

用户停止处理的唯一方式是停止整个 worker 程序。没有按帖子 ID 主动取消的入口、独立取消命令、数据库取消标记或远端取消请求；也不依据 9 的持续时间主动终止任务。

直接触发整个 worker 停止的条件为：收到不属于 2xx 或 5xx 的 HTTP 响应；本帖尝试预算耗尽后仍返回 5xx；或实际捕获 InvalidURL、UnsupportedProtocol、LocalProtocolError、RemoteProtocolError、ProxyError、PoolTimeout。前一项覆盖 400、401、403、404、405、408、415、422、429 等全部 4xx 和重定向等非成功响应；HTTP 408 不与本地连接或读写超时混为一类。连接池等待、协议和请求配置问题须人工排查，不通过猜测消息关键词扩大网络重试。

网络作业发现上述状态或异常后立即设置共享停止信号，无需先生成共同配置错误码；取得具体失败原因后发布一次该帖最终失败消息，禁止新 HTTP 起发及重试。主线程禁止继续选择 0 和登记 9；已完成结果及触发错误的任务保存为 1/-1，未取得最终响应的已认领任务保留 9，未认领任务保持 0，收尾后抛 BatchRunError，不输出全部处理完成。

不以失败比例、消息关键词或厂商错误码增加停止规则。同为 HTTP 400，无论消息是“模型不存在”还是“输入超过长度限制”，均保存该帖 -1 并停止整个 worker，等待用户排查；HTTP 429 直接停止，供用户调整 RPM、并发或配额，不能自动等待 Retry-After 后恢复。5xx 预算耗尽后停止，供用户排查网关或上游服务。HTTP 2xx 的解析、结构或明确 error 失败、拒答、截断、空正文、任务渲染失败、其他非停止型 RequestError，以及预算耗尽的可重试网络异常，仅终结该帖，不停止其他任务。修正后由用户再次启动；若提示词或 payload 改变，仍遵守新配置使用新任务表的约定。

任务保存异常按任务模块使用当前分段的原 start_time/end_time 读回核对，不读整个全年范围；仍失败则停止整个 worker 的新请求及后续月，保留未确认列更新，收尾后抛 BatchPersistenceError。不能因保存失败重启该帖 AI 请求。

KeyboardInterrupt、未预期批次异常及上述停止路径统一先停止提交，再对当前程序持有的真实请求 Task 执行 cancel，gather(return_exceptions=true) 等待收尾，关闭客户端与事件循环，主线程 join。这只是整个 worker 停止时的内部资源清理，不是用户按任务取消功能。

收尾时按同一容量规则逐条收取已发布的完成消息，并在存储仍可用时保存最终响应，包括触发上述停止条件的最终失败消息；不能因为先看到停止信号就跳过已发布的结果。停止消息只释放网络作业；没有最终响应的任务保留 9，不伪造 AI 失败或写入 -1，下次在读取范围内启动时重置为 0。强制结束进程可能来不及保存或清理，已保存的 9 同样按下次启动规则恢复。

### 异常日志（本次已确认简化）

目的与范围：直接显示程序提供的异常和原因，让 Python 标准日志完成异常链及调用栈输出。日志不计算任务状态、未确认结果数量或保存阶段，也不据此拼接提示。

总体顺序：启动或运行出现异常 → 在当前 except 中记录异常 → 按原流程停止请求并尝试保存已完成结果 → 保留原有未确认数据 → 记录“worker 收尾结束” → 按原方式抛出异常。

启动校验失败、普通运行异常停止及收尾保存失败，分别直接调用 logger.exception，使用“worker 启动校验失败；尚未读取或更新任务”“worker 异常停止，开始收尾”“异常收尾时结果保存未确认”这些固定上下文。不自行遍历 cause/context，不分类异常，不为日志维护分段变量，不读取或遍历任务表、缓冲或队列。用户中断沿用原 WARNING 提示。

logger.exception 在 ERROR 级别输出当前异常类型、原始消息、调用栈及标准异常链；空消息沿用 Python 的异常类型显示，不生成自定义原因。比如 BatchPersistenceError 的原因是 TaskValidationError 时，标准日志会打印两者及具体消息；无需专门提取或猜测根因。

原有停止网络、收取和保存已有结果、跳过无法继续保存的条件、未确认数据属性及异常传播关系不变。原有收尾分支走到结束时，只在 INFO 级别输出“worker 收尾结束”，包括收尾保存失败分支；该句只说明收尾流程结束，不宣称全部任务处理完成或所有结果已保存。

此前日志简化已删除 _log_exception、_log_shutdown、仅用于诊断的 current_segment 和仅用于日志识别列的导入，并删除依赖这些统计报告的断言；保存、状态恢复、部分确认、请求次数、资源释放和未确认数据保留等有效回归继续保留。本次 cli 接口简化沿用该标准异常日志行为。

停止消息只释放网络作业，不生成模型结果。收尾仍每作业一条消息，不发送可能阻塞的结束标记，不等待无消费者的 queue.join。cli 长时间阻塞不能由 Python 安全强制中断，真实接入须使用其自身超时。

停止本地程序不保证服务端撤销已收到或已执行的请求，本项目不提供远端取消。

## 11. 输出与接入

RunSummary 统计各分段实际读取与确认的任务，提供 total、already_succeeded、new_succeeded、new_failed、pending、processing、http_attempts_started、elapsed_seconds。正常返回时为全部分段对应计数的总和，五种任务状态计数满足 total=already_succeeded+new_succeeded+new_failed+pending+processing；elapsed_seconds 是整个 worker 的运行时间，不能只保留最后一月统计。HTTP 起发数包括内存重试，仅用于本次统计，不入数据库。异常时未进入月份的状态未知，不把它们推算为 0 或宣称总范围已处理完。

每月可输出当前分段边界及本段成功/失败计数，空月只说明本段无待处理任务。所有分段完成后才输出“本次日期范围内的任务全部处理完了：成功 X，失败 Y”，X/Y 为所有分段本次新确认数量；所有分段均无 0 时也须读完全部分段后才给出总范围完成提示。无界单次读取沿用本次读取范围提示。范围外状态未知；错误或强制中断不能输出处理完成。日志不打印正文、payload、认证头或原始响应。

worker 由 main.py 或已有应用直接调用 run_worker(cli, task_path, config_path, start_time=None, end_time=None)。cli 和 task_path 显式传入所有 TaskStore；移除 integration/use_cli.py、run_existing_tasks 和 TaskCallbacks，不提供旧参数签名或旧转发函数的兼容层。核心包继续导出 run_worker，移除 TaskCallbacks 的导入及 __all__ 项；其余既有包导出保留。

调用方从任务配置取得 task_path 与总日期范围，先准备日志，再创建或提供现有 cli；运行模块不调用 get_client、不导入 xdata 创建连接、不读取 source_path，也不将整个 settings 字典传入 TaskStore。日期分段和参数解析仍由本模块负责，实际同步读写由任务模块直接调用 cli 完成。调用示例为：

~~~python
summary = run_worker(
    cli,
    task_path,
    config_path,
    start_time=scope_start_time,
    end_time=scope_end_time,
)
~~~

例如总范围 [2021-01-15, 2021-03-10)，三个 TaskStore 均接收同一个 cli 和 task_path，但分别取得 [2021-01-15, 2021-02-01)、[2021-02-01, 2021-03-01)、[2021-03-01, 2021-03-10) 的范围；不会将总范围固定成读取闭包。无界范围由任务模块使用 cli.read(task_path)，有界读取由任务模块原样传递收到的当前段 YYYY-MM-DD 字符串，读取范围不扩大，具体调用见任务规格。原 date/id 类型、时区和精度不重建。任务模块按当前段范围校验返回记录，total 与各状态统计仍对应该分段的实际任务。

worker 更新直接使用 cli.update_by_index(task_path, df1)：重置仅 status，认领为 status/config_hash 两列，最终保存为六个终态列；df1 始终保留原 date/id 索引，未提交列保持原值。客户端正常返回与异常后的核对语义由任务规格维护，本模块不再包装读写函数。
