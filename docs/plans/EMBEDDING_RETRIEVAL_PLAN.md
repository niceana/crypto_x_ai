历史实施日期：2026-10-16。以下保留首版只编码 event、本地持久缓存，以及无历史直接 new、有历史交第二轮的方案与验证经过，不再作为当前实施依据。

## 1. 已确定的方向

用户已有部署的 `bge-m3` Embedding 服务，可以通过 OpenAI 兼容的 `embeddings.create(model="bge-m3", input=texts)` 调用。用户示例每批发送 8 段文本，并按响应的 `index` 恢复输入顺序；8 是示例批量大小，不视为服务硬上限。

本次选择只使用 Embedding 计算相似度，取消此前建议的关键词检索、BM25 和多路排名融合。向量相似度用于选择第二轮候选，是否属于同一事件、是否有新增事实仍由第二轮 AI 判断。关键词匹配与向量匹配的信号可能重叠，但纯向量对编号、版本及否定等差异的实际辨别能力仍须样本验证。

## 2. 已确认的输入与保存选择

| 选择 | 已确认规则 | 对结果或使用方式的影响 |
| --- | --- | --- |
| 输入文本 | 当前及历史记录都只编码各自完整的第一轮 `event`。 | 历次 update 的 event 都参与比较，保留中途进展；不把 event 与 new_information 中重复的事实再拼接。若改用 event + new_information，历史表示会随第二轮输出变化，须采用独立缓存标识。 |
| 向量缓存 | 本地持久保存已验证向量，重启后复用。 | 减少重新启动后的重复接口调用；仅用内存则退出后丢弃，下次重新生成所需向量。两者都不持久保存每次检索的候选与得分。 |
| 自动判新 | 前史检查通过且 180 天窗口内确实没有历史记录时直接 new；有历史则最多选 10 组交第二轮。 | 首版不因分数低而自动 new。空窗口仅表示当前检索范围没有历史，不代表全网首次或 180 天以前没有相关披露。另一种选择是空窗口也交第二轮。 |

用户已逐项确认上述三个建议。向量缓存采用 Python 自带 SQLite，按成功批次提交，解决重启复用与中断后增量保存，不增加第三方依赖或向量数据库。

## 3. 实际处理顺序

1. 沿用当前第二轮启动、状态恢复和前史检查。没有待处理任务时，不要求配置 Embedding，不请求服务。
2. 从 `event_config.embedding_config_path` 指向的独立配置读取接口地址、模型、批量大小、超时、请求重试和缓存位置。密钥使用 `${EMBEDDING_API_KEY}`，来自进程环境或配置目录的 `.env`；不写入代码或日志。base_url 填服务的基础地址，程序在其后追加 `/embeddings`，不自动补 `/v1`。
3. 只以 event 生成输入。优先查询缓存，将缺失且内容相同的文本去重，按批量大小请求服务。默认每批 8 条，允许配置修改。
4. 按本批 `index` 还原向量顺序。检查返回数量与输入一致、index 恰好覆盖 `0..批长-1`、没有重复或缺失、所有向量非空且维度一致、值均为有限数值、向量长度非零。仅排序不能发现缺失或重复 index。
5. 将向量归一化为单位长度，用 NumPy 点积计算余弦相似度。维度按服务实际响应检查，不硬编码模型维度，不假定服务已经归一化。
6. 针对每条当前记录，只比较 `common.event_context.EventHistory.get_searchable_records` 返回的同资产历史，即 `[当前时间-180天, 当前时间)` 且第二轮已经完成的披露。
7. 对全部合格历史披露评分，按 event_id 归并，每组取最高相似度作为组分数。按组分数降序选择最多 10 个不同事件组，并列按 event_id 升序固定顺序。分数不累加，重复披露不会靠次数提高组分数。
8. 沿用现有历史回查，为入选组补齐当前时点之前的起点与 update，即使起点位于窗口之外。评分器继续返回现有 `RetrievalSelection`，不改变关联 AI 的输入结构。
9. 第二轮结果保存成功后，才按当前同币时间推进规则加入历史。同刻披露继续共享此前历史，不互相成为候选。

开始关联前批量准备本轮所需固定 event 的向量，包括将来可能成为历史的待处理披露。提前编码后续披露本身不授予历史资格；每次比较仍只使用第 6 步的合格记录，不使用未来关系、未来摘要或全量语料统计。

## 4. 分组示例

| 历史披露 | event_id | 与当前披露的相似度（示意值） |
| --- | --- | --- |
| 提出回购计划 | A | 0.72 |
| 回购开始执行 | A | 0.88 |
| 再次介绍同一回购 | A | 0.81 |
| 另一项独立事项 | B | 0.84 |

A 的组分数为 0.88，B 为 0.84，候选顺序为 A、B。不能先截取前 10 条披露再去重，也不把 A 的三个分数加起来。上述数值仅用于解释排序，不是阈值或准确率承诺。

## 5. 缓存、失败与恢复

缓存标识为包含服务地址、模型、model_version、编码方式、表示版本及实际 event 文本的 SHA-256。SQLite 的 vectors 表只保存缓存键、维度及归一化后的 float32 向量，不保存事件正文。服务端用同名模型替换权重时，需人工更新 model_version，防止旧向量混用。相同文本针对多个资产展开时可复用向量，资产资格仍由检索历史单独筛选。缓存结构、长度、数值或维度不合法时停止提示，不静默修复。

Embedding 每批请求默认最多尝试 3 次，包含首次，仅网络传输故障和 5xx 重试，按 1 秒起、30 秒封顶的指数退避等待；参数可配置。429、其他非成功 HTTP 状态、无效响应或预算耗尽停止本轮，不返回空候选、不自动 new。该预算独立于第二轮关联 AI。直接使用默认传输不重试的 HTTPX，不叠加 SDK 重试。

向量在开始认领前按需批量准备，缓存与 HTTP 客户端在准备结束或异常时关闭；因此 Embedding 失败不会留下本次新认领的业务记录，也不会阻塞已经起发的关联 AI。只准备本范围待处理记录及至少一个当前时点能检索到的已完成历史文本。准备成功后，关联运行中的评分只读取内存向量。

已经成功并通过完整校验的批次可缓存；失败批次不保存错位或部分向量。中断后的业务状态仍按现有第二轮规则恢复，已经完成的关联不重做。仅有向量缓存不表示某披露已经完成关联。沿用现有 config_hash 的范围；其当前不覆盖检索模型或参数，继续运行时须保持检索输入及模型版本固定。

## 6. 实施范围与验证

评分已实现于 `round2/embedding.py`，继续使用 `retrieve(current, searchable) -> RetrievalSelection` 的业务接口。选择优先级为应用注入的 retriever、自定义 `模块:函数`、embedding_config_path；没有任何检索配置才明确报错。`common.config.load_embedding_config` 加载独立配置，runner 在认领前批量准备向量。复用已有 HTTPX、NumPy 和标准库 SQLite，不新增安装依赖。默认配置见 `configs/embedding_config.yaml`，缓存位于项目 `.cache/embeddings.sqlite3`。

新增 14 项模拟测试已经通过，包括批长 8 及末批不足 8、响应乱序及错误 index、非有限值和零向量、模型或文本变更后的缓存隔离、按组取最高分及超过 10 组、180 天边界和同刻排除、窗口外起点回查、失败不判新及重启复用。Python 3.8.10 下完整 249 项回归通过。未调用真实服务；仍需部署者配置接口做小样联调，并用真实关联样本另测 Recall@10，不以模拟流程测试代替召回质量验收。

首版实施时 `common.store.read_stage_hashes` 尚为占位，后续已按用户确认的全表单列 CLI 接入，不再是当前待开发接口。真实服务配置及正式提示词仍待补齐，当前启动条件见 [接入待办](../IMPLEMENTATION_ISSUES.md#运行前必须补齐)。

接口形状参考 [OpenAI 官方 Embeddings 文档](https://developers.openai.com/api/reference/python/resources/embeddings/methods/create)；bge-m3 的可用参数、长度上限和服务行为以用户部署为准。
