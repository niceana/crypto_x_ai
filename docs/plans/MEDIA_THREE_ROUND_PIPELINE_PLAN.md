# 媒体账号帖子三轮 AI 处理实施计划

日期：2026-11-09。状态：代码和专用配置已实现，Python 3.8 下完整 658 项离线测试通过（新增媒体相关 15 项）；正式运行说明见 [媒体处理说明](../MEDIA_PIPELINE.md)。真实数据表及 AI 请求尚未执行，需先填写媒体路径、日期和接口配置。

## 1. 选定方案与范围

采用现有三轮处理思路：第一轮提取新闻或事件及影响对象，第二轮按同对象历史归组，第三轮分析经济影响。

媒体数据采用两张独立处理表：第一轮一张，第二、三轮共用另一张，与官方账号现有布局一致。这两张媒体表均独立于官方账号表。原始媒体帖子来源表通过 `source_path` 配置，作为只读输入。

第一轮对外配置名统一为 `round1_result_path`；第二、三轮保留 `round2_result_path`、`round3_result_path` 两个阶段路径名，但两者必须配置成同一张事件表。这样保留统一命名，同时复用现有共表处理逻辑。

确定的规则：

- 三轮分别使用媒体专用提示词及 AI 配置。
- AI 请求构造、响应解析、并发、限流、重试、存储重试、进度、进程锁等继续复用。
- 第一轮不发送账号关联资产 `account_tickers`，仍发送 `user_name` 和 `text`。
- 对象只能是加密资产代码、行业或宏观标记；统一去首尾空白并转大写，存储编码为具体币种代码、`INDUSTRY`、`MACRO`。
- 第二轮以“事件 × 对象”为一条记录，按对象独立推进，回看一个日历月，发送窗口内全部候选事件组。
- 不计算 Embedding，不调用向量服务，不配置相似度阈值，不沿用向量模式的 Top 10 候选上限。
- 第二轮 AI 可返回 `new/update/repeat/uncertain`；沿用现有逻辑，将 uncertain 按 new 建档，业务列只保存 new/update/repeat，AI 原始回答仍保留 uncertain。第三轮对 new/update 调用 AI，对 repeat 继承历史有效分析。
- 本次实施范围为提取、归组、影响分析及独立存储。交易权重、风控系数和做空规则另行研究。

```mermaid
flowchart LR
    S[媒体原帖来源表] -->|初始化| R1[媒体第一轮表：帖子提取]
    R1 -->|成功帖按事件 × 对象展开| E[媒体事件去重分析表]
    E -->|更新第二轮列| R2[AI：事件归组]
    R2 --> E
    E -->|更新第三轮列| R3[AI：影响分析或继承]
    R3 --> E
```

## 2. 来源表与两张独立处理表

表路径由配置填写。以下仅表示用途，不是真实数据库路径。

| 配置项 | 表用途 | 一行的粒度 | 索引 |
| --- | --- | --- | --- |
| `source_path` | 已有媒体原始帖子表，只读 | 一条原帖 | `(date, id)` |
| `round1_result_path` | 媒体第一轮任务及提取结果表 | 一条原帖 | `(date, id)` |
| `round2_result_path` | 媒体事件去重分析表，第二轮写归组列 | 单帖中的一个事件 × 一个对象 | `(date, record_id)` |
| `round3_result_path` | 与 round2_result_path 为同一张表，第三轮写影响分析列 | 与第二轮相同 | `(date, record_id)` |

完整表路径配置示例：

```yaml
source_path: "填写媒体原始帖子表路径"
round1_result_path: "填写媒体第一轮结果表路径"
round2_result_path: "填写媒体事件去重分析表路径"
round3_result_path: "填写媒体事件去重分析表路径"
```

校验要求：source_path、round1_result_path、共用事件表路径三者互不相同；round2_result_path 与 round3_result_path 相同。媒体目标路径独立于官方账号已有表，不迁移或覆盖官方结果。

### 2.1 第一轮表

沿用现有第一轮九个普通列：

`config_hash`、`text`、`user_name`、`status`、`ai_response_content`、`reasoning_content`、`usage_json`、`response_created`、`error_message`。

初始化时复制原帖输入及索引，`status="0"`，其他结果字段为空。日期使用原帖子完整发布时间，AI 处理期间不修改原文、账号和时间。

### 2.2 第二、三轮共用事件去重分析表

优先沿用现有事件表的 14 列结构，分阶段限制可修改字段：

| 列 | 用途 |
| --- | --- |
| `event` | 第一轮事件描述，导入后固定 |
| `asset` | 单个规范对象编码，导入后固定 |
| `source_post_id` | 原帖 ID，导入后固定 |
| `event_id` | 当前归属的事件组 ID |
| `event_relation` | `new/update/repeat`；AI 返回 uncertain 时按 new 保存 |
| `new_information` | update 的变化过程；其他关系为空字符串 |
| `round2_ai_response` | 第二轮原始回答与调用信息 |
| `round2_status` | 第二轮执行状态 |
| `round2_config_hash` | 第二轮 AI 配置摘要 |
| `round3_ai_response` | 第三轮原始回答与调用信息，repeat 时为继承结果 |
| `round3_status` | 第三轮执行状态 |
| `round3_config_hash` | 第三轮 AI 配置摘要 |
| `error_message` | 最近一次最终失败信息，沿用现有两轮共用口径 |
| `embedding` | 为复用现有表结构保留的空字符串列，媒体分支不生成或加载向量 |

`record_id` 沿用 `source_post_id:event_index:asset`，事件序号从 0 开始。对象先规范化、去重，再生成 ID。

保留空 embedding 列是表结构兼容安排，不代表执行 Embedding 阶段。媒体模式的候选选择直接读取同对象历史。

### 2.3 两轮字段权限

event、asset、source_post_id 由第一轮展开导入后固定。

- 第二轮写 event_id、event_relation、new_information、round2_ai_response、round2_status、round2_config_hash 和错误；非 repeat 成功后将第三轮状态置为待处理。
- 第三轮写 round3_ai_response、round3_status、round3_config_hash 和错误，不修改原事件、对象或第二轮归组结果。
- 第三轮直接读取共用事件表中已经完成归组的记录，不建立第二轮到第三轮的复制表或导入步骤。

三轮执行状态继续使用字符串：`"0"` 待处理、`"9"` 已认领、`"1"` 完成、`"-1"` 失败。第二、三轮的状态列和回答列分别保存。AI 的 uncertain 不是执行失败，业务保存时转换为 new。

## 3. 建表、写入和阶段交接

### 3.1 首次创建

两张目标表均先构造并校验初始化 DataFrame，创建新目标时执行：

```python
cli.register(target_path, "timeseries", "")
cli.write(target_path, initial_df)
```

第一轮初始化沿用现有“指定新目标路径后 register/write”的入口，不把它描述为已经通过 DataNotFound 预读确认缺表。事件表的自动/独立导入则会先 read_meta/read 目标，在读取异常分支使用仓库现有的 DataNotFound 兼容规则。

用户于 2026-11-09 确认 DataNotFound 是真实 SDK 的异常定义。本方案据此沿用现有 `initialization.event_records._is_data_not_found()` 兼容判断：异常类型名恰好为 DataNotFound，或异常信息包含完整 DataNotFound 标记时，进入目标缺表分支。

该异常定义已由用户确认，不再列为未决验证项。连接、权限、超时等错误不解释为缺表。源帖子表不存在时直接报错，不为来源注册空表。

上述判断发生在读目标表或查元数据时，不是捕获写库异常后自动建表，也不说明 SDK 写库时绝不会出现同名异常。写库失败走已有存储错误处理，不据此重新 register。

注册与写入分开处理：注册失败不写入；事件表写入和 AI 结果保存按各自已有预算重试，不重复注册或重新请求 AI。第一轮完整初始化沿用现有一次 register/write 规则，不把它扩展描述成可无条件反复执行；注册成功、首次写入失败时要先辨明目标实际状态，再按对应恢复流程处理。

第一轮初始化继续完整读取来源并一次性建立任务表，不加载 AI 配置、不调用 AI。它是新任务表初始化入口，不用来重置已运行的第一轮表。

### 3.2 已有表续建与本轮更新

- 自动导入与独立导入保持现有校验边界，不概括为每次自动导入都完整比对所有固定输入。
- 新增下游任务沿用 `cli.update_by_index()`，仅追加缺失记录。
- 本轮认领、成功或失败结果沿用 `cli.update_by_column()`，只写本轮允许修改的列。
- 自动导入含历史成功帖时按已有索引补缺，已存在索引直接跳过，不逐项比较 event 等业务列；它依赖已成功第一轮内容固定这一前提。
- 独立导入提供严格固定输入核对：相同索引的 event、asset 或 source_post_id 冲突则停止，不用改变后的第一轮提取覆盖已经归组、分析过的事件输入。媒体首版沿用这种入口区分，不额外加入每次自动导入的全量内容审计。
- 严格核对先完整展开本次配置范围内的第一轮结果，而非不加日期区分地比较所有历史：共同索引逐条比对上述三个固定字段；目标缺失索引作为新增批次；目标在本范围内多出源展开结果没有的记录则停止。已有表的新增批次通过 update_by_index 写入，没有新增记录时不写入；首次缺表仍 register/write。
- 正常写入 round2_ai_response、round3_ai_response、状态和错误等本轮结果不属于上述输入冲突。
- 以 CLI 正常返回为写入确认，随后更新内存工作表和第二轮历史；同一进程中的存储重试不重新调用 AI，跨进程的边界见 3.5。
- 所有新表的首次结构写入使用 `cli.write()`；不将首次建表与续跑追加混为同一种操作。

### 3.3 第一轮到第二轮

媒体第一轮正常结束后，沿用现有自动导入思路，将本次日期范围内的成功帖展开成事件表任务；目标读取被确认符合缺表识别时 register/write，已存在时补缺。

自动导入的数据来自本次运行内存中的两份成功帖：本次新处理成功的帖子，以及本次加载时已经成功、跳过 AI 的帖子。不会因此重新读取整张第一轮表。日期范围两端为空时，处理范围才是第一轮全表；配置了日期时只展开该范围成功帖。

有历史成功帖时，现有自动导入可能完整读取目标事件表来比较索引；纯新批次只查目标元数据后追加。读取整张目标表不等于重写整张表，实际只提交本批缺失记录。补导完成不会覆盖旧归组、旧影响分析或其状态。

独立导入入口是另一条路径：当前默认先完整读取第一轮表，再按配置日期在内存筛选；启用 successful_only 且有日期时可按范围读取。读取范围、参与展开的范围、真正新增写入的记录分别统计，不能混为一谈。

自动导入不比较已有业务正文是现有代码的性能与职责取舍，不是技术限制：纯新成功批次可仅查目标元数据后直接追加，不读取全部旧事件；旧成功帖的正常补漏则依赖第一轮成功内容和稳定 ID，已有索引直接保留。自动路径仍校验本批源输出、展开格式和日期范围，恢复路径还检查索引及跨日期 ID 冲突，不能概括为“完全不核对”。

代价是：如果人为改过第一轮已成功回答、但展开索引没有变化，自动导入会保留已有事件，不能发现正文差异；应通过独立导入或现有审计入口核对。可以增加自动路径的正文比较，但这会改变现有行为，首版不因解释现有机制而自动增加该检查。对已经读取的历史目标记录增加比较本身不要求重调 AI。

第一轮单帖失败不妨碍其他成功帖保存及导入；第二轮启动沿用指定范围第一轮完成检查。现有状态检查本身不证明事件导入覆盖，交接须以自动导入成功或独立补导/审计结果为准。导入失败后可重跑第一轮入口，复用已保存回答补导，不重复调用成功帖 AI。

`events=[]` 正常保存为成功但不展开记录。`tickers=[]` 的事件保留在第一轮原始回答中，统计为对象未确定，不强造对象或生成无目标的第二轮任务。

### 3.4 共表后的第三轮启动

第三轮直接从共用事件表读取本次范围内 `round2_status="1"` 的记录，业务关系为 new/update/repeat；原 AI uncertain 记录已经按 new 保存。不执行 register/write 建第三张表，也不复制一份第二轮输入。

未完成第二轮的记录不能进入第三轮分析，日志单独汇总；后续补跑第二轮后再次运行第三轮即可补齐。

继续沿用现有“要求整个范围第二轮完成 / 跳过未完成记录”的可配置规则。第三轮只更新自己的结果列，不修改第二轮状态。

### 3.5 内存缓冲、写库重试与历史推进

内存中有三类不同的数据：待写 AI 结果的列表或队列、当前分段的 DataFrame 工作表、第二轮用于组织下一次请求的历史索引。

顺序为：AI 返回并通过校验 → 结果进入待写缓冲 → 构造本批数据库更新 → 调用 CLI 写入 → 正常返回后更新内存 DataFrame → 当前时点全部保存后把成功记录加入历史索引 → 推进同对象下一时点。

写库失败时，同一进程继续持有这批已返回的 AI 结果，用相同记录键和 AI 正文再次尝试写库；不是重新读取原帖再请求 AI。存储重试复用 `common.persistence.write_with_retry()`，每次向客户端传 DataFrame 副本；提交时间可按现有机制刷新，AI 回答不重算。

内存 DataFrame 的更新是普通 Python 赋值，历史索引通过现有准备线程接收已保存记录并加入列表、字典索引，不是修改 AI 的对话记忆。待写缓冲里的结果不能提前成为后续事件的历史。

存储重试预算耗尽时停止并保留当前进程可取得的待写结果。当前缓冲不落盘：若结果尚未成功入库就退出进程或重启机器，内存结果可能丢失，重新运行可能再次调用 AI。已有数据库成功结果仍按状态跳过。本计划复用现有进程内重试机制，不承诺未落库结果的跨进程零重复调用。

### 3.6 准备线程与其他线程

每轮独立启动一个进程，业务上主要有主线程、准备线程和网络线程。三轮不是同一进程中的三条线程；不同轮次的进程通过数据库状态衔接，不共享内存队列。

| 线程 | 负责的数据和工作 | 是否使用数据库客户端 |
| --- | --- | --- |
| 主线程 | 读取表、认领任务、收取完成结果、写库及重试、更新当前 DataFrame、调度下一时点 | 是，数据库调用和工作表更新集中在此 |
| 准备线程 | 请求模板渲染和编码；第二轮还组织候选历史并独占维护运行中的 EventHistory | 否，只接收固定输入副本和已保存记录 |
| 网络线程 | 独占 HTTP 客户端和异步事件循环，按并发限制发送请求、执行网络重试和输出校验、交出完成消息 | 否 |

```mermaid
flowchart LR
    M[主线程：数据库与工作表] -->|已认领的固定输入| P[准备线程：历史与请求组装]
    P -->|就绪请求队列| N[网络线程：并发 AI 请求]
    N -->|完成结果队列| M
    M -->|写库成功后的历史更新| P
```

网络线程用异步任务维持多个 HTTP 请求，并发 100 不表示新建 100 条业务线程。准备线程持续补充就绪请求；网络线程取走请求后唤醒准备线程。主线程写库时，已有就绪请求和在途请求仍可继续处理。

第二轮对同对象保持更强顺序：当前时点全部保存成功后，主线程把历史更新交给准备线程，再认领下一时点。准备线程优先消费历史更新，然后构造新请求，避免后一条事件使用尚未确认的归组结果。同刻事件共享此前历史；其他对象不必等待该对象完成。第一、三轮的独立任务仍可批量准备和并发发送。

## 4. 第一轮：媒体新闻与事件提取

### 4.1 输入与输出

输入沿用：

```json
{"user_name":"media_account","text":"原始帖子正文"}
```

输出继续使用现有字段名：

```json
{"events":[{"event":"新闻或事件的完整事实描述","tickers":["BTC"]}]}
```

一帖允许多个独立事件，每个事件有自己的对象列表。同一事实影响多个对象时保留一条 event，导入阶段再展开。

`tickers` 在媒体分支中实际表示影响对象编码，允许加密资产代码、`INDUSTRY` 和 `MACRO`，写入前统一转大写。保留字段名以减少协议改动，不新增事件类型、主体、状态或证据字段。

### 4.2 事件描述要求

描述应交代主体、动作及当前状态；原文有关键金额、比例、日期、条件或限制时保留。对报道、指控、风险警告和传闻，按原文保留报道者、引用来源、证据性质及确认程度。

允许多句话，完整性优先于强制一句话。不得把据称、推测、计划、否认或条件性事项改写成已经证实并完成的事实，不补造缺失信息。

### 4.3 内容筛选

- 提取与加密资产、加密行业或相关宏观环境有关的具体披露。
- 排除无具体信息的喊单、价格预测、普通观点、宣传、日常互动和单纯行情复述。
- 评论中包含具体事实时，只提取事实部分。
- 具有具体内容的风险报道、计划、公开政策表态、确认、否认、更正和恢复可以提取；是否已发生、是否重大不作为统一前置门槛。
- 第一轮不判断相对历史是否新增，也不判断一小时内是否存在价格预测力；分别交给第二轮和后续研究。

### 4.4 对象规范

全部对象沿用现有 `initialization.event_records.expand_first_round()` 的 strip/upper/列表去重规则，用户已确认统一大写，无需为行业、宏观标记增加小写例外。

- 程序只处理对象字符串的写法：所有对象去首尾空白并统一大写，包括 INDUSTRY、MACRO。
- 在同一事件的对象列表内按规范结果去重，保留首次出现的顺序，再生成 record_id；不跨帖子合并事件。
- 例如 `[" btc ", "BTC", "eth", "industry", "Macro", "ETH"]` 规范为 `["BTC", "ETH", "INDUSTRY", "MACRO"]`。
- 此处不再次调用 AI，不把项目或交易所名称映射成币种，不自动把不同代码或包装资产合并，例如 WBTC 与 BTC 继续保留为不同对象。字符串统一大写不等于已经证明它是有效币种；语义识别仍由提取规则和样本验收负责。
- 项目名、交易所名、国家、机构和非加密资产名称写进 event，不作为对象编码。
- `INDUSTRY` 表示加密行业层面，具体行业范围写在 event 中；`MACRO` 表示宏观消息对加密市场的影响层面。
- 两个预留对象不能充当无法识别币种的通用兜底，不能给每条新闻都附加。
- 无法可靠确定对象时允许空数组；不按媒体账号映射币种，不凭账号名补充币种。
- AI 负责语义识别，程序负责格式和规范编码校验；语义正确性通过人工样本验收。

## 5. 第二轮：同对象一个月全量历史归组

### 5.1 调度与候选

沿用按对象、按完整披露时间推进的方式：同对象下一时点等待当前时点全部保存确认；不同对象可并发；同刻事件共享严格此前历史。

当前时刻为 T 时，候选披露窗口为 `[T 向前一个日历月, T)`，包含下界、排除同刻及未来。月末边界继续复用 `common.time_rules`。

取窗口内同对象已经完成第二轮的记录，按 event_id 组织全部候选组。组是否入选由窗口内是否存在披露决定，不按组最初创建日期过滤。

每组提供窗口内最早可用披露及后续 update；普通 repeat 不重复塞入正文，仅剩 repeat 时仍保留可比较的最早可用事实。原 AI uncertain 已按 new 建档，直接沿用现有组起点规则。不会补入窗口外事实，new 只表示在本窗口未能确认匹配事项。

全量模式绕过 Embedding、相似度阈值、Top N 和最多 10 组限制。候选为空时第一版仍使用 `candidates=[]` 的固定输入调用 AI，不引入低分自动判新。

### 5.2 AI 协议

输入结构与现有第二轮一致；对象筛选及真实组 ID 留在程序中：

```json
{
  "current":{"published_at":"2026-11-09T12:00:00+08:00","event":"当前事件描述"},
  "candidates":[
    {"candidate_id":"E1","history":[{"published_at":"2026-11-08T12:00:00+08:00","event":"历史事件描述"}]}
  ]
}
```

输出恰好三个字段：

| event_relation | matched_candidate_id | new_information |
| --- | --- | --- |
| new | null | null |
| update | 本次候选编号 | 非空变化说明 |
| repeat | 本次候选编号 | null |
| uncertain | null | null |

先判断是否为同一具体事项，再比较所提供的全部组历史。相同主题、同一对象或措辞相似不足以认定同一事项；重复报道历史中已经出现的阶段应判 repeat。

update 包括新增事实、范围或数量变化、独立证据补充、明确确认、否认和更正。账号不同或转载同一原始来源不自动构成新证据。

变化说明必须写清必要的此前状态、当前新增或修正内容、变化后状态和关键条件，带有可独立理解的历史过程。旧事实只来自匹配组，新事实只来自当前 event。

### 5.3 uncertain 沿用现有转换逻辑

AI 正常输出 uncertain 时，沿用现有 save_relation_batch 行为：业务 event_relation 转换为 new，event_id 使用自身 record_id，new_information 保存为空；round2_ai_response 内的原始 AI 正文仍保留 uncertain，不改写原回答。

后续前史校验、组历史构建、续跑和第三轮均按普通 new 处理，无需增加 uncertain 组起点或临时组机制。第三轮自然会分析这类记录，不能把其原始归组不确定自动视为经济影响方向不确定。

不追溯改写已成功记录，不自动合并旧组。后续若发现重复建组，另行审计并确定重算范围。

### 5.4 容量与失败

记录每次候选组数、历史条数和输入大小，按模型及接口允许的输入空间预留输出容量。行业和宏观桶需单独检查繁忙时段。

输入超限明确保存准备失败并暂停该对象推进，不隐含截断、取最近若干组或改为摘要。若需要分批比较或历史摘要，作为后续显式方案调整。

沿用前史未完成检查、历史补录检查、配置摘要检查和保存后才推进历史的规则。普通失败暂停该对象，其他对象可继续。

## 6. 第三轮：共用事件表中的经济影响分析

new/update 调用 AI，包括已经由 uncertain 转换为 new 的记录；repeat 走历史结果继承。直接复用现有第三轮任务选择，不增加独立 uncertain 分支。

AI 输入沿用 `asset`、`event` 及可选的 `new_information`；仅 update 提供非空变化说明，不重新发送全部候选历史或原帖。

输出沿用五字段及现有枚举：

- `direction`：利好、利空、中性、不确定。
- `materiality`：高、中、低、不确定。
- `execution_stage`：未开始、执行中、已完成、不确定。
- `persistence`：短期、中期、长期、不确定。
- `materiality_reason`：简洁的判断依据及关键信息缺口。

媒体提示词移除“官方发布”和“目标必须是代币”的假设。具体资产分析对该资产的经济影响；INDUSTRY 分析对加密行业的影响；MACRO 分析宏观消息通过资金、流动性、风险环境等对加密市场的影响，不转成评价宏观经济本身的好坏。

始终分析当前完整 event，变化说明补充必要背景，不把历史事实当成本次新发生。保留通用经济原理推导与事件事实的区别，不补造项目专属机制或宏观市场预期。

persistence 继续表示经济机制的持续时间，不表示价格反应速度、建议持仓期或小时预测力。

repeat 从共用事件表查找同对象、同组、严格此前最近的有效第三轮响应并复制，查询不受第二轮一个月窗口限制。不存在有效来源则保存明确失败，不把空回答标为完成。复制的 usage、attempts 和时间不计作本条新增 AI 调用。

- `configs/media_event_processing_config.yaml`：round1_result_path、填写同一物理路径的 round2_result_path / round3_result_path、两轮 AI 配置、日期及一月回看。

媒体配置不引用 Embedding 配置，账号映射为空。密钥使用环境变量占位，不写入明文。AI 配置仍保留每轮独立并发、重试和超时设置。

已实现可选 round2_max_input_characters：正整数限制第二轮业务 JSON 字符数，超限记录准备失败且不发送 AI、不截断；null 不设置本地字符上限。它不含 system 提示词，也不等同 token 上限，应按实际模型配置。三轮提示词、数据路径、接口 URL、模型和密钥均有独立媒体配置，运行前需填写。

首版提供下列入口，名称在实现时保持统一：

```powershell
python -X utf8 -m entrypoints.initialize_media_tasks
python -X utf8 -m entrypoints.run_media_round1
python -X utf8 -m entrypoints.run_media_round2
python -X utf8 -m entrypoints.run_media_round3
```

第一轮入口完成后补导共用事件表；第二轮和第三轮分别更新这张表各自的列。另提供独立事件补导入口或可复用函数，使补导失败时复用已落库的第一轮回答重试，不重新调用这些已成功 AI。

每轮锁按“阶段 + 实际目标表路径”绑定。第二、三轮虽然共表，仍可分别持有本轮锁；导入写入另用共用事件表的导入锁，沿用已有锁机制。创建目标、追加任务和更新结果均在相应锁内完成，同阶段同表不能按不同日期重复启动。

每张表分别核对本轮 AI 配置摘要。现有 ai_config_hash 仅对 system/user 原始提示词模板和 api.payload（模型、temperature 等）计算摘要，不包括实际帖子、历史窗口、候选选择策略、对象规范化代码、日期范围、并发、重试、URL 或认证。

例如，提示词和模型不变，但回看从 1 个月改为 2 个月，第二轮的候选和判断可能改变，而现有 AI 摘要仍相同。程序也不会自动重做已经成功的记录：旧记录可能保留一月口径，新处理记录使用两月口径。这里的“处理版本”只是指区分这种结果生成口径，不要求首版新增完整版本管理系统或业务指纹列。

沿用当前处理规则：改变提示词或 payload 时由已有摘要检查处理；改变历史窗口、候选策略等摘要之外的语义规则时，如果要比较或重算历史，使用新的结果表路径，或另行明确需要重算的下游范围，不把改配置视为已经重新计算。仅调整第二轮窗口时，可保留原帖和第一轮结果，另建一张新的第二三轮共用事件表，重新展开、归组并分析，无需因此重新调用第一轮 AI。仅延长处理日期、调整并发或重试通常仍可沿用原表续跑，不因这些运行设置变化要求新建数据版本。

## 9. 实施顺序与验收

| 步骤 | 工作 | 验收点 |
| --- | --- | --- |
| 1 | 新配置、两张表契约、对象规范化和事件导入函数 | 两张媒体表分别 register/write；来源路径明确；第二三轮配置同一路径；沿用用户已确认的 DataNotFound 识别；已有表缺失记录用 update_by_index 追加 |
| 2 | 媒体第一轮提示词及接入 | 不发送 account_tickers；支持多事件、多对象、空事件及来源状态保留 |
| 3 | 第二轮全量候选、一月窗口、四态输出与三态入库 | 超过 10 组仍全部参与；对象隔离；同刻及未来排除；uncertain 按 new 建档而原始回答不变 |
| 4 | 第三轮共表执行与媒体对象分析 | new/update 调用 AI，包含原 uncertain 记录；update 带变化过程；repeat 继承有效来源 |
| 5 | 入口、锁、续跑、进度和错误处理 | 已落库成功任务可复用；同进程写库重试不重新调用模型；明确未落库结果在进程退出后的边界 |
| 6 | 自动验证和小批真实样本验收 | 官方流程回归通过；媒体语义质量、行业/宏观桶容量有实际检查结果 |

自动验证重点覆盖：

1. 一帖多事件、同事件多对象，稳定 record_id；所有对象统一大写，INDUSTRY/MACRO 不被交易名单误删；规范化不擅自映射项目名或合并不同币种。
2. 第一轮新表初始化与事件表自动/独立导入的分支区别、已确认缺表时的注册、写入失败恢复、按日期范围补缺、独立导入的固定输入冲突；正常写本轮 AI 回答不触发输入冲突。
3. 一个日历月的月末边界、下界包含、同刻与未来排除、不同对象隔离及超过 10 个候选组。
4. AI 四种输出及 uncertain 转 new 的业务保存、原回答保留、普通组起点校验、第三轮按 new 分析。
5. 第二轮失败、第三轮失败、第一轮事件导入失败分别续跑，已落库成功 AI 不重做；同进程存储重试不新增模型调用；未落库缓冲不假定为持久化。
6. repeat 有效来源、无来源、跨月来源及不将继承 usage 计为新调用。
7. 原有官方账号测试与默认配置行为保持通过；不要求把官方数据迁移到媒体表结构。

真实样本应包含纯观点、评论夹事实、风险传闻、同源转载、明确确认、否认、更正、具体资产、行业和宏观消息。检查事件遗漏、对象错配、来源限定丢失、误归组及影响理由是否有事实依据。

正式运行前补齐媒体来源路径、两张新表的物理路径、模型及接口配置、日期范围，并检查繁忙月份同对象历史输入规模。该阶段不以回测收益替代数据处理质量验收。
