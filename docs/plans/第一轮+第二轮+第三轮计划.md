本版沿用 V1.4 的三轮职责、事件去重分析表和状态设计，补充已确认的代码实施规则。round1事件提取结果已保存在round1帖子事件提取表的 ai_response_content 中，实际 JSON 为 {"events":[{"event":"事件事实","tickers":["ETH","LEND"]}]}。后续程序使用固定的round1事件提取结果，不在中间程序、round2事件去重归组或round3事件影响分析运行时重新生成或改写它。

2026-10-15 补充：用户要求round1事件提取也增加正文 JSON 与事件字段校验。请求时和后续导入共用 events/event/tickers 校验，允许空 events 与空 tickers；账号映射仍在导入阶段处理。三轮每个任务的网络、可重试 5xx 和无效回答共用各自 run.max_attempts，首次计入，默认 3 次。round1事件提取预算耗尽只使该帖失败；已成功历史任务不追溯新增校验。具体规则以 docs/rules/KEY_RULES.md 第 5、6 节为准，文中较早“round1事件提取行为保留”描述不包含本次明确要求的校验与重试变化。

本方案将三轮 AI 任务清晰分开：
- round1事件提取 AI（已有）： 从帖子提取具体事件及相关代币，优先保证事实召回与准确性。
- 中间程序（必经的轻量检查）： 展开记录、历史召回、组织事件历史，并以保守规则决定是否需要round2事件去重归组 AI。
- round2事件去重归组 AI（按需调用）： 只做事件关系判断和信息增量提取，不负责经济影响评分。
- round3事件影响分析 AI（单独调用）： 对新的有效信息分析 direction、materiality、certainty、persistence 和 materiality_reason。
**已确定的总原则：**以「单条提取事件 × 单个目标代币」为披露记录粒度；使用 (date, record_id) 复合索引；event_id 指向事件组首条建档记录的 record_id。历史检索限定同币、当前披露前默认 5 个日历年的已完成关联记录，窗口包含下界、排除当前时刻及未来；候选组历史也限定在同一窗口，不回查窗口外起点。按事件组最高余弦分数筛选，仅提交达到阈值的最多 10 组，不补足；无历史或所有组低于阈值时自动 new。默认阈值 0.50 为待标定试运行值，低分不证明没有历史关联；round2事件去重归组正常返回且通过格式校验的 uncertain，由程序按 new 建立独立事件组。
## 一、round1事件提取：如何判断一条帖子是不是事件？
我建议不要让round1事件提取判断“这个事件重不重要”，因为这实际上已经在要求 AI 预测市场影响。
但也不能把任何具体活动都当作事件，否则普通 AMA、社区抽奖、会议宣传都会进入研究库。
因此，需要定义一个适中的边界。
1. 事件的工作定义
事件是指帖子明确披露了项目、协议、代币或相关主体在技术、业务、规则、资金、运营状态等方面发生的具体行动、变化、决定、结果，或者具有明确内容的未来计划。
重点是三个条件：
条件	判断问题	举例
具体性	是否能明确说出发生了什么？	宣布回购 200 万美元代币
事实性	是否是可以从原文确认的事实、决定或计划？	治理提案已通过
研究相关性	是否涉及项目发展、资产经济机制、风险或交易条件等实质内容？	新版本主网正式上线


这里“研究相关性”的要求应当宽松。
只需要判断这是不是值得记录的项目事实，不要求 AI 判断它会不会影响币价。
2. 事件识别的边界案例
我建议优先用下面这些例子，来明确模型的判断规则。
帖子内容（示意）	round1事件提取结果	判断理由
Aave V4 正式上线	提取	具体的产品上线事件
Aave 计划明年推出 V4	提取	明确的未来计划
Aave V4 上线推迟两个月	提取	计划发生变化
Aave V4 上线后运行良好	视内容判断	如果没有具体新事实，可能只是宣传
Aave V4 上线首周 TVL 达到 10 亿美元	提取	具体的业务指标披露
DAO 提议回购 20% 协议收入对应的代币	提取	明确的经济机制提案
DAO 回购提案投票通过	提取	具体治理结果
我们与 ABC 公司正式签署合作协议	提取	有明确合作主体及动作
我们期待与更多机构合作	不提取	一般愿景
重大消息即将到来！	不提取	没有具体事件事实
我们将在周五举办 AMA	不提取	普通社区运营活动
某项目遭遇攻击，损失 500 万美元	提取	具体安全风险事件
我们的协议没有受到此次攻击影响	提取	具体风险澄清，必须保留否定含义
BTC 刚上涨 5%	不提取为项目事件	只是报道已发生的行情
本周协议收入达到 100 万美元	提取	具体经营指标披露


其中有两个特别值得注意的边界。
第一，计划也是事件。
因为市场可以在事件实际发生前交易预期，因此不能只提取已实施事项。
第二，周期性指标披露也应保留。
例如每月代币销毁量、协议收入、活跃地址等，即使是例行披露，也可能包含新数值。是否超出预期、是否产生 Alpha，留到后续研究。
3. 我建议采用的宽松事件范围
不要求round1事件提取给它们分类，但可以将下面这些作为内部识别参考：
- 技术与产品变化：升级、上线、部署、延期、故障、停止服务。
- 商业与生态变化：实际合作、客户采用、集成、业务扩张。
- 代币经济变化：回购、销毁、解锁、增发、收益分配、质押规则。
- 治理与决策：提案、投票、批准、规则修改。
- 风险与经营事实：攻击、资金损失、恢复、收入和用户数据。
- 资本与交易条件：融资、交易所上市、退市、重要交易机制调整。
这些是事件识别的参考范围，不是要求round1事件提取输出的事件类别。
round3事件影响分析再根据真实事件库确定最终分类体系。
## 二、round1事件提取：输出中哪些要素不可缺少？
round1事件提取实际输出只包含顶层 events 字段；每个事件对象包含 event 和 tickers：
{
  "events": [
    {"event": "事件事实", "tickers": ["ETH", "LEND"]}
  ]
}
没有事件时输出 {"events":[]}。event 保存事实描述，tickers 保存该事实对应的目标代币列表。后续程序按每个事件对象中的 tickers 展开记录。
不新增事件类型、事件阶段、代币关联评分等结构化字段。以下内容要求针对各事件对象的 event 文本。
1. 必须明确三个核心要素
① 事件主体或对象
谁做了这件事？改变的是哪个协议、产品、资产或服务？
② 具体行动或变化
上线、宣布、批准、销毁、回购、遭攻击、暂停等，具体发生了什么？
③ 事件状态
是计划、提案、已批准、已完成、已取消，还是被否认？保留原文所表达的状态。
此外有两个条件性要求：
关键数字与时间：原文有明确金额、比例、日期、数量、版本号，就保留；原文没有，不得补充。
关键限定条件：例如“仅在测试网”“仅适用于部分用户”“尚待治理批准”“未受到攻击”等，不能在摘要中丢失。
2. 用一个例子说明为什么这几个要素重要
原帖：
ABC Protocol proposes allocating 20% of revenue to token buybacks, subject to DAO approval.

不好的输出：
ABC 项目回购代币。

这个摘要存在三个问题：没有保留 20% 的回购比例，丢失“提议”状态，也丢失了“仍需 DAO 批准”的条件。
更好的输出：
ABC Protocol 提议在 DAO 批准后，将 20% 的协议收入用于代币回购。

这只是一句话，但已经包含round2事件去重归组需要比较的关键事实。
3. 多事件怎么处理？
如果一条帖子同时宣布：
ABC V3 已正式上线，同时 DAO 批准将 20% 收入用于代币回购。

那么输出：
{
  "events": [
    {"event": "ABC V3已正式上线", "tickers": ["ABC"]},
    {"event": "ABC DAO已批准将20%的协议收入用于代币回购", "tickers": ["ABC"]}
  ]
}
这里 ABC 为示例中的目标代币；实际 tickers 使用固定的round1事件提取结果，不由后续程序依据外部知识补充。
原则是：一个能够独立成立的事实变化，对应一个事件描述。
不要把同一件事的不同说法重复提取。
4. 我建议round1事件提取坚持四条底线
1. 不漏掉计划与执行之间的区别。
2. 不把否定、推测、条件事件改写成已经发生的事实。
3. 不把第三方项目事件自动归为发帖账号自己的事件。
4. 不依据外部知识补充原帖没有的信息。
对弱模型而言，这几条比“理解全部加密金融知识”更加实际，也更加容易验收。
## 三、当前确定的整体流程与数据粒度
1. 处理流程
原始 X 帖子
    ↓
round1事件提取 AI（已完成）：每帖提取 events[]，保留事件事实及受影响资产
    ↓
程序：按「event × asset」展开、生成稳定 record_id、按发布时间排序
    ↓
程序：从历史记录检索相关候选（同资产、默认前 5 个日历年；不回查窗口外组历史）
    ↓
程序：判断历史关联可能性是否足够低？
    ├─ 是 → 自动 new：event_id = record_id；记录自动跳过原因
    └─ 否 → 程序取 Top 10 不同事件组，组织每组事件历史
                 ↓
              round2事件去重归组 AI（按需）：new / update / repeat / uncertain
                 ↓
              程序校验输出；正常 uncertain 转为 new；分配/继承 event_id
    ↓
round3事件影响分析 AI（独立）：默认只分析 new / update 的经济影响
    ↓
事件去重分析表（date, record_id 复合索引）→ 历史价格/Alpha检验
程序化检索用于选择历史候选并降低round2事件去重归组调用；2026-10-16 用户要求启用低分自动 new，默认阈值 0.50 为可调整的试运行起点，未经过实际样本标定。可靠性须通过独立样本测得的漏关联率验证，分数不是同一事件的概率。
2. 记录粒度：round1事件提取单个 event × 单个 asset
假设某帖子输出两条事实：第一条影响 ARB 和 ETH，第二条仅影响 ARB。程序展开为三条 record：
round1事件提取序号	事件事实	asset	披露记录
0	某协议与两个生态达成合作	ARB	r001
0	某协议与两个生态达成合作	ETH	r002
1	ARB 公布解锁计划	ARB	r003


每条 record 是某次披露针对某个代币的独立研究观测；它并不等于「唯一的现实世界事件」。同一条原始事实对应不同币种时，可共用 source_post_id，但在本方案中分别建立按币种划分的 event_id 事件组，以便round2事件去重归组按币种比较、round3事件影响分析分别分析经济影响。
round1事件提取事件的 tickers 为空数组时，按该帖 user_name 从配置取得代币，再展开记录；user_name 也无法映射时，报错并停止启动该处理范围。事件已有合法 tickers 时使用原列表，不额外追加账号映射代币。events=[] 是正常无事件结果，不展开记录，也不要求该用户名有代币映射。round1事件提取原始结果保持不变，映射所得代币只写入展开后的记录。具体配置示例见第十一章。
对同一份固定的round1事件提取结果和映射配置重复导入或重启后续程序时，已创建的 record_id 必须保持稳定。后续若需要更换round1事件提取结果或改变已有记录的代币映射，事件重排、拆分、合并及后续重算范围须另行确认，不在当前流程中自动覆盖。
3. ID 的含义
- record_id： 每一条「event × asset」披露记录的唯一标识；由程序创建并固化，不依赖数据库自增。
- event_id： 一组相互关联的披露记录共用的事件标识。首次建立事件组时，直接使用该组首条建档记录的 record_id，以后不随补录更早帖子而变动。
- source_post_id： 原始 X 帖子的标识，用来追溯证据；单个帖子可有多个 record_id。
record_id 按原始帖子 ID、固定的round1事件提取事件序号和规范化的 asset 生成确定性标识，格式为 source_post_id:event_index:asset。事件序号从 0 开始，保留原 events[] 的顺序，不在导入时重排。帖子 ID 拼接为字符串，不修改round1事件提取的原始索引；例如帖子 ID 为 22222222、第 0 个事件影响 ETH，则 record_id 为 "22222222:0:ETH"。槽位与 ID 的对应可由固定输入重新生成，无须另建对照表。文中 r001 等为展示缩写；更换round1事件提取结果、补录或改变槽位对应后的处理另行确认。
round2事件去重归组/程序结果	event_relation	event_id 赋值	new_information
程序无合格历史或所有组低于阈值	new	当前 record_id	null（当前 event 即新增事实，不代表已证明与历史无关）
AI 判断全新事项	new	当前 record_id	null（当前 event 即新增事实）
AI 判断为已有事件进展	update	匹配到的历史组 event_id	本次新增或变化的事实
AI 判断为重复披露	repeat	匹配到的历史组 event_id	null
AI 正常返回 uncertain	new	当前 record_id	null；模型原始 uncertain 保留在处理记录中


所以 event_id 不等于每行的 record_id：它只在新事件首次建档时与该行 record_id 相等。
## 四、中间程序：历史检索、分组与round2事件去重归组按需触发
1. 中间程序的职责与边界
中间程序负责以下可复现的步骤：
1. 将round1事件提取 events[] 拆成「event × asset」记录并稳定赋予 record_id。
2. 按精确帖子发布时间从早到晚处理历史数据；保证候选只来自当前时点之前已知的信息。
3. 在同一个 asset 内检索相关历史 record，只使用已部署 bge-m3 的向量相似度。
4. 将检索命中的 record 按 (asset, event_id) 聚成事件组，并给事件组排序。
5. 无合格历史或所有组低于阈值时自动 new；否则取达到阈值的最多 10 个事件组，构造结构化历史供round2事件去重归组判断，不补足候选。
6. 对 AI 返回的匹配 ID 做存在性、资产一致性、时间有效性校验，再更新当前记录和事件索引。
程序不依据文本相似度直接给出 update 或 repeat。高相似度也必须经过round2事件去重归组 AI 判断，因为「两次回购计划」「相同主题的两次安全事故」可能措辞相近却是独立事件。
2. 历史范围、检索对象和时间边界
- 默认检索当前披露前 5 个日历年、同一目标 asset 的历史 record；第二轮前史检查、候选检索和向量准备共用配置 history_lookback_years，默认值为 5。对发布时间 t，窗口为 `[t-5年, t)`，包含下界，排除同刻及未来；闰日回推平年取 2 月 28 日，保留时区和纳秒，不把 5 年换算成固定天数。
- 事件组可以早于窗口建立，但只提供窗口内的组事实，不回查窗口外的首次披露和关键进展。窗口内缺少建档起点时，内部保留 event_id，设置 first_disclosure=null、history_trimmed=true，并提供 first_available_disclosure 表示窗口内最早披露；发送第二轮 AI 时只保留该组的本次请求短编号和可用事件的 published_at、event。
- 当前记录所需的同代币历史尚未完成关联时，停止并提示需要先补跑的历史，不自动扩大处理范围，不把空历史索引视为没有相关披露。Embedding 等检索服务异常也不能作为自动判 new 的依据。
- 发布时间直接取round1事件提取索引的 date，不做时区转换。缺失、无法解析或只有年月日且缺少时分秒的数据，在启动检查时报告错误，不擅自补出时间。示例 "2018-01-01 12:12:12" 满足要求；完全相同的发布时间不算错误，同一代币该时刻的记录使用同一份此前历史，完成该批后再加入索引。
- 历史回测严格避免使用未来的事件摘要或后续修订结果。候选事件历史只能包含当前记录发布时间以前已经公开、且当时可用于判断的信息。
3. 检索与排序：先召回 record，再归并 event_id
2026-10-16 用户确认只编码每条历史 record 的完整 event，包含历次 update 对应的 event，而不是只使用事件组首次 event。new_information 保留在内部组历史中，第三轮只使用本条记录的 new_information，不重复拼接到向量文本，也不再发送给第二轮 AI。
2026-10-16 用户确定第一版直接调用已部署的 bge-m3 Embedding 接口，只使用向量相似度检索，取消此前建议的关键词 / BM25 及排名融合。时间和资产用于限定候选，不额外加权。用户后续确认把向量保存到事件去重分析表 embedding 列，按组最高分与可配置阈值筛选，无历史或全部低分直接 new；完整规则见 [表内向量与阈值方案](EMBEDDING_TABLE_STORAGE_PLAN.md)。


程序对合格窗口内历史 record 全部做向量比较，再按 event_id 归并。相同 event_id 的多个 record 只占一个候选事件组的名额，组分数取组内最高余弦相似度，原始记录不删除；本轮不持久保存检索得分或候选明细。
最终向round2事件去重归组提供最多 10 个达到相似度阈值的不同事件组，不是 10 条 record。不能先取 10 条 record 再去重，以免高频事件挤掉其他组。窗口内全部比较，按 event_id 取最高分，分数大于等于阈值才参与 Top 10；无历史或全部低于阈值直接 new，默认阈值 0.50 待样本标定。
4. 事件历史如何由程序构造（不另调 AI）
为便于从单表重建历史，运行程序维护两个轻量索引：
record_search_index:  asset → 可检索的历史 record（含 event / new_information / 精确发布时间等）
event_history_index: (asset, event_id) → 同一事件组的历史 record 列表
当前实现先按配置日期读取本次任务，有待处理任务时才补读所需的默认前 5 年历史，在内存建立这两个索引；不读取全表事件内容，不接入外部检索或本地持久缓存组件。数据库仍只有确定的 (date, record_id) 复合索引；该复合索引不会天然加速按 asset / event_id 查找，因此不能假定仅凭事件去重分析表索引即可高效回查事件组。
恢复或追加历史索引时，只纳入 round2_status="1" 且早于当前披露时点的记录。round3事件影响分析尚未分析或分析失败不影响已完成关联的记录参与历史检索；round2事件去重归组待处理、处理中或失败的记录不能冒充已经完成关联的历史。
对每个命中的 event_id：
1. 从 event_history_index[(asset, event_id)] 取得本条披露历史窗口内的 record；按精确发布时间和 record_id 排序。
2. 窗口内有唯一建档 new 时，将其作为 first_disclosure，history_trimmed=false；缺少起点时，first_disclosure=null、history_trimmed=true，另以 first_available_disclosure 提供窗口内最早披露，不把它改写成 new。
3. 对窗口内每条 update，附上日期、record_id、原始 event 及 new_information，形成进展时间线。
4. 对 repeat，统计窗口内披露次数，一般不在事实时间线中重复正文；缺少起点时，即使窗口内只有 repeat，也通过 first_available_disclosure 提供可比较事实。原始行仍保存在数据库中。
5. 内部生成包含 event_id、asset、可用起点、窗口内更新、窗口内披露次数和截断标记的组结构。发送第二轮 AI 时，由 build_relation_input 转为 current.published_at、current.event 及每组 candidate_id、history 事件列表，每条历史含 published_at、event。每条 published_at 为对应 df 的 date 索引值的字符串，保留完整精度和时区。按候选顺序使用 E1、E2 等编号，并返回短编号到真实 event_id 的映射。不发送真实 event_id、资产、披露标识、new_information、次数或截断标记；第三轮不读取或接收组历史。只组织事实，不另调 AI 生成摘要，不推断窗口外事实。
发送第二轮 AI 的固定结构示例：
{
  "current": {
    "published_at": "2025-01-03 12:00:00",
    "event": "ABC Protocol 已开始执行1000万美元代币回购计划。"
  },
  "candidates": [
    {
      "candidate_id": "E1",
      "history": [
        {
          "published_at": "2025-01-01 12:00:00",
          "event": "ABC Protocol 提议投入1000万美元回购代币，尚待治理投票。"
        },
        {
          "published_at": "2025-01-02 12:00:00",
          "event": "ABC Protocol 的1000万美元代币回购提案已通过治理投票。"
        }
      ]
    }
  ]
}
history 保留窗口内起点和全部 update 的原 date 索引值及完整 event；缺少起点时保留窗口内最早可用披露，再接全部 update。同一披露同时作为最早可用披露和首条 update 时只发送一次，不按文本相同去重；事件文本中已有的日期、金额和限定条件原样保留。date 表示披露时间，不必等同事件实际发生时间。具体边界见 [事件规则](../rules/EVENT_RULES.md#6-round2事件去重归组调度和输出)。
**历史窗口与组长度：**当前实现按默认前 5 个日历年限定组历史，不回查窗口外起点；history_trimmed 只在第二轮内部组历史中表示窗口内是否缺少建档起点。第二轮 AI 仅比较收到的事件文本。窗口内全部 update 都保留，不按条数或文本长度额外裁剪，也不自动总结。若窗口内历史仍超出上下文或内存，再确认额外裁剪规则及其对事实完整性的影响。
5. 何时自动跳过round2事件去重归组 AI？
检索成功且历史覆盖可信
         ↓
完全没有合格历史，或所有组最高余弦分数都严格低于配置阈值（默认0.50，试运行值待标定）
         ↓
程序判 new → event_id = 当前 record_id → 直接进入round3事件影响分析
至少有一个组达到阈值时，进入round2事件去重归组 AI。检索服务、向量解析或保存失败时停止本轮，不转为自动 new，也没有自动转交人工复核的实现。低相似度不等于严格证明独立事件，因此放行阈值应优先控制真实关联事件被错判为 new 的比例。
自动判 new 的记录，在事件去重分析表使用统一的 event_relation='new'；在程序运行日志中记录 decision_source='auto_new' 及使用的规则版本。不默认持久保存本次候选、检索得分或round2事件去重归组输入。自动判新完成保存后，round2事件去重归组任务状态也标为成功，避免续跑时再次计算。
用户已要求开启阈值自动放行；运行后仍须用人工确认样本分别测 Recall@10 与自动 new 的漏关联率，再调整阈值，不把当前默认值视为已经验证的安全边界。
6. 增量、补录和异常处理
- 按时间批处理：同币同一时刻的关联全部保存后，再把成功记录加入检索索引与事件历史索引；同刻记录互不成为历史，不使用后续时点信息。
- 日常增量：仅从事件去重分析表恢复第二轮历史索引，不读取原帖；已完成关联不重做。
- 历史补录：同币存在更晚已完成关联时，补入更早待处理记录会在启动检查中停止；程序不自动重算下游或改写原 event_id，须先确定重算范围。同刻前沿续跑和末尾追加沿用原规则。
- 如果 AI 输出不存在的 matched_candidate_id、真实长 ID 或旧字段 matched_event_id，不得自动合并；按无效输出使用原请求预算重试，耗尽后保存失败并暂停该币。短编号只映射到本次已通过同币和时间筛选的候选，不能指向其他资产或未来记录。当前没有自动复核队列。
- round2事件去重归组正常返回且通过格式校验的 uncertain，按 new 建立独立事件组，event_id = 当前 record_id；保存成功后可参与后续历史检索，并进入round3事件影响分析。保留模型原始输出，以便区分 AI 明确判新与 uncertain 转为新事件。
- 请求失败、回答截断、JSON 或字段无效、非法匹配 ID 等不是正常 uncertain，仍走失败、重试或复核路径，不能转为 new。
## 五、round2事件去重归组 AI：事件关系及信息增量（按需）
1. 任务边界
round2事件去重归组只判断两件事：
A. 当前披露是否属于某个已有的具体事件组？
B. 如果属于，当前披露相对于该组截至当时的历史状态是否增加了新的可核实事实？
round2事件去重归组不输出 direction、materiality、certainty、persistence、materiality_reason，也不预测未来币价。相关判断全部留到独立round3事件影响分析，降低单次推理负担。
2. 输入与输出约定（正式提示词见 configs/round2_ai_config.yaml）
**输入：**current 只包含 published_at、event；candidates 最多 10 组，每组只包含 candidate_id 和 history，candidate_id 为 E1、E2 等本次请求短编号，history 为窗口内可用历史事件的 published_at、event 对象列表。每条 published_at 取对应 df 的 date 索引值的字符串。时间窗口、同币筛选和历史排序由程序负责，不给第二轮 AI 发送真实 event_id、资产、披露标识、增量或截断标记。第二轮不读取或发送原帖正文；第三轮只使用本条 asset、event、new_information，不读取正文或历史。
AI 输出结构示例（假设匹配历史已明确披露1000万美元回购提案尚待治理投票）：
{
  "event_relation": "update",
  "matched_candidate_id": "E1",
  "new_information": "ABC 的1000万美元回购计划此前处于提案、尚待治理投票阶段；本次披露投票已通过，状态由已提议转为已获批准。本次未披露是否开始回购。"
}
其中 matched_candidate_id 只可从本次提供的 candidate_id 中选择；new、uncertain 时为 null。程序校验短编号后转换成内部 matched_event_id 真实 ID，再按第三章规则写入事件去重分析表。输入与映射固定在各自请求中，同一任务的所有重试复用；不同任务可各自使用 E1，不共享映射，数据库结构和真实 event_id 的含义不变。AI 原始回答保留短编号。
event_relation	判定含义	matched_candidate_id	new_information
new	当前候选中未确认匹配的同一具体事项	null	null，整条 event 即新事实
update	同一具体事项的后续实质进展	候选短编号	包含必要旧状态、本次变化及当前状态和条件的可独立阅读说明
repeat	同一具体事项的既有事实重复披露	候选短编号	null
uncertain	关系或增量无法可靠确认；程序通过格式校验后按 new 建档	null	null；模型原始结果保留


new 表示在所收集历史信息和本次候选检索范围内未确认已有同一事项，不代表全网首次公开。由于检索可能漏召回，new 也不等于绝对不存在先前披露。
事件去重分析表还包含由正常 uncertain 转换而来的 new。该转换表示不强行匹配现有组，按独立事件继续处理；不表示模型已经确认它与所有历史事件无关。它可能将同一真实事件拆成多个事件组，分析时可通过处理记录识别此类建档来源。
3. 判断同一事件的规则
以相同具体事项、相同关键对象、存在合理连续关系为标准，不能仅凭事件类别或一般文本相似度合并。提示词将关系选择融入这一步：比较所有候选后确认都不匹配才选 new，唯一匹配后进入新增事实判断，无法可靠判断或无法唯一选择时选 uncertain。
历史记录	当前记录	建议判断
ABC 提出 V3 升级计划	同一 V3 正式上线	update，继承历史ID
ABC 提出某项回购计划	该计划通过治理	update，继承历史ID
ABC 与 XYZ 开始试点	完成同一试点	update，继承历史ID
ABC V3 已上线	ABC V4 宣布开发	new，不同版本
ABC 与 XYZ 签约	ABC 与 DEF 签约	new，不同合作事项
ABC 发生一次攻击	ABC 数月后发生独立的另一次攻击	new，不同事故


**周期性事件：**不同月份的销毁、不同批次的回购、不同月份经营指标应保留为独立披露；如果明确属于同一持续性计划，可以共享事件组但必须保留各期新的数值及期间。若是重新批准的独立计划或不同具体事项，则应独立建组。其最终边界用样本测试验证，第一版不引入复杂的多级事件树。
4. 新增信息识别规则
提示词将其作为第二个判断步骤：与唯一匹配组的全部 history 比较，没有新增事实选 repeat，有新增事实选 update 并填写 new_information，无法可靠区分时选 uncertain。第三轮不再读取组历史，因此新增信息须能独立说明“此前已知状态 → 本次变化 → 当前状态及条件”，不能只写“获批”“金额提高”等短摘要。旧状态引用唯一匹配组最近已知且未被后续事实更正的历史，本次新事实引用 current.event；必要旧事实只作为对照，不复制完整历史或重新算作新增。多项新增事实分别交代，保留数值、期间、单位及关键条件，区分累计值与新增量、计划与执行。旧状态无依据时说明所给历史未披露，当前没说明执行时不能写成尚未执行；同一事项和新增本身已确认时，不因旧状态缺失就改选 uncertain。完整例子和边界见 [第二轮规则](../rules/EVENT_RULES.md#6-round2事件去重归组调度和输出)。固定输出结构只规定字段和空值，不另列关系判定或新增信息填写章节。
- **update：**出现新的决定、批准、执行、结果、取消、阶段、时间条件、金额/比例/指标、实质确认或否认；说明本次新增事实及理解变化所必需的旧状态，不分析经济影响。
- **repeat：**只有已知事实的转述、宣传或情绪表达，无实质新条件或结果。
- **new：**为独立的具体事项；原始 event 保存完整事实，无需再复制到 new_information。
- **uncertain：**信息缺失、多个候选都可能匹配或无法确认独立性，不强行合并；程序对正常输出按 new 建立独立事件组。
例如“正在积极推进 V3 开发”通常未提供可核实的新阶段；“V3 已通过审计”则是新增事实。
5. round2事件去重归组之后的程序校验
1. 校验 AI 输出 JSON 字段、枚举值和空值规则。
2. 对 update / repeat，验证 matched_candidate_id 属于本次短编号映射，再转换为真实 matched_event_id；映射只能来自本次同币、当前时点之前的合法候选。未知短编号、真实长 ID 和旧字段均按无效 AI 输出处理，重试沿用原输入和映射。
3. 通过校验后，update / repeat 的 event_id 设为匹配组的 event_id；new 的 event_id 设为自己的 record_id。正常 uncertain 转成 event_relation='new'，event_id 设为自己的 record_id，new_information 为 null；处理记录保留 AI 原始关系 uncertain。
4. 不自动将两个已经独立建立的事件组合并。若一条披露同时指向多个事件组，作为特殊冲突处理。
5. 完成写入后，再刷新 record_search_index 和 event_history_index。
先测试「一条当前记录 + 最多10组历史事件，一次判断」；如果多候选历史让小模型经常选错 ID、忽略某次更新或出现上下文干扰，再考虑裁剪历史、缩小候选数量或逐对比较。逐对比较不能补救检索阶段根本没召回真实事件的问题。
## 六、round3事件影响分析 AI：独立分析经济影响
round3事件影响分析与round2事件去重归组明确拆开，避免把多历史事件关联与经济影响多维度判断同时塞进一次推理。默认只有 new 和 update 进入round3事件影响分析，其中 new 包括正常 uncertain 转换后建立的事件；repeat 的经济影响字段可留空，保留披露记录供注意力/重复传播研究。请求或校验失败的记录仍未完成关联，不进入round3事件影响分析。
round3事件影响分析输入必含 asset、event，new_information 仅有内容时发送，空值或纯空白时省略该字段，不再读取原帖或组历史。new 分析当前 event；update 使用第二轮保存的新增信息作为分析重点，event 提供上下文。repeat 跳过。第三轮不重新检索、复核历史或核实组起点，仍要求整个处理范围的第二轮状态和本条基本关联合法，再恢复和认领任务。
输出字段	判断内容	重要约束
direction	利好/利空/中性/混合/不确定	根据经济机制，而不是文本情绪或未来价格
materiality	高/中/低/不确定	综合利益或风险重要性、影响规模、供需/价值捕获途径、项目影响传导到代币的直接程度
certainty	计划或提案/已批准/执行中/已发生/不确定	衡量事件实现状态，不是模型自信程度
persistence	一次性/持续性/结构性/不确定	衡量经济机制持续性，而非价格反应持续几天
materiality_reason	简短说明影响路径、规模依据、与代币的关联	无法判断的部分明确说明信息不足，不臆造数据


经济重要性可能来自代币供应、需求、销毁/回购、权益分配、安全风险，或项目经营规模变化；重大项目新闻不必然对目标代币具有重大经济影响。round3事件影响分析不输出预测涨幅、买卖指令或人为指定的价格影响折扣系数。
## 七、事件去重分析表与数据库约束
1. 事件去重分析表粒度和索引
每一行 = round1事件提取单个 event × 单个 asset 的一次披露记录。既有round1事件提取的原始 events[] 不因关联而删除，事件去重分析表保存展开后的研究记录。
复合索引固定为 (date, record_id)。 record_id 保证单条记录唯一，event_id 可以在多行重复，不能以 (date, event_id) 代替主键。
字段	含义 / 来源
date	直接复制round1事件提取任务/事件去重分析表中对应帖子的 date；同帖展开出的全部记录使用相同值，不采用事件描述中的日期或 AI 生成时间
record_id	程序生成的单条「事件×代币」披露ID
event_id	事件组ID：首次建档 record_id 或匹配到的历史组ID；尚未完成关联时为 null
event	round1事件提取得到的客观事件事实
asset	round1事件提取 tickers 经程序规范化的目标代币；tickers 为空时按配置中的 user_name 映射取得
source_post_id	原始帖子ID
event_relation	完成关联后为 new / update / repeat；AI 正常返回的 uncertain 由程序转换为 new，原始关系保存在处理记录中
new_information	本次相对历史的增量事实；新事件/重复披露可为 null
round2_ai_response	第二轮 AI 原始正文和调用信息的 JSON；自动判新为空
round3_ai_response	第三轮 AI 原始正文和调用信息的 JSON；正文保留五个经济字段，repeat 跳过时为空
round2_status	round2事件去重归组阶段状态："0" 待处理、"9" 处理中、"1" 本阶段已完成、"-1" 本轮最终失败
round2_config_hash	round2事件去重归组提示词与 api.payload 的 64 位 SHA-256 摘要，初始为空；认领时保存
round3_status	round3事件影响分析阶段状态：沿用同一套状态值；repeat 无须分析时也标为 "1"
round3_config_hash	round3事件影响分析 AI 配置摘要，初始为空；repeat 跳过 AI 时保持为空
error_message	两轮共享的最近一次最终失败原因；初始化及当前阶段成功后为空字符串，完整失败过程记录在日志中
embedding	本行 event 的归一化向量和模型/输入标识 JSON，初始化为空；仅在round2事件去重归组准备阶段更新，供重启复用


表结构共 16 项：date、record_id 两个索引项，以及 14 个普通列，包括 embedding 和两轮各自的回答列。2026-10-16 用户确认第三轮不再拆为五列；两轮回答列均保存 ai_response_content、usage、response_created、attempts、created，不保存推理文本。usage 只取最后一次响应，created 取实际提交数据库前的北京时间，存储重试只刷新 created。两轮状态和共享错误字段直接保存在该事件去重分析表中，不另建状态表。date 保留round1事件提取对应帖子的原值、类型和精度，不做时区转换；回答内的处理时间和接口生成时间不能替换原索引。完整约定见 [表结构](../data/EVENT_RESULT_TABLE.md)。
文中的年月日或月日简写仅用于展示示例，实际存储和时序处理使用round1事件提取的完整 date。
程序日志（不必添加为事件去重分析表列）建议记录：round2事件去重归组是否跳过、decision_source（自动/AI/复核）、检索规则与模型/提示词版本、失败重试，以及 AI 原始关系和 uncertain 转为 new 的动作。不默认保存每次检索的候选、得分或round2事件去重归组输入；任务状态和最终关联结果必须持久保存，供调度和续跑使用。

date	record_id	event_id	event_relation	event
10-01	r001	r001	new	ARB宣布回购计划
10-03	r002	r001	repeat	再次介绍原计划
10-05	r003	r001	update	回购提案获得批准
10-08	r004	r004	new	ARB与交易所达成新合作


事件组的 event_id = r001 表示组第一次建档时由 r001 创建，并不表示只保留 r001 的内容。再次检索时，程序将 r001、r002、r003 聚合成「起点 + 更新 + 重复次数」的历史，不得丢失 r003 的进展。
3. 分阶段写回
- round1事件提取后，插入展开后的事件去重分析表行；后续判断字段暂空，round2_status 与 round3_status 均初始化为 "0"，两轮 config_hash 和 error_message 初始化为空字符串。
- 程序/round2事件去重归组认领时，将 round2_status="9" 与 round2_config_hash 共同提交；确认保存后才开始处理该任务。
- 程序/round2事件去重归组完成时，在一次按列更新中共同提交 event_id、event_relation、new_information、round2_ai_response、round2_status="1" 和 error_message=""。若关系为 repeat，同一次更新还提交 round3_status="1"，round3_ai_response 保持为空；若为 new / update，round3事件影响分析状态保持 "0"。自动判新不伪造回答。
- round3事件影响分析认领时，将 round3_status="9" 与 round3_config_hash 共同提交；确认保存后才请求 AI。
- round3事件影响分析完成时，在一次按列更新中共同提交 round3_ai_response、round3_status="1" 和 error_message=""，不修改第二轮状态、回答或关联结果。
- 请求或校验最终失败时，在一次按列更新中共同提交该轮最后一次可安全提取的回答、状态 "-1" 和 error_message，失败过程同时记录在运行日志中。存储正常返回视为整批成功，异常视为本批未写入，按原存储预算重试，不读回或重新调用 AI；每次提交仅重新取 created。
每次提交保持原 (date, record_id) 索引，更新行按索引严格递增，只提交本次需要修改的列。xdata 按列更新与空值处理已由用户确认准确；单次调用异常即整批未写入，按原预算重试同一完整批次，不读回确认或只重试部分行。调用正常返回后才同步内存；若此后内存同步失败，则停止且不重写已经保存的数据。
4. round2事件去重归组与round3事件影响分析任务状态与续跑
两轮均以展开后的单条 record 为任务粒度，分别使用 round2_status 和 round3_status；不复用round1事件提取每帖一行的状态。日常任务选择依据状态和阶段前提，不通过检查结果字段来代替任务调度。

状态值使用与round1事件提取一致的字符串编码，"1" 统一表示本阶段已完成：

| 保存的值 | 含义 | 下一次运行 |
| --- | --- | --- |
| "0" | 待处理；round3事件影响分析还需等待round2事件去重归组完成。 | 满足阶段前提后可被调度。 |
| "9" | 已认领，正在计算、请求、重试或等待保存。 | 重启时按本阶段、本范围分批恢复为 "0"，不根据残留结果补成功。 |
| "1" | 本阶段已完成；round3事件影响分析 repeat 跳过分析也属于完成。 | 保持 "1"，跳过。 |
| "-1" | 本轮最终失败，原因保存在 error_message，失败过程记录在日志中。 | 恢复为 "0" 后重新处理。 |

round2事件去重归组选择 round2_status="0" 的任务，并遵守历史时间处理顺序。round3事件影响分析只选择 round2_status="1"、round3_status="0" 且 event_relation 为 new / update 的任务。round2事件去重归组未完成时，即使 round3_status 为 "0"，也不能调用round3事件影响分析 AI。
认领状态保存确认后，才开始该任务的处理。同一运行中的并发调度不能重复认领本阶段已处于 "9" 的任务；状态仅在调用程序协调写入的约定下使用，不引入多个独立进程同时抢任务的机制。
AI 正常返回 uncertain 并按 new 保存，以及程序自动判 new 并保存，round2事件去重归组均标为 "1"，round3事件影响分析保持 "0" 等待分析。repeat 的两轮状态在关联保存成功后均为 "1"；其round3事件影响分析完成表示按规则跳过，不表示调用过 AI。new / update 的round3事件影响分析状态 "1" 则要求经济影响输出通过校验并已保存。
例如 r002 被判为 update：关联保存后状态为 ("1", "0")；round3事件影响分析请求期间为 ("1", "9")；分析保存后为 ("1", "1")；round3事件影响分析最终失败为 ("1", "-1")。若 r003 被判为 repeat，关联保存后直接为 ("1", "1")，round3_ai_response 为空。
运行round2事件去重归组时只恢复本次处理范围内 round2_status 的遗留 "9"/"-1"，运行round3事件影响分析时只恢复 round3_status 的遗留 "9"/"-1"；已完成的 "1" 保持不变。一轮失败或恢复不清空另一轮已完成的状态和结果。
round2事件去重归组实际输入、候选列表和检索得分在运行内存中生成，不默认持久保存。续跑时保留已完成的round2事件去重归组关联结果，使用同一份round1事件提取结果、检索规则和历史时间边界，重新计算未完成任务的候选和输入。
重启只将所运行阶段、本范围的 "9/-1" 分批恢复为 "0"，保留旧结果与错误，不解析残留回答来补成功状态，也不对历史成功回答做通用质检。已保存为 "1" 的任务跳过；未保存答复可能需要重新请求 AI。新响应仍执行对应业务校验，实际使用事件组时仍检查前史、同币、引用和时间是否合法；异常历史不自动修复。
5. 两轮共享 error_message
在当前固定输入、已完成阶段不重跑的流程中，round3事件影响分析必须等待round2事件去重归组成功，因此一条记录不会同时处于round2事件去重归组失败和round3事件影响分析失败。两轮共享一列 error_message，保存该记录最近一次最终失败的原因；不在此列累计历次失败。

| round2_status | round3_status | error_message 的含义 |
| --- | --- | --- |
| "-1" | "0" | round2事件去重归组最终失败原因。 |
| "1" | "-1" | round3事件影响分析最终失败原因。 |
| "1" | "1" | 空字符串；两阶段都已完成，包括 repeat 跳过round3事件影响分析。 |

只在当前任务最终失败或成功时更新此列。状态恢复、认领以及跳过已完成任务时，不清空已有错误；重新处理成功后才清空。这样round3事件影响分析失败后，再运行round2事件去重归组并跳过已完成记录，不会擦掉round3事件影响分析的错误原因。
例如 r002 round3事件影响分析超时后，状态为 ("1", "-1")，error_message 保存超时原因；续跑时恢复为 ("1", "0")，原错误仍可查看。round3事件影响分析重试成功后，将经济影响字段、round3_status="1" 和 error_message="" 一起保存。
6. 导入与后续任务处理的前置检查
round2事件去重归组与round3事件影响分析分别启动、各自续跑。round1帖子事件提取表路径、事件去重分析表路径、处理日期范围和用户名代币映射从配置读取，实际路径由用户填写。
2026-10-15 用户确认改为由导入模块负责round1事件提取检查，并进一步要求 main.py 在round1事件提取结束后自动导入本次范围 status="1" 的成功帖，失败帖补跑成功后再导入。成功回答须符合约定 JSON、事件和代币规则，原 date 须可用于时序处理。空 tickers 尝试配置映射，映射失败报错；events=[] 合法且不生成记录。导入负责固定输入核对、去重及追加，已有索引不携带初始值再次写入；独立导入入口默认仍要求范围内全部成功。
round2事件去重归组只根据事件去重分析表状态处理本范围已有任务，不重新展开第一轮结果或核对账号映射；第三轮也不执行这些检查，只使用本行 asset、event、new_information，不读取原帖、组历史或元数据。source_post_id 保留用于证据追溯。

main.py 按以下步骤自动导入：

1. round1事件提取按本次配置的帖子发布时间范围读取 round1帖子事件提取表。读取时已经 status="1" 的帖子不再调用 AI，使用该行已保存的 ai_response_content；其他帖子按原规则处理，成功后保存。
2. round1事件提取正常结束后，导入模块直接解析内存中的 ai_response_content.events，不重读 round1帖子事件提取表。如果本次读取时没有帖子已经 status="1"，只查目标元数据，表存在就直接追加本次任务。
3. 如果本次读取时有帖子已经 status="1"，则读取一次整张事件去重分析表，将这些帖子和本次新成功帖子生成的任务一起按 (date, record_id) 核对。不存在的任务追加完整初始字段；已存在的跳过，保留round2事件去重归组与round3事件影响分析状态和结果，不比较已有行的业务字段。明确 DataNotFound 时 register/write。

范围指帖子发布时间，不是程序启动到结束的时间；范围外帖子不参与本次导入，不设日期限制时按全表处理。例如 A round1事件提取已成功但任务写入失败，B 的任务已导入且round2事件去重归组已完成，C round1事件提取之前失败：再次运行同一范围，A、B 直接使用已保存的回答，C 重新调用 AI；round1事件提取结束后，核对索引追加 A 和本次成功的 C，跳过 B，保留 B 的结果。完整示例见 [自动导入方案](../history/AUTOMATIC_EVENT_IMPORT_PLAN.md#再次运行补上之前未导入成功的任务)。
run_extraction 新增兼容的可选 on_successful_posts 回调，原调用和返回统计保留；不新增持久状态，round2事件去重归组与round3事件影响分析仍分别启动。人工改变历史输入、映射或状态时，通过独立入口核查并决定重算范围。
round3事件影响分析在恢复、认领或调用 AI 前，先检查整个日期范围的全部已有记录：round2_status 必须为 "1"，event_relation 为 new/update/repeat；new 自引用 event_id，update/repeat 的组 ID 非空且不等于自身。不回查组起点或历史，不校验历史 AI 回答；新产生的第二轮结果仍受严格输出校验。任何月份不满足本条前提时，全范围停止，不只处理成功部分。
round2事件去重归组还检查事件去重分析表中当前记录历史窗口内所需的同代币历史是否已经完成关联，不重新展开该窗口内的round1事件提取源帖。已有前史缺口时停止提示，由用户先补跑，不自动增加额外日期的任务或 AI 调用。前史检查、候选检索和向量准备共用 history_lookback_years，默认回看 5 个日历年；不回查窗口外组起点，同刻披露仍互不作为历史。
7. 失败后的推进与重试
round2事件去重归组普通任务在请求预算耗尽或最终不能取得有效结果时，保存 round2_status="-1" 和 error_message，暂停该代币在本轮剩余范围内的后续关联；其他代币继续。该代币未开始的后续记录保持待处理，不伪造失败结果。round3事件影响分析普通任务最终失败只影响本条，其他记录继续分析。
网络错误、HTTP 状态和整体停止条件沿用round1事件提取；公司接口认证或限额等停止型错误仍停止整轮，不能只暂停某个代币。新增业务输出校验失败也重试，包括 AI 正文不是合法 JSON、字段或枚举不合法、非法匹配 ID、跨资产或时间无效的匹配等；正常 uncertain 仍按 new 完成，不属于需要重试的失败。
网络故障、可重试的 5xx 和 AI 输出校验失败共用 run.max_attempts 的总请求预算，包含首次请求；当前默认值为 3，不分别累计多套预算。例如第一次网络超时、第二次返回非法匹配 ID，则还剩一次请求。配置与提示词保持本轮固定，重试使用本任务运行内存中的同一份输入。保存失败另用存储重试预算，不消耗 AI 请求预算，也不触发新的 AI 调用。
8. 两轮 AI 配置摘要
事件去重分析表分别保存 round2_config_hash、round3_config_hash，初始为空。直接复用round1事件提取的 ai_config_hash 函数，原始提示词模板与 api.payload 参与 SHA-256 计算；并发、重试、认证、URL 和检索输入不参与。round1事件提取摘要计算不变，新增正文校验不参与摘要，也不追溯重算已完成的round1事件提取结果。
还有任务需要继续处理时，核对该轮全表已有非空摘要与本轮配置是否一致，包含本范围外的历史；冲突时停止，不自动改旧摘要或重算。认领时仅共同提交该轮状态与摘要，保存确认后才处理；状态恢复、失败和结果写入保留已存摘要。
round2事件去重归组自动判新也绑定round2事件去重归组配置；round3事件影响分析 repeat 跳过 AI，摘要留空。本程序认领时生成 64 位小写十六进制摘要，但读取历史不校验格式、不因成功状态单独要求摘要非空，也不推断或补写旧摘要。准备继续处理时全表原值参与比较，空字符串不参与，其他原值与本次摘要不同则停止。第二、三轮无需调用 AI 的已完成路径不加载当前 AI 配置；第一轮仍在读表前校验其配置。
历史补录识别使用已有字段：按币比较本范围最早未完成时间与全表最晚已完成关联时间；前者严格更早则报告两条冲突记录并停止。这只能识别已导入历史的状态缺口，不能区分新增补录与人为状态回退。新增源记录尚未导入时不影响已有任务；导入后再检查补录冲突，同刻前沿续跑与末尾追加可正常继续。

## 十一、已确认的代码实施约定

| 事项 | 当前约定 |
| --- | --- |
| 数据路径与时间 | 路径从配置读取，由用户填写。事件去重分析表 date 直接取round1事件提取对应帖子的 date，不做时区处理；"2018-01-01 12:12:12" 是可用示例。 |

| 运行入口 | main.py round1事件提取正常结束后自动导入本次范围成功帖，失败帖补跑后再导入；round2事件去重归组与round3事件影响分析分别启动。独立导入入口保留，不作为日常必需步骤。 |
| 前置检查职责 | 自动导入只检查本批成功帖，独立导入默认要求本范围全部成功；round2事件去重归组按事件去重分析表处理已有任务并检查已导入历史；round3事件影响分析要求本范围已有任务的round2事件去重归组全部完成且关联合法。后续两轮不重复展开round1事件提取或核对覆盖。 |
| 空代币 | tickers=[] 在第一轮合法，导入时查 user_name 配置映射；映射不到则停止本次全部事件导入，写入前报错，第一轮成功状态保留，不创建失败事件行。缺少 tickers 字段则第一轮校验失败。events=[] 合法，不展开，也不要求映射。 |
| 失败推进 | round2事件去重归组普通任务最终失败暂停该代币后续关联，其他代币继续；round3事件影响分析普通任务最终失败只影响本条。 |
| 重试预算 | 网络、可重试 5xx 和 AI 输出校验失败共用 run.max_attempts，总次数包含首次；存储重试独立。 |
| 历史缺口 | 所需前史未完成关联时停止提示，由用户手动补跑，不自动扩大处理范围。 |

用户名映射配置建议统一使用代币列表，与round1事件提取 tickers 的结构相同；单个代币也写为一项列表。以下账户名仅为示例，实际填写源数据中的 user_name：

```yaml
user_name_to_tickers:
  account_a: ["ETH"]
  account_b: ["LEND"]
```

映射键按原 user_name 精确匹配，仅在事件代币列表为空时使用，不修改round1事件提取结果。映射得到的列表按相同规则规范化、去重，再按事件与代币展开。例如 account_a 的事件 tickers=[]，映射得到 ETH，创建该事件针对 ETH 的一条记录；若整帖 events=[]，则不需要查映射。

round2事件去重归组并发仍按时间边界组织：同一代币按发布时间推进，不同代币并行；相同发布时间使用同一份此前历史，该批完成后再加入索引。round3事件影响分析独立批量并发。事件去重分析表写入统一协调，提交保持原 date 和唯一递增的 date/record_id 索引。

第二、三轮正式提示词已配置，第三轮经济含义和枚举取值以 configs/round3_ai_config.yaml 为准；第一轮正式提示词仍须补齐，经济评分质量仍需真实样本验证。默认阈值可用于小样，正式全量前标定；窗口内候选历史的额外裁剪预算和严格枚举校验可根据试跑再完善。真实客户端的新增行、date/record_id 索引、向量及回答 JSON 长度仍需小样联调；按列更新及整批成功或失败的接口约定已经确认，当前不实施异常读回。模块拆分、内部函数命名和常规批量参数不作为单独审批事项。
