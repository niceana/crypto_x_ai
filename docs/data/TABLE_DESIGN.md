# 任务表字段

任务表每帖一行，保存登记时的帖子输入及最新一次完整处理的结果。处理规则见 [关键规则](../KEY_RULES.md)，项目关系见 [项目总览](../../project_overview.md)。

## 索引与字段

表格使用两层索引，名称和顺序固定为 `date`、`id`，即 pandas 的 `MultiIndex`。普通列恰好为下列九列。程序初始化任务和提交更新时，所有提交的普通单元格均为字符串，没有结果时写空字符串。读取旧任务时按状态区分结果校验，规则见下文。

| 索引或字段 | 含义 | 初始化值 |
| --- | --- | --- |
| `date`，索引第 1 层 | 源帖子的原始时间，对应原帖 `created_at`；保持原类型、时区和精度。 | 源值。 |
| `id`，索引第 2 层 | 帖子的唯一、非空白字符串 ID，与 date 共同定位行。 | 源值。 |
| `config_hash` | 提示词模板及 AI 调用参数的 64 位小写十六进制标识。 | 空字符串。 |
| `text` | 登记时的帖子正文。 | 源值。 |
| `user_name` | 登记时的用户名，仅作记录和保存核对。 | 源值。 |
| `status` | 未处理、处理中、成功或本次最终失败。 | `"0"`。 |
| `ai_response_content` | 最终 AI 回答正文，保留原文。 | 空字符串。 |
| `reasoning_content` | 最终推理文本，保留原文。 | 空字符串。 |
| `usage_json` | 最终响应 `usage` 的标准 JSON。 | 空字符串。 |
| `response_created` | 最终响应 `created` 按 Unix 秒转成的北京时间文本，格式为 `YYYY-MM-DD HH:mm:ss`。 | 空字符串。 |
| `error_message` | 最终失败原因，最多 512 个字符；成功时为空。 | 空字符串。 |

`date` 不能缺失，复合索引、ID 和列名均须唯一，同一 ID 不能对应多个日期。日期不会被处理时间或 AI 生成时间替换。

处理任务时，每批按列更新的行必须按原 `(date, id)` 严格递增：先按日期升序，同一日期按字符串 ID 升序；索引值及整行结果共同排序。并发答复按原键对应帖子，完成顺序不决定提交顺序；本批出现重复键时停止写入。

初始化源表需要字符串 `text`、`user_name`，保留原两层索引；其他源列不写入任务表，无需提供 id 普通列。仅有旧 `username` 的源表不满足要求，任务表也不接受额外的用户名列。

## 状态含义

| 保存的值 | 含义 | 下次运行读取到该任务时 |
| --- | --- | --- |
| `"0"` | 等待处理。 | 保持 0。 |
| `"9"` | 已标记开始处理，正在请求、等待重试或等待保存结果。 | 重置为 0。 |
| `"1"` | 成功结果已保存。 | 保持 1，跳过。 |
| `"-1"` | 本次最终失败及其原因已保存。 | 重置为 0。 |

状态只是本地任务记录。`"9"` 不证明请求已发送，`"1"` 不证明回答的业务判断正确。

## 数据有效性

- `config_hash` 为空或符合 64 位小写十六进制格式；成功记录的标识和非空白正文必须存在，错误原因必须为空。
- 成功记录的非空 `usage_json` 必须是标准 JSON；新结果保存时同样使用标准 JSON。它只表示最终一次响应，不累计重试用量。未成功记录的旧用量值不阻止重跑。
- 新响应的 `created` 按数值 Unix 秒转为北京时间（固定 UTC+8），`response_created` 仍为文本，例如 `1791947560` 保存为 `"2026-10-14 11:12:40"`，小数秒不保留。缺失或 null 时为空，不影响回答成功判断；`0` 是有效时间戳。
- `created` 非数值（包括布尔值和数字字符串）或超出可转换日期范围时，该帖保存为 `"-1"`，同时将 `ai_response_content/reasoning_content/usage_json/response_created` 全部写空，覆盖同一任务的旧结果，并记录失败原因。其他失败继续保留本次可安全提取的结果。具体错误优先级见 [关键规则](../KEY_RULES.md#response_created-保存北京时间文本)。
- `response_created` 不参与日期筛选，不替换原索引时间。已完成的历史记录不会自动转换或清空，原来的时间戳文本仍允许读入并跳过。
- 原输入 `text`、`user_name` 和索引在任务处理期间保持不变；后续新增任务按同一字段要求完整创建。

## 读取时按任务状态校验旧结果

旧结果不作为 AI 请求输入，读取任务时按以下顺序检查：

- 所有记录继续校验原索引、九列结构、`text/user_name/config_hash/status` 的类型，以及状态和配置标识是否合法。缺失的帖子输入仍须先恢复，不能用空字符串自动掩盖。
- `status="1"` 的记录不会重新请求 AI，继续检查已有结果的字符串类型、用量 JSON，以及成功所需的摘要、正文和空错误原因。
- `status="0"/"9"/"-1"` 的记录会在本轮重新处理，不因旧结果字段为 `None/NaN/pd.NA`、数字或旧 JSON 格式错误而拒绝启动。这些旧值不作为 AI 输入，也不自动转换或清空，直到最终结果保存时由新值覆盖。
- 新结果保存前仍检查提交值都是字符串。保存异常后的读回，只用原输入和配置标识做一致性核对；尚未匹配的新结果值仍视为未确认更新，不能因为本月其他未处理记录的旧结果为空而停止核对。

例如原索引和帖子输入完整，`status="9"`、`config_hash=H`、`ai_response_content=NaN`：允许恢复为待处理并重新请求 AI，最终保存新结果。若同一记录为 `status="1"`，缺失正文仍应报错，不能当作完整成功记录跳过。

按状态区分旧结果校验只解决重跑被旧结果格式阻止的问题，真实运行中任务输入丢失的原因仍须通过实际更新参数和保存行为核实。
