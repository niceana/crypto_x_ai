# 关键处理规则

这里说明会影响处理范围、结果、调用费用和恢复方式的行为。运行方法见 [使用说明](../README.md)，字段见 [任务表](data/TABLE_DESIGN.md)，具体代码通过下方链接定位。

## 1. 建立初始任务

初始化完整读取现有源帖子，保留原 `date/id` 两层索引及字符串 `text`、`user_name`，建立 [任务表](data/TABLE_DESIGN.md) 规定的完整数据。初始状态为 `"0"`，配置标识和结果为空。空源也会建立结构合法的空表。

流程是读取源 → 校验并建立任务表 → `cli.register(task_path, "timeseries", "")` 注册目标 → `cli.write(task_path, df)` 一次写入。源校验或建表失败不注册、不写入；注册失败不写入；整个初始化不自动重试。

初始化使用已知尚未创建的新目标，不读取或检查目标是否存在，不承诺避免覆盖。注册或写入报错可能留下资源或部分数据，用户须等待旧操作结束、核查目标状态，再选择新目标或按真实客户端规则处理原目标后重跑。仅清空数据不保证重复注册安全。

初始化不按处理日期过滤，不读取 AI 配置，也不调用 AI。以后新增帖子的完整任务由现有数据流程创建，程序不会从源表补建遗漏任务。

代码：[初始化接入](../integration/initialize_tasks.py)、[任务初始化](../ai_batch/tasks.py)。

## 2. 处理哪些日期

`start_time/end_time` 同时设置时，使用 `YYYY-MM-DD` 字符串，包含起止日期全天；起点不得晚于终点，起止同日有效。两端均不设置时，只读取全表一次；只设置一端会报错。

例如 `2021-01-01` 至 `2021-12-31` 按 12 个自然月处理；一月读取 `2021-01-01` 至 `2021-01-31`，二月从 `2021-02-01` 开始。截止日期若写成 `2022-01-01`，还会处理这一天。

每月使用同一组日期字符串读取和异常后的再次读取。当前月请求结束且结果保存确认后，才读取下个月；空月或全是已成功任务的月份也会继续后续月份。起止不足整月时，使用实际指定日期。

日期依据原任务索引，原值、时区和精度保持不变。客户端必须返回范围内的记录，程序发现范围外数据会报错，不会自行扩大范围或删掉多读的记录。截止日下一天的零点只用于本地校验末日全天，不传给客户端。

日期字符串对应哪个日历时区、是否覆盖末日全天，仍需用真实客户端验证。只改变日期范围不改变处理配置的标识。

代码：[日期分段](../ai_batch/runner.py)、[读取范围校验](../ai_batch/tasks.py)。

## 3. 开始处理与重启

每月首次读取后，只把本月遗留的 `"9"` 和 `"-1"` 改回 `"0"`；已有成功 `"1"` 和范围外记录保持不变，旧结果及配置标识保留。

任务沿原读取顺序选取。发送请求前，先共同保存状态 `"9"` 和本轮配置标识，确认保存后再请求 AI。请求及运行内重试期间保持 `"9"`，不保存中间失败或尝试次数。

最终成功共同保存 `"1"` 和结果，最终失败共同保存 `"-1"`、可用结果及原因。本轮新失败不再次进入处理列表；下次运行读取到它时才重新处理。

例如网络重试后仍失败，本轮只保存一次最终失败；重新启动后，该任务重新开始尝试。成功任务直接跳过。

代码：[任务选择与保存](../ai_batch/tasks.py)。

## 4. AI 输入与配置变化

AI 消息只包含配置中的提示词和单帖 `text`，不发送任务键、用户名、状态或旧结果。提示词支持 `{{task.text}}`；请求体还支持 `{{prompts.system}}`、`{{prompts.user}}`。插入的正文不再次当作模板执行，未知变量会报错。

请求为非流式 POST JSON。公司接口消息字段使用 `messages`，模型及其他参数来自 `api.payload`；配置模块按原字段构造请求，不猜测字段名称。环境变量只在接口 URL 和请求头中展开，同目录 `.env` 的优先级低于进程环境。

每次启动读取一次 AI 配置，整轮使用同一份内容。修改文件不会改变已经运行中的请求。

`config_hash` 是用原始提示词模板和 `api.payload` 计算的 SHA-256 标识。计算前按固定 JSON 格式排列字段和编码，避免仅因字段顺序不同而得到不同标识。它不包含帖子正文、URL、认证、日期范围、并发、重试或响应解析逻辑；不同帖子使用同一配置时标识相同。

改提示词、模型或其他 payload 参数，应使用新任务表。仅调整 URL、日期或运行参数不会改变标识；这些变化是否仍代表相同处理含义，由调用方保证。标识只在准备处理任务时计算，发现本月已有非空标识与本轮不符就停止；没有待处理任务时不会检查全表配置是否一致。

代码：[配置与请求构造](../ai_batch/config.py)。

## 5. 请求失败时怎么办

以下次数均包含首次请求，网络重试和服务错误共用同一帖子的尝试预算；默认最多三次，实际以 `run.max_attempts` 为准。

| 情况 | 本轮处理方式 |
| --- | --- |
| 建立连接、读取响应或发送数据时出现指定的网络错误或超时 | 有预算则重试；耗尽后仅该帖失败，继续其他任务。 |
| 服务返回 500～599 | 有预算则重试；最后仍是服务错误时停止整个程序。 |
| 返回其他非成功状态，包括重定向、400、401、403、408、429 | 保存该帖失败并停止整个程序，等待人工排查。 |
| 请求地址、协议、代理或等待连接池异常 | 停止整个程序，不自动重试。 |
| 成功状态码但响应解析失败、回答截断、拒答或正文为空 | 仅该帖失败，继续其他任务。 |
| 单帖请求构造失败或其他非停止型请求异常 | 仅该帖失败，不自动重试。 |

本地读取超时可重试，服务返回 HTTP 408 则停止；等待连接池超时也停止。具体异常类型由 [运行模块](../ai_batch/runner.py) 的 `_RETRY_NETWORK` 和 `_STOP_REQUEST` 列表限定，不根据错误文案猜测类别。

重试之间采用随机等待，等待上限随次数增加并受配置限制。可重试的 5xx 若带有效 `Retry-After`，后续新请求共同遵守服务要求的等待时间；429 始终停止，不自动等待恢复。可选每秒起发上限同时约束首次请求和重试，为 0 时不额外限速。

网络错误或 5xx 不能证明服务端没有执行请求，重试仍可能重复执行并产生费用。

## 6. 什么结果算成功

成功要求 HTTP 状态为 200～299，响应为标准 JSON 对象，没有明确 error。候选回答列表 `choices` 中必须只有一项整数编号 `index=0`，程序取这一项；它必须是 assistant 消息、`finish_reason="stop"`、正文为非空白字符串，并且没有拒答或内容过滤。需要保存的字段须能正常编码。

正文和推理保留原文，不自动拆解正文内的业务 JSON，也不验证回答的业务判断是否正确。失败时保留可安全提取的结果及具体原因，原因最多 512 个字符；不保存完整原始响应。

`usage_json` 只记录最终一次响应的 usage，不累计中间重试。缺失或 null 时为空，不能据它计算全部尝试的总费用。`response_created` 保存最终响应 created 的原值表示，不推算时间单位，也不替换帖子时间。

代码：[响应解析](../ai_batch/response.py)、[结果写入](../ai_batch/tasks.py)。

## 7. 保存时只改哪些内容

所有更新按原 `(date, id)` 定位，通过同一客户端的 `update_by_index` 提交本次指定列，未提交列保持原值。

| 操作 | 提交的列 |
| --- | --- |
| 重启恢复 | 只改 `status`。 |
| 标记开始处理 | `status`、`config_hash`。 |
| 保存最终结果 | `status`、`ai_response_content`、`reasoning_content`、`usage_json`、`response_created`、`error_message`。 |

成功清空旧错误，缺失的结果字段明确写空字符串，不能保留上次结果冒充本次结果。状态和相关字段在一次更新中共同提交；这不等于真实存储已经被证明具有原子性。

默认每 200 条最终结果保存一次，不足时按首条结果等待时间达到 1 秒保存，月末和收尾时也提交余量。实际值以 `batch_size`、`result_buffer_size`、`flush_interval_seconds` 为准，结果缓存容量不得小于批次大小。

保存异常后，重新读取同一月份，核对原任务键、输入和本次提交值，只重写尚未确认的记录。如果最后一次更新报错但读回已全部匹配，仍视为保存成功；读回失败、输入变化或更新预算耗尽则停止。默认更新预算三次，由 `storage_max_attempts` 指定。

保存失败只重试数据写入，不再次请求 AI。尚未确认的更新和未保存响应只留在异常对象及程序内存，进程退出后会丢失。

代码：[保存与核对](../ai_batch/tasks.py)、[批量保存](../ai_batch/runner.py)。

## 8. 停止、并发与实际保证

一个任务表只支持一个处理程序写入，其他新任务创建流程也须协调写入。同步客户端始终在调用入口线程使用，AI 请求在独立网络线程执行。

默认同时处理 100 个网络作业，完成消息及结果缓存有容量限制；实际参数来自 AI 配置。每月数据表仍可能很大，按月读取和有界结果缓存不代表整个程序有固定内存上限。两端日期未设置时会全表读取。

整体停止时不再开始新任务或重试，结束本地请求并尽力保存已取得的最终结果。已标记开始处理、但没有最终响应的任务保留 `"9"`，未开始的任务保持 `"0"`，停止后不读取后续月份。强制结束进程可能来不及保存。

本地停止不保证远端请求撤销。请求已执行但结果丢失或未保存时，下次运行可能重复调用；程序不保证服务端恰好执行一次。

正常结束表示指定范围的本轮处理及保存完成，允许存在本轮失败任务；统计区分已有成功、本轮成功和本轮失败。异常收尾日志不表示处理完成或结果全部保存。

## 9. 验证范围

仓库最近的验证记录是 Python 3.8.10 下 86 项模拟测试通过，覆盖日期边界、状态、请求重试、停止、保存核对和入口行为。模拟结果不能替代真实接入验证。

仍需核实：真实 xdata 的安装来源和版本、日期日历与末日全天、复合索引及精度、未提交列保持、多列写入一致性、报错后的稳定读取；公司 AI 的认证和响应格式；真实请求限额、并发容量和数据规模下的资源占用。

源帖完整性、全表及跨月 ID 唯一性、后续新增任务完整性由现有数据流程保证。请求头或 URL 是否改变业务处理含义也需调用方判断，配置标识不会自动检测这些变化。
