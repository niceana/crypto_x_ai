# 关键处理规则

这里说明会影响处理范围、结果、调用费用和恢复方式的行为。运行方法见 [使用说明](../README.md)，字段见 [任务表](data/TABLE_DESIGN.md)，具体代码通过下方链接定位。

## 1. 建立初始任务

初始化完整读取现有源帖子，保留原 `date/id` 两层索引及字符串 `text`、`user_name`，建立 [任务表](data/TABLE_DESIGN.md) 规定的完整数据。初始状态为 `"0"`，配置标识和结果为空。空源也会建立结构合法的空表。

流程是读取源 → 校验并建立任务表 → `cli.register(task_path, "timeseries", "")` 注册目标 → `cli.write(task_path, df)` 一次写入。源校验或建表失败不注册、不写入；注册失败不写入；整个初始化不自动重试。

初始化使用已知尚未创建的新目标，不读取或检查目标是否存在，不承诺避免覆盖。注册或写入报错可能留下资源或部分数据，用户须等待旧操作结束、核查目标状态，再选择新目标或按真实客户端规则处理原目标后重跑。仅清空数据不保证重复注册安全。

初始化不按处理日期过滤，不读取 AI 配置，也不调用 AI。以后新增帖子的完整任务由现有数据流程创建，程序不会从源表补建遗漏任务。

代码：[初始化接入](../integration/initialize_tasks.py)、[任务初始化](../ai_batch/tasks.py)。

## 2. 处理哪些日期

`start_time/end_time` 同时设置时，使用 `YYYY-MM-DD` 字符串，包含起止日期全天；起点不得晚于终点，起止同日有效。两端均不设置时，只读取全表一次；只设置一端会报错。

例如 `2021-01-01` 至 `2021-12-31` 按 12 个自然月处理；一月读取 `2021-01-01` 至 `2021-01-31`，二月从 `2021-02-01` 开始。截止日期若写成 `2022-01-01`，还会处理这一天。

每月使用同一组日期字符串读取和异常后的再次读取。当前月请求结束且结果保存确认后，才读取下个月；空月或全是已成功任务的月份也会继续后续月份。起止不足整月时，使用实际指定日期。

日期依据原任务索引，原值、时区和精度保持不变。客户端必须返回范围内的记录，程序发现范围外数据会报错，不会自行扩大范围或删掉多读的记录。截止日下一天的零点只用于本地校验末日全天，不传给客户端。

日期字符串对应哪个日历时区、是否覆盖末日全天，仍需用真实客户端验证。只改变日期范围不改变处理配置的标识。

代码：[日期分段](../ai_batch/runner.py)、[读取范围校验](../ai_batch/tasks.py)。

## 3. 开始处理与重启

每月首次读取后，只把本月遗留的 `"9"` 和 `"-1"` 改回 `"0"`；已有成功 `"1"` 和范围外记录保持不变，旧结果及配置标识保留。

读取时先校验所有记录的索引、表结构、输入、状态和配置标识，再校验成功记录的已有结果。`"0"/"9"/"-1"` 的旧结果不作为 AI 输入，允许为缺失值或其他格式，最终保存时由新结果覆盖；成功记录仍须满足完整结果要求。具体字段规则见 [任务表](data/TABLE_DESIGN.md#读取时按任务状态校验旧结果)。

任务沿原读取顺序选取。发送请求前，先共同保存状态 `"9"` 和本轮配置标识，确认保存后再请求 AI。请求及运行内重试期间保持 `"9"`，不保存中间失败或尝试次数。

最终成功共同保存 `"1"` 和结果，最终失败共同保存 `"-1"`、可用结果及原因。本轮新失败不再次进入处理列表；下次运行读取到它时才重新处理。

例如网络重试后仍失败，本轮只保存一次最终失败；重新启动后，该任务重新开始尝试。成功任务直接跳过。

代码：[任务选择与保存](../ai_batch/tasks.py)。

## 4. AI 输入与配置变化

AI 消息只包含配置中的提示词和单帖 `text`，不发送任务键、用户名、状态或旧结果。提示词支持 `{{task.text}}`；请求体还支持 `{{prompts.system}}`、`{{prompts.user}}`。插入的正文不再次当作模板执行，未知变量会报错。

请求为非流式 POST JSON。公司接口消息字段使用 `messages`，模型及其他参数来自 `api.payload`；配置模块按原字段构造请求，不猜测字段名称。环境变量只在接口 URL 和请求头中展开，同目录 `.env` 的优先级低于进程环境。

默认请求参数包括 `temperature: 0` 和 `provider_options: max`；后者作为字符串 `"max"` 原样发送。

每次启动读取一次 AI 配置，整轮使用同一份内容。修改文件不会改变已经运行中的请求。

`config_hash` 是用原始提示词模板和 `api.payload` 计算的 SHA-256 标识。计算前按固定 JSON 格式排列字段和编码，避免仅因字段顺序不同而得到不同标识。它不包含帖子正文、URL、认证、日期范围、并发、重试或响应解析逻辑；不同帖子使用同一配置时标识相同。

改提示词、模型或其他 payload 参数，应使用新任务表。仅调整 URL、日期或运行参数不会改变标识；这些变化是否仍代表相同处理含义，由调用方保证。标识只在准备处理任务时计算，发现本月已有非空标识与本轮不符就停止；没有待处理任务时不会检查全表配置是否一致。

代码：[配置与请求构造](../ai_batch/config.py)。

## 5. 请求失败时怎么办

以下次数均包含首次请求，网络重试和服务错误共用同一帖子的尝试预算；默认最多三次，实际以 `run.max_attempts` 为准。

| 情况 | 本轮处理方式 |
| --- | --- |
| 建立连接、读取响应或发送数据时出现指定的网络错误或超时 | 有预算则重试；耗尽后仅该帖失败，继续其他任务。 |
| 服务返回 500～599 | 有预算则重试；最后仍是服务错误时停止整个程序。 |
| 返回其他非成功状态，包括重定向、400、401、403、408、429 | 保存该帖失败并停止整个程序，等待人工排查。 |
| 请求地址、协议、代理或等待连接池异常 | 停止整个程序，不自动重试。 |
| 成功状态码但响应解析失败、生成时间无法转换、回答截断、拒答或正文为空 | 仅该帖失败，继续其他任务。 |
| 单帖请求构造失败或其他非停止型请求异常 | 仅该帖失败，不自动重试。 |

本地读取超时可重试，服务返回 HTTP 408 则停止；等待连接池超时也停止。具体异常类型由 [运行模块](../ai_batch/runner.py) 的 `_RETRY_NETWORK` 和 `_STOP_REQUEST` 列表限定，不根据错误文案猜测类别。

重试之间采用随机等待，等待上限随次数增加并受配置限制。可重试的 5xx 若带有效 `Retry-After`，后续新请求共同遵守服务要求的等待时间；429 始终停止，不自动等待恢复。可选每秒起发上限同时约束首次请求和重试，为 0 时不额外限速。

网络错误或 5xx 不能证明服务端没有执行请求，重试仍可能重复执行并产生费用。

## 6. 什么结果算成功

成功要求 HTTP 状态为 200～299，响应为标准 JSON 对象，没有明确 error。候选回答列表 `choices` 中必须只有一项整数编号 `index=0`，程序取这一项；它必须是 assistant 消息、`finish_reason="stop"`、正文为非空白字符串，并且没有拒答或内容过滤。需要保存的字段须能正常编码。

正文和推理保留原文，不自动拆解正文内的业务 JSON，也不验证回答的业务判断是否正确。一般失败保留可安全提取的结果及具体原因；生成时间无法转换时，按下文规则清空全部 AI 结果。原因最多 512 个字符，不保存完整原始响应。

`usage_json` 只记录最终一次响应的 usage，不累计中间重试。缺失或 null 时为空，不能据它计算全部尝试的总费用。

### `response_created` 保存北京时间文本

最终响应的数值 `created` 按 Unix 秒转换为北京时间（固定 UTC+8），保存为 `YYYY-MM-DD HH:mm:ss` 字符串，小数秒不保留。例如用户提供的真实接口值 `1791947560` 保存为 `"2026-10-14 11:12:40"`。转换在响应解析阶段完成，保存模块直接写入该文本。不使用本机时区，不根据数值大小猜测秒或毫秒，也不替换帖子的索引时间。

`created` 缺失或为 null 时，生成时间写空字符串，不因此判失败；`0` 是有效时间戳，保存为 `"1970-01-01 08:00:00"`。非数值（包括布尔值和数字字符串）或超出可转换日期范围时，该帖失败，最终共同保存 `status="-1"`、空的 `ai_response_content/reasoning_content/usage_json/response_created` 和失败原因，覆盖这条任务上次留下的 AI 结果。其他失败仍保留本次可安全提取的结果，不改变现有规则。

若本次响应还有更优先的 HTTP、接口、回答或编码错误，保留原有优先错误原因；仅时间转换失败时，原因明确说明 `response_created` 无法转换。成功 HTTP 响应中的时间转换失败不自动重试，继续其他任务；HTTP 失败仍按第 5 节决定重试或停止。改动只作用于之后的新响应，不自动转换或清空其他已完成的历史记录。

代码：[响应解析](../ai_batch/response.py)、[结果写入](../ai_batch/tasks.py)。

## 7. 保存时只改哪些内容

所有更新按原 `(date, id)` 定位，通过同一客户端的 `update_by_column(task_path, df)` 提交本次指定列。提交的 DataFrame 可以只包含本批要更新的部分行，索引键直接取自原读取表，普通列只包含下表列出的字段；未提交列保持原值。客户端必须提供按列更新的接口，不能用 `update_by_index` 代替。

并发请求的答复随完成消息携带原任务键，先按键生成每行结果，再检查本批复合键唯一，并将整个更新表按 `(date, id)` 升序排列，确认索引严格递增后提交。先比较 `date`，日期相同再比较字符串 `id`；不转换索引值、日期时区或精度，不单独重排索引。恢复状态、认领任务、最终保存和异常收尾均遵守此规则；部分写入后只删除已确认行，剩余重试行沿用已排序的顺序。重复键在调用客户端前报错，不静默去重。

例如原帖键为 `(2021-01-01, "10")`、`(2021-01-01, "2")`、`(2021-01-02, "3")`，答复按第三帖、第二帖、第一帖的顺序完成，提交时仍按上述原帖键的顺序排列，答复和同一行其他结果字段一起移动。这里 `"10"` 排在 `"2"` 前，因为 ID 保持字符串类型。每个更新批次内部严格递增；任务选择仍沿原读取顺序，不等待较早请求完成才保存较晚请求。

| 操作 | 提交的列 |
| --- | --- |
| 重启恢复 | 只改 `status`。 |
| 标记开始处理 | `status`、`config_hash`。 |
| 保存最终结果 | `status`、`ai_response_content`、`reasoning_content`、`usage_json`、`response_created`、`error_message`。 |

成功清空旧错误，缺失的结果字段明确写空字符串，不能保留上次结果冒充本次结果。状态和相关字段在一次更新中共同提交；这不等于真实存储已经被证明具有原子性。

最终保存前，先校验本批所有更新字段都是字符串。发现非字符串时，报错说明具体字段名和实际类型，例如 `最终更新字段必须为字符串：字段=response_created，实际类型=int`；错误说明只包括字段名和类型，本批在写入前停止。该校验针对本轮待保存结果，不读取历史结果字段，也不将非字符串自动转成文本。

默认每 200 条最终结果保存一次，不足时按首条结果等待时间达到 1 秒保存，月末和收尾时也提交余量。实际值以 `batch_size`、`result_buffer_size`、`flush_interval_seconds` 为准，结果缓存容量不得小于批次大小。

保存异常后，重新读取同一月份，核对原任务键、输入和本次提交值，只重写尚未确认的记录。本次更新列只有读回为字符串且与提交值相等时才确认；缺失值或其他类型表示该记录尚未确认，继续使用保存重试预算。本月其他未处理记录的旧结果为空或格式不对，不会阻止核对。如果最后一次更新报错但读回已全部匹配，仍视为保存成功；读回失败、输入变化或更新预算耗尽则停止。默认更新预算三次，由 `storage_max_attempts` 指定。

保存失败只重试数据写入，不再次请求 AI。尚未确认的更新和未保存响应只留在异常对象及程序内存，进程退出后会丢失。

代码：[保存与核对](../ai_batch/tasks.py)、[批量保存](../ai_batch/runner.py)。

### 2026-10-14 写入接口修正与已有数据恢复

2026-10-14 用户反馈：第一次运行因并发超额停止，第二次运行在第一个月读取时失败。读取结果为四行、六个结果列，索引仍为 `date/id`；对应任务的状态为 `"1"`，结果已有值，但 `config_hash`、`text`、`user_name` 显示为 `NaN`。数据库仍保留九个普通列的表结构。

原实现把部分列交给 `update_by_index`，没有保留未提交的任务输入和配置标识。用户确认 xdata 的 `update_by_column(path, df)` 支持保留原索引、只更新提交列，因此恢复状态、认领、最终保存、异常收尾及保存重试统一使用该接口。沿用上表的列范围、读回核对和重试预算，避免重复传输原帖或写回未修改字段。

例如一条任务原有 `text="原帖"`、`user_name="用户"` 和配置标识 H，成功保存时只提交六个结果列，保存后这三个值仍为原帖、用户和 H。恢复状态只提交 `status`，认领只提交 `status/config_hash`。

模拟客户端只提供 `update_by_column`，用于检查程序采用正确接口。测试覆盖状态恢复、认领、成功与失败保存、异常收尾及部分写入重试，并检查原输入、配置标识和非目标字段保持原值。真实客户端的按列保存与异常后读回一致性仍需接入验证。

后续用户反馈：使用新代码运行时，一批任务为 `"9"`，有配置标识但缺少 `text/user_name`；另一个收到 429 的任务为 `"-1"`，配置标识也缺失。用户确认缺失值直接在数据库中看到，重新启动的进程加载的是 `update_by_column`，手动调用该接口可保留其他列，并允许只提交索引键对应原记录的部分行。真实运行中字段丢失的具体原因仍未确定，需要继续检查实际提交的 DataFrame 与保存前后的记录。

本地诊断实验将模拟客户端设为“用提交字段替换整行，未提交字段变为缺失”，复现了相同的两类记录；程序内存中的帖子输入仍完整。这说明现象符合认领和最终保存阶段的覆盖模式，但实验不能证明真实客户端内部采用相同实现。

检查真实调用时，在 `ai_batch/tasks.py` 的 `self.cli.update_by_column(...)` 行设置断点，调用前查看 `stage`、`self.pending_patch`、列名、索引名及缺失值数量。实际提交的是该表的深拷贝。索引应与 `self.df.loc[self.pending_patch.index].index` 相等，所有本次提交的值都应为字符串；允许只包含批次对应的部分行。

修正接口不会自动恢复已经丢失的数据。本次用户确认源表还能提供 `text/user_name`，且上次运行后没有修改提示词模板或 `api.payload`，由用户手动按原 `(date, id)` 恢复输入，并使用当前配置计算原配置标识：

如果仍停在调试断点，在调用堆栈中选择 `ai_batch/tasks.py` 的 `TaskStore.__init__`，执行 `config_hash(self.config)` 即可取得当前已加载配置的摘要。单独计算时可以执行：

```python
from ai_batch.config import config_hash, load_config

digest = config_hash(load_config("ai_config.yaml"))
print(digest)
```

以上代码在项目根目录、原运行环境执行；若任务配置指定其他 AI 配置文件，应使用该实际路径。只修改并发等运行参数不影响摘要。将摘要补回受影响的成功记录，保留状态和已有结果；手动保存这些修复列也使用 `update_by_column`。检查范围包括所有受影响记录，不仅检查已成功的四条。

已有损坏记录不能通过补空列恢复。以后如果提示词模板或 `api.payload` 已修改，必须找到上次配置或备份才能恢复原摘要，不能使用新配置冒充原配置。

## 8. 停止、并发与实际保证

一个任务表只支持一个处理程序写入，其他新任务创建流程也须协调写入。同步客户端始终在调用入口线程使用，AI 请求在独立网络线程执行。

默认同时处理 100 个网络作业，完成消息及结果缓存有容量限制；实际参数来自 AI 配置。每月数据表仍可能很大，按月读取和有界结果缓存不代表整个程序有固定内存上限。两端日期未设置时会全表读取。

答复通过原 `(date, id)` 与帖子关联，不能按答复到达的行号配对。2026-10-14 用户反馈 xdata 在第 86 行附近拒绝无序或重复索引；本地复现确认旧实现能保持键与答复的对应，但会直接提交完成顺序形成的无序批次，即使键全部唯一也能触发同类拒绝。此次修复在统一更新入口排序并检查重复键，实际运行的第 86 行及真实客户端行为仍需接入核实。

整体停止时不再开始新任务或重试，结束本地请求并尽力保存已取得的最终结果。已标记开始处理、但没有最终响应的任务保留 `"9"`，未开始的任务保持 `"0"`，停止后不读取后续月份。强制结束进程可能来不及保存。

本地停止不保证远端请求撤销。请求已执行但结果丢失或未保存时，下次运行可能重复调用；程序不保证服务端恰好执行一次。

正常结束表示指定范围的本轮处理及保存完成，允许存在本轮失败任务；统计区分已有成功、本轮成功和本轮失败。异常收尾日志不表示处理完成或结果全部保存。
